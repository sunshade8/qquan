# CT — Chart Trading

투자 메뉴는 전략 → CT → 급등주 순서다. CT의 주식/코인 선택과 투자 메뉴 선택은 기기에 기억된다. 주식은 기존 Toss 미국 현금 주식, 코인은 Upbit KRW 현물이다. 기본값으로 전략 생성을 시작할 수 있다. 연구 방향, 종목(주식 1–4개, 코인 BTC/ETH/SOL 1–3개), 연구 기간(90–1,095일, 기본 365일), 자본, 연구 비용은 선택 설정이다. 봉 주기는 소유자가 고르는 설정이 아니다. 연구 데이터는 1분봉이고, **규칙과 측정마다 설계자가 봉 주기(1/5/15/60분, 주식 1/5/15분)를 직접 고른다**(2026-10-16, 아래 「봉 주기 자유 선택」). 이전에 등록된 5/15/60분 패키지는 그대로 유효하다.

## 현재 로컬 데이터 정책 (2026-10-13)

기본 연구는 주식 **NVDA / Massive raw 1m**, 코인 **Binance Spot BTCUSDT / USDT 1m**다.
Settings에서 공유 Parquet 데이터를 먼저 다운로드한다. CT는 로컬 coverage를 사전 검사하고
불변 파일 snapshot/version을 고정하며, 연구 중 과거 시세 API를 호출하지 않는다.
NYSE 캘린더는 2020–2035로 확장했다. NVDA 원주가 분할 경계는 세션 격리로 처리한다.
Binance USDT 연구의 Upbit KRW 실행은 차단한다. 기존 Upbit 기록·포지션 청산은 보존한다.
아래의 기존 실행 검증/저장 기록 중 Upbit, 연구별 수집, 2025–2028 캘린더 설명은 과거 버전 기록이다.
현재 실행 명령과 정책은 [로컬 실행 문서](local-runtime.md)를 따른다.

## 판 정상화 (2026-10-14, 엔진 `ct-pattern-2`)

`docs/prompts/ct-stage1-playing-field.md`의 작업 결과다. 연구 모델을 바꾸기 전에 **판 자체**(비용, 보유 규칙, 관찰 창, 데이터 범위)를 실측 근거로 고쳤다. 새 계약은 `ct-pattern-2`이고 이전 계약·등록 패키지(`ct-pattern-1`)는 저장된 비용·규칙 그대로 같은 결과를 낸다(골든 회귀 테스트 `tests/ct-pattern-1-regression.test.mjs`가 시그널·거래·일별 곡선·게이트를 비트 단위로 고정).

### 천장 측정: 이 판에 비용 후 우위가 있을 수 있는가

[CT 천장 측정 보고서](research/ct-ceiling-2026-10-14.md) (`npm run research:ceiling`, 모델 비용 0). 1분봉 매 시점에서 다음 봉 시가 진입 → 보유 상한(60/240/390봉/당일 청산, 당일 경계 비월경) 안에서 +3×왕복비용에 −1×왕복비용보다 먼저 닿으면 양성으로 라벨링하고, 현재 DSL 10개 피처를 1분(30봉)·1시간(24봉)·일봉(10봉) 규모와 시간대로 모은 31개 피처에 깊이 ≤ 3 트리(잎 최소 표본 = 학습 일수 이상)를 확장 창 **워크포워드 4폴드**로 검증한다. 비용(현재 계약/실측 프로필/각각 2배) × 보유 상한 × 데이터(코인 180일·1년·3년, NVDA 180일·전체) 64개 조합 전부에서 **비용 2배 워크포워드 일평균이 양수인 잎은 없었다**. 64개 중 학습 구간에서 트리가 거래를 고른 조합은 51개이고 그 51개 모두 검증 구간 일평균이 음수다(1배 비용 기준; 가장 덜 나쁜 조합도 거래 4건에 일평균 −0.0004%). 무조건 진입의 거래당 비용 후 평균은 −0.19~−0.67%이고, 학습 구간(표본 내)에서는 64개 중 52개 조합에서 비용 후 양수인 잎이 보였지만(최대 거래당 +1.24%) 표본 밖에서는 어느 폴드 묶음도 양수가 아니었다(양수 폴드 최대 1/4, 해당 조합도 합계 음수). 표본 내에서만 보이는 우위는 판의 우위가 아니라 과적합이라는 뜻이고, 그래서 이 판에서 "학습 구간에서 양수"는 증거가 되지 못한다. 반복 검정은 조합 64 × 폴드 4 × 피처 31 = 7,936건(트리가 평가한 후보 분할 약 170만 개)이다. 이 결과는 2·3번 작업(규칙 언어 확장, 에이전트 구조)을 하지 말라는 근거가 아니라 **무엇을 기대하면 안 되는지**의 기준이다: 단순 피처 세트의 얕은 트리가 못 찾는다는 뜻이지 어떤 규칙도 없다는 증명이 아니다.

### 비용 프로필 (`lib/ct-costs.ts`)

거래소별 **버전이 있는 프로필**이 `replayCT`가 쓰는 수수료·세금·스프레드·슬리피지를 정한다. 새 계약은 프로필에서 숫자를 뽑아 `contract.costs`에 동결하고 `contract.costProfile: {id, version}`을 함께 저장한다. 이전 계약과 등록 패키지는 `costProfile`이 없고 저장된 `costs`만 읽는다(테스트: `tests/ct-contract.test.mjs`). 화면은 연구 시작 카드와 진행 바에 프로필·버전·잠정 여부·왕복 비용을 보여 준다.

| 프로필 | 수수료 | 스프레드·슬리피지 | 출처 |
| --- | --- | --- | --- |
| `binance-spot-usdt` v1 (새 코인 연구) | 편도 0.1%(Regular User maker/taker 0.100%, BNB 할인은 가정하지 않음) | **실측 p90**, 종목·주문 규모별(`lib/ct-cost-measurements.ts`) | [Binance 수수료표](https://www.binance.com/en/fee/schedule), 2026-10-14 확인 |
| `upbit-krw` v2 (참고, 새 계약에 쓰지 않음) | **0.05%**(원화마켓 일반 주문, 매수·매도 동일) — [Open API 주문 가능 정보 문서](https://docs.upbit.com/kr/reference/available-order-information)(수정 2026-10-07)의 `bid_fee`·`ask_fee`·`maker_*` 값 0.0005, 2026-10-14 확인. v1의 0.139%는 **예약주문** 요율로 Open API 일반 주문에 적용되지 않는다. 실전 진입은 주문 가능 정보의 실제 수수료가 0.05%를 넘으면 계속 차단한다 | 실측 p90 | [Upbit Open API](https://docs.upbit.com/kr/reference/available-order-information) |
| `toss-us-equity` v1 (주식) | 기존 `lib/broker-costs.ts`(편도 0.1% + SEC 매도 0.0008%) | 기존 가정 0.05%/0.03%, **측정하지 않음** | `docs/toss-api.md` |

**스프레드·슬리피지 측정** (`scripts/data/measure-orderbook.mjs`, 인증 없는 공개 API만): Binance `depth`(500호가)와 Upbit `orderbook`을 1분마다 BTC·ETH·SOL 스냅샷으로 저장(SQLite `ct_orderbook_samples`)하고, $1,000와 $10,000(자본의 10배) 시장가 매수·매도가 mid를 얼마나 미는지 호가를 직접 걸어 계산한다(Upbit은 KRW-USDT 환산). 프로필 값은 **측정 p90을 올림**한 값이고 측정값 아래로 내려가지 않는다(`--check`가 이를 확인하고 낮으면 실패). 스프레드 = p90 스프레드, 슬리피지 = p90 편도 충격이 반 스프레드를 넘는 부분이라 `spread/2 + slippage ≥ p90 충격`이다. 자본이 1,000 이하면 $1,000 값, 그 이상이면 $10,000 값을 쓰고 선택한 종목 중 최악의 값으로 계약을 만든다.

실측 결과(초기 약 30분 표본): Binance BTCUSDT는 스프레드·충격이 ≈0.00001%로 **가격 틱(0.01 USDT) 수준**이고 ETHUSDT 0.0004%, SOLUSDT 0.009%다. 이전 계약이 가정한 스프레드 0.05% + 슬리피지 0.03%(편도 0.055%)는 BTCUSDT에서 약 4,000–9,000배 과대였다. 그래서 BTC 왕복 비용은 0.3095%에서 **약 0.200%**(수수료 0.1%×2가 거의 전부)로 내려갔다. 반대로 Upbit KRW-BTC는 $1,000에서도 편도 충격 p90 0.06%로 Binance보다 훨씬 비싸다 — Binance 연구와 Upbit 실행이 다르다는 기존 차단 정책의 근거가 하나 더 생겼다.

**잠정**: 측정 72시간(`CT_PROFILE_MIN_HOURS`)을 채우기 전의 프로필은 `provisional`로 표시된다. 샘플러는 72시간 실행으로 시작했다(`npm run data:orderbook -- --hours=72`, 로그 `~/.qquan/logs/orderbook-sampler.log`). 끝난 뒤 `npm run data:orderbook -- --profile --write-lib`로 표를 갱신하고 `--check`로 확인하면 잠정 표시가 사라진다(프로필 버전 변경 시에는 `version`을 올린다). **측정으로 알 수 없는 것**: 신호 봉 종가와 실제 체결 사이의 지연, 큐 위치, 역선택. 프로필은 실거래 비용의 하한이지 예측이 아니며, 게이트의 **비용 2배 스트레스는 그대로 유지**된다.

### 단타 보유 규칙

CT는 단타다: 포지션은 하루를 넘기지 않는다. **코인의 하루는 UTC 00:00 = KST 09:00**이다(게이트의 코인 일별 집계가 이미 UTC 날짜라 하루 손익이 그날 안에서 닫히고, Binance·Upbit의 일봉 경계도 이 시각이다). 주식은 정규장 종료다.

- 청산 방식: 주식 `session`과 같다. 하루의 마지막 거래 봉(UTC 23:59에 닫히는 봉, 주식은 종료 1분 전에 닫히는 봉)의 **종가**로 청산하고 사유는 코인 `day_end`, 주식 `session`이다. 신규 진입은 그 마지막 봉에서 막힌다. 백테스트(`replayCT`), 모의·실전(`ct-trading-engine.ts`), 설계 도구(`query_conditional_returns` 손절·목표 격자, `cost_hurdle`)가 **같은 함수**(`ctDayClosing`, `ctForcedExit`, `ctEntryBlocked`)를 쓴다. `ct-pattern-1` 코인은 이전처럼 연속(강제 청산 없음)이다.
- `maxHoldBars` 상한: 코인 1,440(주식 390 유지). `spec.exit.maxHoldBars`는 시장별로 검증한다.
- `entry.noEntryBeforeDayEndMinutes`(0–240, 기본 0 = 없음): 하루 끝 N분 전부터 신규 진입을 막는다(주식 포함). 0과 생략은 같은 실행 해시다.
- `cost_hurdle`: 코인 보유 지평에 720·1,440봉과 **당일 경계까지**(`bars: 0`, 가변 길이)를 추가했고, 모든 지평을 당일 경계에서 잘라 계산한다(`ct-pattern-2` 계약만; 이전 계약은 이전 표).
- 학습/개발 경계가 UTC 자정에 정렬돼 있으므로 `ct-pattern-2` 코인 연구에서는 포지션이 구간 경계를 넘지 않는다.

### 관찰 창: 상위 시간대

`condition.timeframe`에 **60·240·1440**(1시간·4시간·일봉)을 추가했다(`ct-pattern-2`). 1분 원봉에서 **완성된 봉만** 집계한다(`lib/ct-timeframes.ts`): 코인은 UTC 격자(일봉 = UTC 하루), 주식은 정규장 개장 기준 격자(첫 봉 09:30–10:30…, 조기 폐장·마지막 봉은 짧게, 일봉 = 정규장 한 세션) — 기존 UTC 격자의 "개장 첫 30분은 60분 봉이 되지 않는" 한계를 이 시간대에서는 고쳤다. 1분 중 하나라도 빠진 봉은 만들지 않는다(합성 없음). lookback 상한은 시간 배수와 함께 검증한다: **관찰 가능한 과거는 최대 30일**(`lookback+offset+1`개 봉이 차지하는 일수, 주식은 세션 수; 일봉은 `lookback+offset+1 ≤ 30`).

- 주식: 1·3·12분 조건은 기존대로 세션 안 연속 봉만 쓰고, 60/240/1440 조건은 **이전 세션의 완성 봉**까지 이어 쓴다(주말·휴장은 이어지고, 거래일인데 데이터가 비었으면 끊긴다). **분할·기업행사 경계는 격리**한다(`CT_STOCK_SPLITS`, 예: NVDA 2024-06-10 전후의 창은 합치지 않음).
- 성능: 심볼·시간 배수별 상위봉을 리플레이마다 한 번 만들고(`ctHigherSets`) 이진 탐색으로 참조한다. 구간 밖(`fromMs` 이전, `toMs` 이후) 봉은 시리즈에 넣지 않는다. 코인 1분 원봉을 1,500봉만 들고 다니는 한계는 상위 시간대 조건에 적용되지 않는다(상위 시리즈가 대신한다).
- 실전·모의에서 이 조건을 쓰려면 이력이 필요하므로 `ctRecentBars`의 주식 웜업 일수가 규칙의 조건에서 계산된다(`ctWarmupDays`). Binance 연구 규칙은 Upbit에서 실행하지 않는다(기존 차단).

### 데이터 범위

- 요청 `days`: 90–1,095일(코인 3년). 주식은 로컬 데이터가 있는 만큼(현재 약 2년, Massive 계정은 2024-10-12 이전 구간이 HTTP 403)이며 부족하면 시작 전에 부족 구간을 알려 준다. **기본값은 365일**이다. 근거: 하루 0.4건 수준의 셋업이면 180일의 개발 구간(36일)은 약 14건으로 최소 20건 게이트에 구조적으로 걸리지만 365일(개발 73일)은 약 29건이라 표본이 생긴다. 천장 측정에서는 1년과 3년이 부호를 바꾸지 않았고(둘 다 비용 후 우위 없음) 3년은 리플레이·도구 시간이 3배라 기본으로 쓰지 않는다. 3년은 선택으로 열어 둔다.
- 시간순 60/20/20 분할과 최종 구간 1회 사용은 그대로다. 개발·최종 결과 요약에 **분기별 일평균 순수익과 양수 분기 비율**(`ctStability`)을 추가했다 — 게이트는 바꾸지 않았고 설계자·독립 검토자에게 보여 주는 안정성 정보다.
- 계산 예산: 새 계약 `maxComputeMs` 600초 → **1,200초**. 측정: 1년 BTC 1분봉 `replayCT` 약 1.2초, 3년 약 3.9–4.8초, `query_conditional_returns` 1년 2.1–2.8초·3년 6.3–8.8초, `cost_hurdle` 3년 5.1초(변경 전과 동일 코드 경로는 처리 시간이 같다 — 아래 검증 절). 3년 연구에서 설계 세션당 도구 24회와 실험 묶음을 합치면 600초에 근접하므로 새 계약만 올렸다. 활성 작업 한도 3,600초는 그대로다(이전 계약은 각자 저장된 값).
- **코인 종목 추가**: ETHUSDT·SOLUSDT를 같은 Binance Public Data 파이프라인으로 받는다(`store.py`의 `eth`·`sol` 데이터셋, Settings 버튼·catalog·coverage·품질 보고 동일, 다운로드 스크립트 `scripts/data/download-eth-minute.py`·`download-sol-minute.py`). 연구는 BTC/ETH/SOL 1–3개를 고를 수 있고 종목마다 불변 snapshot이 따로 계약에 고정된다(`contract.dataSnapshots`). 종목 집중도 게이트(80%)는 그대로다.

### 진입 시간 창

`entry.entryWindows`(최대 3개, `{fromMinute, toMinute}`)는 **하루 시작 후 경과 분**으로 쓴다: 코인은 UTC 00:00(KST 09:00), 주식은 정규장 개장(0–389). 신호 판정 시각(마지막 단계 완성 봉의 끝)의 경과 분이 `fromMinute ≤ m ≤ toMinute`일 때만 진입한다(양끝 포함; `{0, 30}` = 개장 후 30분 = 봉 마감 1…30분). 창은 개장 기준이라 조기 폐장일은 하루가 더 일찍 끝날 뿐이다. `noEntryBeforeDayEndMinutes`와 함께 동작한다. 라이브 러너는 `signal.decidedAt`(백테스트와 같은 시각)로 판단한다.

### 레벨·ATR 피처

모두 그 시점까지 완성된 봉만 쓴다. 하루는 코인 UTC 일자, 주식 정규장 세션이다. 하루의 첫 봉이 하루 시작에 정확히 시작하고 그 뒤 봉이 빠짐없이 이어질 때만 값이 있다(분 하나가 빠진 날의 VWAP은 VWAP이 아니다) — 아니면 null. 전일 값은 직전 **완성** 일봉(`prevDailyBar`)에서 오고, 직전 세션이 비었거나 분할 경계를 넘으면 null이다(주말·휴장은 이어진다).

| feature | 정의 | 고정 파라미터 |
| --- | --- | --- |
| `vwap_distance_pct` | 종가 / 당일 누적 VWAP − 1 (VWAP = Σ(전형가×거래량)/Σ거래량, 전형가 = (고+저+종)/3) | lookback 2 · offset 0 · timeframe 1 |
| `prev_day_high/low/close_distance_pct` | 종가 / 전일 고가·저가·종가 − 1 (개장 직후 종가 대비는 갭) | 같음 |
| `day_open_distance_pct` | 종가 / 당일 시가 − 1 | 같음 |
| `opening_range_position` | (종가 − OR 저가)/(OR 고가 − OR 저가), OR = 당일 첫 `lookback`분. 0–1 밖 = 돌파. OR 미완성·고저 같음 → null | `lookback` = OR 길이(≥5분), offset 0, timeframe 1 |
| `day_range_position` | 당일(그 봉까지) 고저 안 위치 0–1 | 고정 |
| `atr_pct` | `lookback`봉 평균 진폭(TR 평균) / 종가 × 100, `timeframe` 완성봉 | |
| `atr_percentile` | 현재 ATR이 최근 `lookback`개 ATR 중 몇 분위(앞선 값 중 현재 이하 비율, 0–1), ATR 길이 `atrLookback`(기본 14) | |

의미 없는 파라미터는 스키마가 고정값을 강제한다(설계자가 쓸모없는 숫자를 탐색하지 못하게). 차트 근거(`signal.references`)는 실제로 쓴 선(VWAP, 전일 고가·저가·종가, 당일 시가, 당일 고저, 시가 범위 상·하단)을 표시한다.

**`unit: "atr"`**: 수익률·거리 조건(`return_pct`, `*_distance_pct`, `range_pct`)의 값을 고정 %가 아니라 **ATR 배수**로 비교한다 — 값(%) ÷ ATR%. ATR은 `atrTimeframe`(기본 조건의 timeframe)의 `atrLookback`(기본 14)봉을 판단 시점(offset 0)에서 읽는다. 1분봉 조건에 `atrTimeframe: 60|1440`을 쓰면 시간·일 단위 변동폭으로 거리를 잰다. 비율·위치 피처와 ATR 피처에는 쓸 수 없다. 기본값을 명시한 것(`unit` 생략, `atrLookback 14`, `atrTimeframe` = 자기 시간대)은 같은 실행 해시다.

### 관리형 청산과 `ctExitStep`

`exit`는 두 모양 중 하나다. 고정형(`stopPct`, `targetPct`, `maxHoldBars`, `invalidation`)은 모든 엔진에서 그대로이고, 관리형은 `ct-pattern-3`에서만:

```
exit: { stop: {type: pct|atr|pattern_low|swing_low, value}, target?: {type: pct|atr|r, value},
        breakeven?: {triggerR, offsetPct?}, trail?: {type: pct|atr|swing_low, value, activateR},
        timeStop?: {bars, minR}, atr?: {timeframe, lookback}, maxHoldBars }
```

R = 초기 위험 = 진입가 − 초기 손절. `pattern_low`·`swing_low`의 `value`는 그 레벨 아래 여유폭(%)이다. 초기 손절이 진입가 이상이거나 15%보다 멀거나(또는 ATR·확정 스윙이 없으면) 그 신호는 **진입하지 않는다**(`blocked.invalid_stop`) — 추측한 손절로 거래하지 않는다.

**하나의 순수 함수**: `ctExitStep(spec, signal, position, bar, forced) → {position', exit | null}`을 `replayCT`, 모의·실전 러너(`ct-trading-engine.ts`), 설계 도구(손절·목표 격자, 청산 모드 비교)가 모두 쓴다. 러너의 손절가 인라인 재계산은 없앴고 `position.stopLevel`을 읽는다. 백테스트와 운용의 손절가가 갈라질 경로가 없다.

봉 안의 순서(보수적):

1. 그 봉 **이전에** 서 있던 손절을 먼저 검사한다(불리한 갭은 시가 체결, 손절·목표가 같은 봉이면 손절 먼저).
2. 목표, 시간 손절(`bars`번째 봉에서 한 번), 최대 보유(고정형 사유 `time`, 관리형 `max_hold`), 호출자가 넘긴 당일 경계 강제 청산(`day_end`/주식 `session`) 순이다.
3. 봉이 살아남은 뒤에만 그 봉의 고가로 `highestHigh`·본전·트레일을 갱신한다. 올라간 손절은 **다음 봉부터** 적용된다 — 같은 봉에서 트레일을 올리고 같은 봉 저가로 그 트레일에 걸리는 낙관·비관 혼합이 없다.

손절은 올라가기만 한다. 본전은 `+triggerR` 도달 시 `진입가 × (1 + offsetPct/100)`로, 트레일은 `+activateR` 도달 뒤 `pct`(최고가 × (1 − v)), `atr`(최고가 − v × 판단 시점 ATR), `swing_low`(진입 후 확정된 마지막 스윙 저점 × (1 − v), 5봉 중앙이 가장 낮을 때 확정)를 따른다.

**청산 사유**: `stop`, `breakeven`, `trail`, `target`, `time_stop`, `max_hold`(고정형은 `time`), `day_end`(주식 `session`), 구간 경계 `boundary`, 라이브에서 손절을 만들 수 없을 때 `invalid_stop`. 거래 기록(`CTTrade.management`: 초기 손절·목표·손절선 이동 이력, 고정형 거래에는 이 필드가 없다)과 차트(손절선 계단, 사유 라벨)에 남는다. 운용 거래는 `ctPosition`·`ctExitReason`을 거래 레코드에 저장한다.

**운용 상태**: 러너가 재시작하면 저장된 `ctPosition`에서 이어 가거나, 없으면 진입 봉부터 `ctRebuildPosition`으로 결정적으로 다시 계산한다. 두 방식이 같은 결과를 낸다는 테스트가 있다. 운용은 진입 봉(신호 봉이 닫힐 때 열리는 봉)부터 판단한다 — 백테스트가 진입 봉도 판단하는 것과 같다(이전에는 체결을 확인한 시각 이후 봉만 봤다).

**스트레스 "손절 ±10%"의 정의**: 고정형은 이전과 같이 `stopPct`에 ×0.9/×1.1(0.2–15%로 자름)을 적용한다. 관리형은 **초기 손절 거리**(`진입가 − 초기 손절`)에 ×0.9/×1.1(`replayCT`의 `stopScale` 옵션)을 적용하고 본전·트레일·시간 손절 파라미터는 그대로 둔다(R 목표는 그 R에 정의되어 있으므로 함께 움직인다).

### 설계 도구

- `query_conditional_returns`: 새 피처·`unit`·`entryWindows`를 받는다. `exitCompare`(선택)는 **같은 이벤트**를 고정 손절·R 목표 / 본전 이동 / 트레일(목표 없음) / 시간 손절로 나란히 돌려 행마다 이벤트 수, 승률, 평균 R, 비용 후 평균, 비용 2배 평균, 일평균(이벤트 합 ÷ 학습 일수; 겹침 무시한 상한 감각), 청산 사유 비율을 준다(학습 구간만, 손절 ≤ 3 × 목표 R ≤ 2 × 모드 3 + 트레일 ≤ 21행). 이벤트 목록과 청산 규칙은 `ctOpenPosition`+`ctExitStep` 그대로다.
- `screen_rule`은 새 spec을 받고 결과에 `freedom`(자유도)과 `multipleTesting`을 붙인다. `ctRuleText`는 새 요소를 한국어로 쓴다(고정형 규칙의 문장은 이전과 같다).
- `CT_DESIGNER_SYSTEM`: 새 어휘를 나열하는 데서 그치지 않고 각 어휘를 언제·왜 쓰는지 설명한다. "청산 구조로 비용을 이기는 방법"(R로 본 비용, 손실·이익의 비대칭, 변동성에 맞춘 손절, 본전·트레일·시간 손절의 이유)은 비용 장벽 설명 바로 뒤에 있다. 시스템 프롬프트와 도구 정의는 상수라 실행 중 바이트가 바뀌지 않는다(캐시 유지).

### 다중 검정 장부와 자유도

설계 세션의 모든 `query_conditional_returns`·`screen_rule` 호출을 **가설 서명**으로 센다: 단계별 `feature|timeframe|방향|단위`의 집합과 시간 창 사용 여부. 임계값·lookback·offset·maxGapBars·청산 숫자가 다른 변형은 같은 서명(1회), 다른 feature 조합·반대 방향·ATR 단위·시간 창은 새 검정이다. 연구 단위로 누적(`ct.tests`)하고,

- 설계자에게는 매 도구 결과에 `multipleTesting: {hypothesisTests, toolCalls}`로 짧게,
- 위험·증거 검토자에게는 `research.multipleTesting`(검정 수 + 후보 자유도)과 새 지시("검정 수 대비 개발·최종 결과의 유의성을 판단하라, 어휘가 늘었으니 단순한 규칙을 선호하라")로 전달한다.

후보의 **자유도** = 조건 수 + 청산 숫자(손절·목표·본전·트레일·시간 손절·최대 보유·ATR 설정) + 시간 창 끝점·진입 금지·ATR 단위 등 기타. 결과 요약(`screen_rule`, 이전 세션 후보 기록)과 검토 입력에 표시한다. 게이트는 바꾸지 않았다.

LLM은 수치 공간을 손으로 탐색하는 데 약하고 "이 패턴에 메커니즘이 있는가, 우연인가"를 판단하는 데 강하다. 그래서 **서버**가 거래할 가치가 있던 순간과 그 직전의 차이를 통계와 그림으로 정리하고, **설계자(Opus)**가 메커니즘을 판단하고 규칙으로 옮기고 스스로를 의심한다. 새 기능은 `policy.traderTools = 1`이 있는 **새 계약에서만** 켜진다. 이전 계약(턴 12·도구 24, 기존 4개 도구, 이전 지시문)은 바이트 단위로 그대로 돈다(`CT_DESIGNER_SYSTEM_STAGE2`의 SHA-256을 테스트가 고정). 게이트·롱 전용·당일 청산·1분봉·시간순 60/20/20·최종 구간 1회 평가는 바꾸지 않았다. **모든 새 도구는 학습 구간 전용**이고 앞을 내다보는 구간이 `trainingToMs`를 넘는 라벨·대조군·차트·거래는 버린다(자르지 않는다).

|---|---|
| `label_moves` | `k`(목표 = k × 왕복 비용, 기본 3) · `m`(손절 = m × 왕복 비용, 기본 1) · `horizon`(5–1,440봉 또는 `day_end`) · `costMultiplier`(1·2). 모든 분에서 다음 봉 시가 진입 후 목표가 손절보다 먼저 닿으면 양성(`labelMoves`, 천장 측정과 같은 함수). 양성 순간 수, **사건 수**, 하루 평균, 기저율, 시간대·변동성 국면·요일·월별 분포(사건 비율 ÷ 전체 유효 순간 비율 = lift), 서버가 발급하는 대표 이벤트 시각 12개와 짝지은 대조군 시각 12개, `labelId`. |
| `contrast_moves` | `labelId` + 피처 명세 ≤ 12개(feature·lookback·offset·timeframe·unit, 임계값 없음). 이벤트 대표 시점의 피처 분포와 **같은 시(하루 시작 후)·같은 달**에서 시드 고정으로 사건당 3개 뽑은 대조군의 분위수, 대조군 5분위별 이벤트 수·lift·z. `tree: true`면 깊이 ≤ 3 트리를 **앞 2/3 학습 일수**로 키우고(뒤 1/3 시작 뒤에 청산되는 순간은 제외) **뒤 1/3**에서 같은 잎의 lift·양성 비율·비용 후 평균을 다시 잰다(잎마다 라벨과 같은 청산 구조 하나를 가정). `contrastId`는 **같은 feature·timeframe을 측정한 조건**에 한해 근거 id로 인정된다. |
| `view_charts` | 서버가 발급한 시각만(이벤트·대조군·조회 앵커·`screen_rule` 거래 시각), 호출당 ≤ 8장, 세션 ≤ 32장. `blind: true`는 이벤트와 대조군을 같은 수로 섞어 무작위 순서·그룹 숨김으로 보여 준다. 이미지는 `tool_result`의 image 블록. |
| `grade_blind` | 블라인드 세트의 모든 차트에 positive/control 예측을 한 번에 제출 → 정확도와 **정확 단측 이항검정 p값**(세트가 균형이라 귀무가설은 50%). 세트는 한 번만 채점되고 채점 뒤 정답을 공개한다. 설계자의 "눈"이 이 시장에서 신호를 갖는지 스스로 확인하는 장치다. |
| `diagnose_trades` | `screen_rule`의 `screenId`(또는 후보 id)의 **학습 구간 거래**를 시간대·변동성 3분위·1시간 SMA20 위/아래·요일·보유 시간·청산 사유로 분해하고, 손실 거래 중 +1R(또는 왕복 비용 2배)에 한 번이라도 닿은 비율(**청산 문제**)과 비용만큼도 못 오른 비율(**진입 문제**), 이익 거래의 MFE 대비 실현 비율, 같은 진입에 다른 청산(원래 규칙·고정 2R·+1R 본전·+1R 트레일·시간 손절)을 `ctOpenPosition`+`ctExitStep`으로 적용한 결과, 필터 힌트를 준다. `diagnosisId`는 `range_pct`(1분)·`sma_distance_pct`(60분)에 한해 근거로 쓸 수 있고, 진단 필터를 쓴 후보는 `observedProblem`·`changes`에 부모 대비 변경을 적어야 한다. |

**사건 묶음 규칙**: 종목별로 시간순 스캔해 첫 양성 순간 i0에서 사건을 열고 i0의 거래가 목표에 닿는 봉까지 나오는 양성 순간은 같은 사건이다. 그다음 양성 순간부터 새 사건이다. 대표 시각은 사건 안 양성 순간들의 **중앙값 순간**의 봉 마감이다(첫 순간은 원인이 아직 보이기 전이고 마지막 순간은 이미 움직임 안이라서, 거래할 수 있었던 순간들의 한가운데를 쓴다).

**다중 검정 장부 합산**: `label_moves` 정의 1회, `contrast_moves`는 feature × 대조군 5분위마다 1회(라벨 정의가 다르면 다른 가설), `diagnose_trades`는 확인한 층 칸마다 1회, 블라인드 세트 채점 1회가 각각 서명으로 장부에 들어간다. 트리가 평가한 후보 분할 수는 서명이 아니라 `treeSplitsEvaluated`로 따로 보고한다. 도구 결과의 `multipleTesting`은 `conditionCombos`·`contrastCells`·`diagnosisCells`로 나뉘어 나온다.

### 차트 이미지

SVG를 그린 뒤 `@resvg/resvg-wasm`(WebAssembly, 네이티브 바이너리 없음, 어느 머신에서나 같은 바이트, Node·Workers 모두 가능)으로 PNG로 바꾼다. resvg-wasm은 텍스트를 렌더링하지 못하므로 글자는 `@pdf-lib/fontkit`으로 `assets/fonts/NotoSans-Regular.ttf`(OFL)의 윤곽을 벡터 경로로 그린다(시스템 폰트 무관). 한 장 1,420 × 456px, PNG 약 65KB, 렌더 약 0.2초, 입력 약 860–1,100토큰. 왼쪽 최근 5일 1시간봉(+전일 고가·저가), 가운데 당일 5분봉(VWAP·시가 범위 첫 30분 박스·전일 고가·저가·종가), 오른쪽 앵커 직전 90분 1분봉 + 거래량. **앵커 이후 봉은 읽지도 않는다**(앵커 뒤를 오염시켜도 PNG가 비트 단위로 같다). 축은 가격이 아니라 **앵커 종가 대비 %**, 날짜는 없고 시각만 있다. 이미지 base64는 세션 메시지(`ct_session_messages`)에 그대로 저장되어 이후 턴 요청에 바이트 그대로 다시 실리고(캐시 읽기 유지), 화면용 사본은 `ct_chart_images`에 있다. 비용 예약과 실시간 추정은 base64 글자 수가 아니라 이미지당 약 1,100토큰으로 센다(`lib/designer-request-size.ts`).

### 플레이북 (`lib/ct-playbook.ts`)

시장 단위 누적 기억이다. `ct_playbook`(아이디어 하나 = 한 행: 시장·종목·주기·메커니즘·조건 구조(feature·timeframe, 임계값 제외)·검증 방식·결과 등급·사유·**측정 기간**·비용 프로필·엔진·실행 id)과 `ct_playbook_runs`(실행별 가설 검정 수 = 누적 검정 수의 원천). 연구가 끝날 때(정상 종료·통과·탈락 모두) 설계 세션의 `rejectedHypotheses`(`rejected_in_training`), 학습 게이트 탈락 후보(`screen_failed`), 개발 결과(`development_failed`), 최종 구간을 연 후보(`passed_final`/`failed_final`)를 기록한다. 같은 실행을 두 번 기록해도 같다(결정적 id). 이 작업 이전에 끝난 실행은 처음 읽을 때 한 번 소급 기록한다(`source: backfill`). 시드는 `docs/research/results-2026-09.md`의 가설 10개(`timeframe: daily`, `comparable: false` = 단타와 직접 비교 불가; H2만 `adopted_daily`, 나머지는 `development_failed`)이며 주식 시장 항목이고 1분봉 누적 검정 수에는 섞지 않고 `dailyTests`로 따로 보여 준다.

**누출 규칙**: 항목의 측정 기간이 **새 연구의 개발·최종 구간**(`[trainingToMs, toMs]`)과 겹치면 메커니즘과 결과 등급·사유만 보여 주고 `detail` 수치를 빼며 자유 서술 사유의 숫자도 `#`로 가린다. 새 연구의 학습 구간 안에서만 측정된 항목은 수치를 보여 준다. **최종 구간 성과는 어디에도 저장하지 않는다**(테스트: 최종 수익률 99.9를 넣은 실행을 기록해도 저장된 어떤 행에도 없음). 기존 `ctMemory`도 같은 규칙을 따른다(겹치면 `netReturnPct: null`). 설계 세션 안정 블록(캐시)에는 같은 시장 최근 40개(1분봉 먼저), 이전 실행 수, **누적 검정 수**가 들어가고 실행 시작 때 한 번 고정되어(`playbook_summary` 도구 캐시) 재개해도 같다. 위험·증거 검토자에게는 누적 검정 수(이 실행 + 이전 실행)와 플레이북 항목, 라벨·contrast·차트·블라인드 결과·진단 요약, 후보의 `selfRebuttal`이 가고 지시에 "이미 기각된 메커니즘의 변형인가, 누적 검정 수를 고려해도 개발 결과가 의미 있는가"가 들어 있다. CT 화면의 「플레이북」 섹션(접이식)이 읽기 전용 목록과 등급·주기·검색 필터를 보여 준다. 5단계에서 계열 단위 교훈과 커버리지 지도가 더해졌다 → [연구 교훈](#연구-교훈-2026-10-15-설계-세션-5단계).

### 설계자의 작업 순서와 한도

`CT_DESIGNER_SYSTEM`을 "단타 고수의 작업 순서"로 다시 썼다(단계를 강제하지 않고 이유를 설명한다): ① 판 읽기(비용 장벽·플레이북·누적 검정 수) → ② 거래할 가치가 있던 순간 보기(`label_moves`, `view_charts`) → ③ 직전의 차이 찾기(`contrast_moves`, 블라인드 보정) → ④ 메커니즘과 반증 조건 → ⑤ `query_conditional_returns`로 확인 → ⑥ 청산 모드 비교 → ⑦ `screen_rule`·`diagnose_trades` → ⑧ **제출 전 자기 반박**: 새 필드 `selfRebuttal`(우연일 가장 그럴듯한 이유 3개 이상, 각각의 배제 방법과 `excluded: yes|partly|no`)을 새 계약의 모든 제출 후보에 요구한다. `contrast_moves`의 lift는 단서일 뿐 성과 근거가 아니며 최종 확인은 `query_conditional_returns`·`screen_rule`로 한다.

한도(새 계약): 세션당 모델 턴 **16**, 도구 호출 **40**, `screen_rule` 6, 차트 이미지 **32장**, 블라인드 세트 **2**. 이전 계약은 12/24/6, 이미지 없음. 진행 화면은 새 도구를 "지금 하는 일"과 피드에 표시하고, 세션 섹션에 이벤트 수·최대 lift·본 차트 썸네일·보정 정답률(p)·복기 요약(손실 중 +1R 도달 % / 수익권 미도달 %)·가설 검정 수를 보여 준다(`traderSummary`, `lib/ct-activity.ts`).

**보정 모드**: 8장 중 6장 적중 · 정확도 75% · **p = 0.145**. 설계자는 "눈으로 사건과 대조군을 가르는 능력이 입증되지 않았다"고 기각 가설로 기록했다.

**contrast의 읽는 법**: 사건 직전 특징의 lift는 하위·상위 20% 양쪽 꼬리에서 함께 올라갔다(1회차 최대 `return_pct(15, 1m)` 하위 20% ×1.88, 2회차 `return_pct(30, 1m)` 하위 20% ×1.9). 설계자는 이를 방향이 아니라 **변동성 효과**로 읽었고, 깊이 3 트리의 잎 8개는 학습과 홀드아웃 모두 비용 차감 후 순손익이 음수(−0.07~−0.31%)이며 두 잎은 홀드아웃 표본이 0이었다. lift를 성과 근거로 쓰지 않는다는 지시가 지켜졌다.

**플레이북**: 1회차 시작 때 코인 시장에 이전 실행 4개(`893af88c` 20 · `a682e11b` 13 · `ae0d8fd0` 14 · `8c2fe70f` 21회 검정, 소급 기록)의 항목 40개(그 밖 오래된 항목은 생략)와 누적 가설 검정 **68회**가 안정 블록에 들어갔다. 설계자는 세션 결론에 "플레이북에 있는 이전 4회 연구(68개 검정)의 평균 회귀·돌파·추세 지속·투매 반등 계열이 모두 실패했다"고 인용했다. 1회차 종료 시 **5개 항목**이 기록됐다(예: ① 고변동 국면 사건 직전 특징으로 +5×비용 움직임 예측 — `rejected_in_training`, ② UTC 6시간 블록 시간대 계절성 — `rejected_in_training`, ③ 시간봉 ATR 상위 + 일중 저점권 15분 급락 반등 매수 — `rejected_in_training`). 2회차에는 이 5개를 포함한 항목 40개와 누적 검정 **118회**(이전 실행 5개)가 전달되었다(개발 구간과 겹치는 3개 항목은 수치 없이 등급만, 최종 구간 수치는 0개).
- **플레이북이 실제로 피하게 했는가**: 2회차는 1회차가 기각한 **시간대 계절성, 일중 저점권 반등, 고점권 추종, 블라인드 차트 보정을 다시 하지 않았다**(턴 4 · 조회 1 · $0.434로 1회차의 59%). 다만 `label_moves` → `contrast_moves` 탐색과 "모멘텀 점화 추종"(1회차의 "고점권 추종"과 이웃한 변형)은 다시 했고, 이를 새 가설로 기각했다. 같은 아이디어를 완전히 피한 것이 아니라 **이미 기각된 계열을 인용해 더 일찍 멈춘 것**이다. 누출 규칙은 지켜졌다(전달된 40개 중 개발 구간과 겹쳐 수치를 가린 항목 3개, 수치 `detail`이 실린 항목 0개, 최종 구간 수치 0개).
- **누적 검정 수의 의미**: 이 연구가 후보 0개로 끝났기 때문에 검토자에게 가지 않았다. 후보가 생기면 위험·증거 검토자는 이 실행의 장부와 이전 실행 합계(`cumulativeHypothesisTests`)를 함께 받는다.

**주식(NVDA) 1회 `f8aeaf03`**(왕복 0.310%, 예산 $8): 총 **$0.597**(설계 Opus $0.521 · 8턴 · 도구 8회), 가설 검정 59회, 후보 0 → 0 → 0, 종료 "비용 후 우위 미발견 · 최종 기간 미개봉". 흐름은 `label_moves`(k4 · m1.5 · 당일 끝까지 → 사건 240건 · 하루 1.1건; 개장 60분 lift 3.0, 고변동 2.2) → `contrast_moves`(특징 12개 · 트리 7잎, 최대 `range_pct(60, 1m)` 상위 20% ×1.94) → 조회 2회 → `view_charts` 2회(일반 8장 + 블라인드 8장) → `grade_blind` → 제출. 블라인드 **4/8 · 정확도 50% · p = 0.637**로 눈의 판별력 없음이 기록되었다. 설계자는 차트를 보고 세운 가설(갭 상승 후 전일 종가 지지, 24건 · 모든 보유 기간 순평균 음수)을 숫자로 확인해 기각했고, 트리 잎이 학습 3일에 기대고 홀드아웃에서 lift가 뒤집힌 것을 근거로 contrast 잎을 기각했다. 시작 때 받은 플레이북은 항목 40개(이전 NVDA 실행 2개의 기록 + 2026-09 일봉 시드 10개 `comparable: false`)와 이전 검정 32회였고, 설계자는 "이전 실행의 3일 하락+VWAP 회복 후보도 개발 구간에서 실패했다"를 인용해 같은 계열을 다시 쓰지 않았다. 이 실행도 `screen_rule`까지 가지 않아 `diagnose_trades`는 호출되지 않았다.

**`diagnose_trades`**: 세 실행 모두 설계자가 `screen_rule`까지 가는 후보를 만들지 않아 실제 실행에서는 호출되지 않았다(복기할 거래가 없었다). 이 도구는 합성 시장 테스트(청산 반사실이 `ctExitStep`과 일치, 분해 합계, 학습 구간 밖 오염 무영향)와 전체 세션 테스트(`screen_rule` → `diagnose_trades` → 근거 기록 · 장부 합산)로 검증했다. 따라서 "진입/청산 문제 비율이 후보를 실제로 바꾼 사례"는 아직 없다.

**한계와 해석**: 두 번의 실행이 같은 결론(비용 후 우위 미발견, 최종 구간 미개봉)으로 끝났으므로 비용 $0.4–0.7로 "우위 없음"에 도달하는 경로가 이전보다 짧아졌다는 것 말고는 수익 전략 발견 여부에 대해 말할 수 있는 것이 없다. 두 실행은 같은 데이터·같은 계약이라 독립적인 증거가 아니고, 한 연구의 결과를 일반 무수익성의 증거로 쓰지 않는다. 블라인드 p=0.145는 표본 8장이라 검정력이 낮다.

### 판 서명과 재실행 규칙

연구를 시작할 때(**유료 호출 전**, `createCTResearch`에서 `assertFinalWindowFree`와 같은 시점) 판 서명을 계약에 저장하고 같은 소유자의 이전 실행과 비교한다(`lib/ct-board.ts`, `assertBoardFree`).

- 서명 = SHA-256( 시장 · 정렬된 종목 · 봉 주기 · 엔진 · 설계 도구 정책 버전 · 비용 프로필 id·버전과 실제 `costs` · 학습·개발·최종 경계 4개 · 종목별 데이터 스냅샷 해시 · 공백을 정규화한 연구 방향 `brief` ). 생성 시각·예산·요청 id는 넣지 않는다.
- 같은 서명의 **진행 중(running/paused)** 실행 또는 **통과 전략 없이 끝난** 실행이 하나라도 있으면 HTTP 409로 거부한다. 취소된 실행·통과한 실행은 막지 않는다. 응답에는 이전 실행 id(앞 8자)·날짜·종료 사유와 "무엇을 바꾸면 새 판인가"(종목, 기간, 연구 방향, 비용 프로필 갱신)를 한국어로 담는다.
- 서명이 생기기 전에 만든 계약은 저장된 계약과 `brief`로 서명을 계산해 비교한다. 그래서 위 세 실행은 서로 같은 판으로 인식된다(점검: `scripts/research/ct-board-check.mjs`, 실데이터·DB 읽기 전용).
- 예외: 요청에 `repeatReason`(10자 이상)을 주면 실행하고 계약에 `repeat: {n, reason, previousRuns}`를 저장한다. 진행 상태바와 설계 세션 섹션이 "같은 판 N번째 실행 · 사유"를 보이고 위험·증거 검토자 입력에 `research.repeatedBoard`로 실린다. 누적 검정 수에는 그대로 합산된다.
- 화면: 거부 메시지, 이전 실행 목록, 사유 입력란과 "그래도 실행" 버튼(사유 10자 미만이면 비활성). 기본 동작은 막는 것이다. 미리 점검(`preflight`)도 같은 거부를 준다.
- **도구 버전이 바뀌면 같은 데이터도 한 번 다시 볼 수 있다**: 정책 버전이 서명에 들어 있으므로 3단계 도구로 본 BTC 판은 4단계 도구에서는 새 판이다(의도). 날짜가 바뀌면 경계가 하루 밀려 서명도 바뀐다(최종 구간 재사용 금지는 별도로 계속 적용된다).
- 검증 전용 환경변수 `QQUAN_CT_POLICY_VERSION=1`은 새 계약을 이전 정책으로 동결해, 이전 정책 계약의 거부를 실데이터로 확인하는 데 쓴다. 일반 사용에서는 설정하지 않는다.

### 대조군 모드 (`contrast_moves.controls`)

`controls: "time" | "vol_matched" | "losers"`, 기본 `time`.

| 모드 | 대조군 | 읽는 법 |
|---|---|---|
| `time` | 같은 시(하루 시작 후)·같은 달의 유효 순간, 사건당 3개(3단계와 **바이트 동일**, 골든 해시 테스트) | +k×비용 움직임은 고변동 구간에 몰려서, 값이 어느 쪽으로든 극단인 순간이 사건에 많다 → 양쪽 꼬리 lift가 같이 오르면(`two_tailed`) 방향이 아니라 변동성이다 |
| `vol_matched` | 위 + **같은 변동성 5분위**(결정 시점에 완성된 60분봉 ATR(14) ÷ 그 종가 = DSL `atr_pct(14, 60m)`, 5분위 경계 = 그 종목 학습 구간 유효 순간 전체), 사건당 3개를 비복원·시드 고정. 칸에 후보가 3개 미만이면 그 사건을 버리고 `droppedEvents`에 센다 | 변동성 국면을 맞췄으니 남는 lift는 변동성 효과가 아니다 |

- 결과에 `controlMode`, 대조군 수, 사건당 대조군, 버린 사건 수, 매칭 규칙 문장, 변동성 5분위 경계, **특징별 `shape`**가 붙는다. 모양 분류(코드 주석 `CT_SHAPE_RULE`): 양 끝 5분위 중 lift ≥ 1.25 이고 z ≥ 2 이면 "높음". 양 끝 모두 높음 `two_tailed`, 위쪽만 `monotone_up`, 아래쪽만 `monotone_down`, 그 밖 `flat`(분류는 읽기 보조이지 유의성 검정이 아니다).
- 트리(`tree: true`)는 선택한 대조군을 음성 클래스로 쓴다(사건 대표 순간 대 대조군 순간). 앞 2/3 → 뒤 1/3 규칙과 청산 퍼지는 그대로다. `time` 모드의 트리는 3단계와 같다(모든 유효 순간 표본).
- `contrastId`의 입력 요청에 모드가 들어가고, 다중 검정 장부의 서명에도 모드가 붙는다(`…|vol_matched`, `…|losers`; `time`은 3단계 서명 그대로라 이전 실행의 장부와 비교된다). 앞을 내다보는 구간이 `trainingToMs`를 넘는 순간은 대조군에서도 버린다(오염 테스트).
- 합성 시장 검증(`tests/ct-stage4-contrast.test.mjs`): 변동성만 다른 시장에서 `time` = `two_tailed`, `vol_matched`·`losers` = `flat`; 방향 신호(상승 직전 하락)를 심은 시장에서 `vol_matched`·`losers` = `monotone_down`.

읽는 법: 변동성을 맞춰도 "눌림 직후"(20일 위치·전일 종가·VWAP 아래)와 "수축 뒤 거래량 증가" 쪽 lift가 남는다. 그러나 같은 시각·같은 변동성의 **손절 먼저 순간**과 비교하면 어느 특징에서도 차이가 없다 — 사건 직전 모습은 방향 정보가 아니라 "손절에 닿지 않고 저점 근처에서 시작한다"는 라벨 구조와 같은 것이다. 1.2절의 "방향 정보 없음"이 이제 방향을 직접 묻는 모드로도 확인됐다. 이번 4단계 유료 연구 ETH도 `losers`로 19개 특징이 전부 `flat`이었다(아래).

### 이미 잰 것 (`alreadyMeasured`)

같은 소유자·시장·종목·연구 시작·학습 경계·**데이터 해시**의 이전 실행이 부른 `label_moves`(파라미터)와 `contrast_moves`(라벨, 특징, 모드)를 모아 요약 한 줄과 그 실행의 결론(그 측정을 근거로 든 기각 가설의 결과, 없으면 세션 `noEdgeReason`의 첫 문장)과 함께 설계 세션 안정 블록에 넣는다(`lib/ct-measured.ts`). 실행 시작 때 한 번 계산해 `measured_summary` 도구 캐시에 고정하므로 재개해도 같다. 학습 구간 측정만이라 수치를 보여도 되고 개발·최종 결과는 들어가지 않는다. 설계자가 같은 정의의 `label_moves`(·같은 모드·같은 특징의 `contrast_moves`)를 다시 부르면 결과는 그대로 주고 `previouslyMeasured: [{runId, conclusion}]`를 붙인다(계산이 무료라 막지 않는다).

장부 결정: **이 실행의 장부에는 센다**(설계자에게 보이는 검정 수), **누적 검정 수에는 중복 합산하지 않는다**. 4단계 연구의 누적 검정 수 = 이전 1분봉 실행들의 **서로 다른 장부 서명** 수(서명이 없는 오래된 실행은 기록된 개수 그대로)이고, 검토자에게 가는 `cumulativeHypothesisTests` = 이 값 + 이 실행의 서명 중 이전에 없던 것(`ctDistinctPriorTests`). 3단계 계약은 이전 합산 방식(실행별 개수의 합)을 유지한다. 예: ETH 연구 시작 때 플레이북의 누적 검정은 단순 합 203회가 아니라 서로 다른 서명 151회였다.

실데이터 확인: BTC 학습 데이터(3ab2ad6c의 데이터 해시)에서 새 실행이 받는 목록은 이전 3개 실행의 `k5 · m2 · 240봉(사건 952건)` 라벨과 각 실행의 결론("변동성 효과" 등)이다. ETH는 처음 보는 데이터라 목록이 비어 있다.

### 보정 기록 (`ct_calibration`)과 큰 블라인드 세트

**기록을 플레이북과 분리했다.** 플레이북 행은 "다음 실행이 피해야 할 메커니즘"이고 블라인드 결과는 도구 측정(세트 크기 n, 적중 k, p, 검정력)이라 필드와 읽는 법이 다르다. 그래서 별도 테이블 `ct_calibration`(시장·종목·실행 id·n·k·p·판정·검정력 70/75%·필요 적중 수·측정 기간·차트 형식 버전)을 쓰고 안정 블록에는 플레이북과 다른 절 `eyeCalibration`으로 넣는다. `grade_blind`는 서버가 직접 이 테이블에 쓴다(실행·세트마다 한 행, 멱등).

**판정(서버 계산):** `skill` p < 0.05 · `no_skill` p ≥ 0.05이고 n이 실제 70% 눈을 검정력 0.8 이상으로 잡을 만큼 큼 · `inconclusive` 그 밖(표본이 작아 판정 불가). `grade_blind` 결과에 판정, 이 크기에서 유의하려면 필요한 적중 수, 70%·75% 눈일 때 통과 확률, 읽는 문장이 함께 간다.

| 세트 크기 | p < 0.05에 필요한 적중 | 실제 70% 눈 통과 확률 | 75% |
|---:|---:|---:|---:|
| 8 | 7 | 0.26 | 0.37 |
| 16 | 12 | 0.45 | 0.63 |
| 24 | 17 | 0.56 (정확값 0.5647; 지시서 표의 0.57은 반올림 차이) | 0.77 |
| 32 | 22 | 0.64 | 0.85 |
| 44 | 28 | 0.86 | 0.97 |

한계: `no_skill`은 검정력 0.8에 n ≥ 44장이 필요한데 한 세트의 최대가 32장이라 **한 세트로는 `no_skill`이 나올 수 없다**. 같은 형식의 여러 세트를 합친 값(안정 블록의 `pooled`, 합산은 결정 시각을 숨긴 세트만)만 `no_skill`을 말할 수 있다. 작은 세트는 `skill` 아니면 `inconclusive`다.

**블라인드 세트(새 정책):** 16–32장(기본 24), 이벤트와 대조군 같은 수, 이미 일반 보기로 정답 그룹을 본 시각은 서버가 거부(`view_charts`), 다른 블라인드 세트에 쓴 시각도 거부. `label_moves`가 **예비 앵커**(이벤트 최대 16 + 대조군 16, 표시된 12+12와 겹치지 않음, 같은 대표 시각 규칙·시드)를 `blindReserve`로 더 발급한다. 일반 보기는 호출당 8장 이하. 세션 이미지 한도 32 → **48**(24장 블라인드 + 일반 16장), 블라인드 세트 2개, `grade_blind` 예측 수는 세트 크기(16–32)에 맞춘다.

**이미지 토큰·한도 재확인:** 공식 문서(platform.claude.com 비전 가이드)의 식은 이미지 한 장 = ⌈가로/28⌉ × ⌈세로/28⌉ 토큰이라 1,420 × 456 차트는 51 × 17 = **867토큰**이다(긴 변 한도 2,576px 이내라 축소되지 않음). ETH 실제 실행에서 24장 블라인드 결과가 들어간 요청의 캐시 쓰기 증가분이 22,194토큰으로 24 × 867 = 20,808 + 텍스트·직전 출력 약 1.4천과 맞는다(3단계의 "장당 약 900"은 텍스트가 섞인 값). 다음 턴은 같은 이미지를 바이트 그대로 싣고 106,343토큰을 캐시 읽기로 읽었다(쓰기 2,245). 비용 예약 가정(장당 1,100토큰)은 약 27% 보수적이라 유지한다. 요청당 한도: 이미지 100장(200k 컨텍스트 모델; 그 밖은 600장), **20장을 넘으면 모든 이미지가 한 변 2,000px 이하**여야 하고(우리는 1,420px) 본문 32MB — 세션 최대 48장은 약 4MB·4.2만 토큰이라 한도 안이고 해상도를 낮출 필요가 없었다.

**기존 행 이전(마이그레이션, 멱등):** `ctMigrateCalibration`이 플레이북 읽기(`backfillPlaybook`) 때 한 번 돌며 (1) 모든 실행의 채점된 블라인드 세트를 보정 기록으로 만들고 (2) 근거가 **블라인드 id뿐인** `…:rej:<세션>:<k>` 행을 플레이북에서 지운다. 판별은 `evidence`가 전부 그 실행의 `ct.blinds` 키인지 여부이고 텍스트 키워드는 쓰지 않았다(저장된 `bcf289ab`·`f8aeaf03`의 `rejectedHypotheses`를 먼저 확인했다: 눈 가설의 evidence가 각각 `["1c7d8df3abca"]`, `["331f02a4e49b"]`뿐이었다). `ctPlaybookRows`도 같은 규칙으로 이런 가설을 만들지 않아 소급 기록을 다시 돌려도 되살아나지 않는다. 실행 결과(로컬 DB): `bcf289ab:rej:0:4` → 보정 기록(n 8 · k 6 · p 0.145 · `inconclusive`), `f8aeaf03:rej:0:3` → (n 8 · k 4 · p 0.637 · `inconclusive`), 두 플레이북 행 삭제. 설계자가 새 정책에서 눈 가설을 `rejectedHypotheses`에 넣으면 서버가 제출 기록에서 `calibrationRefs`로 옮긴다. 근거를 블라인드 id와 다른 id로 섞은 가설은 거래 가설로 남는다(한계). 이전 정책 계약의 안정 블록은 `ct.playbook`(실행 시작 때 고정)에서만 만들어져 이 변화에 영향받지 않는다(테스트로 확인).

**4단계 실행에서 발견해 고친 것(차트 식별 누출):** 설계자는 블라인드 세트의 시각을 **스스로 고르고**, 차트 머리글은 "decision at 14:37 UTC"를 인쇄하고 시계 눈금도 있어 차트를 자기 목록의 시각과 맞출 수 있다. ETH 실행의 생각 요약에서 설계자가 이를 스스로 짚었다("timestamps tied to the chart list, which risks contaminating a blind read"). 그 세트의 정확도는 45.8%(11/24)라 이득을 보지 않았지만 보정 기록으로서는 오염 가능성이 있다. 그래서 새 정책의 블라인드 차트는 **결정 시각과 시계 눈금을 숨기고** 결정 전 상대 시간(−15m, −30m…)만 보인다(`ct-chart-2-blind`). 나머지 누출은 5분봉 패널의 길이(하루 중 얼마나 지났는지)뿐인데 대조군은 같은 시에서 뽑으므로 그룹을 가르지 못한다. 이 실행의 세트는 `ct-chart-1`(시각 표시)로 기록되어 목록에는 나오지만 `pooled`에는 합산하지 않는다.

### 설계자의 생각 표시

원인 확인(최소 요청 2회, 약 $0.02): Opus 5.5에 `thinking: {type: "adaptive"}`만 주면 `thinking_delta` 한 번에 빈 문자열이고 서명만 오며(최종 메시지의 thinking 0자), `display: "summarized"`를 명시하면 19개 delta에 228자가 온다. 같은 프롬프트에서 출력 토큰은 469 대 455(추론 토큰 180 대 175)로 청구는 같다. 즉 원인은 (a) 기본 `display`가 생각을 생략하는 것이고 (b) `streamClaude`의 누적은 정상(SDK가 `finalMessage`에 누적)이다. 고침: 새 정책 계약의 설계 세션 요청에만 `thinking: {type: "adaptive", display: "summarized"}`를 넣는다(`DesignerTurnRequest.thinkingDisplay`). 이전 정책 요청은 키가 없어 바이트 동일(테스트로 고정). assistant `content`는 받은 그대로 저장하고 그대로 붙인다(preserved thinking 유지). **캐시·청구 영향 없음**: ETH 실행의 캐시 읽기 비중 84.9%(3ab2ad6c의 82.5%와 같은 수준), 턴 2부터 캐시가 이어졌다.

표시: 진행 화면 설계 세션 섹션이 턴마다 "설계자 생각(요약)"을 접이식으로 보인다(`GET ?thinking=1&id=…&session=…`가 `ct_session_messages`에서 읽음, 새 저장소 없음; 데이터는 `lib/ct-activity.ts`의 `sessionThinking`). 빈 생각은 이전 계약이면 "기록 없음(이 계약은 생각 요약을 받지 않음)", 새 계약이면 "이 턴은 생각 요약이 없습니다(모델이 생각 없이 응답함)". **위험·증거 검토자 입력에는 넣지 않는다**: 길이가 크고(요약만도 턴당 수백–수천 자) 검토자의 독립성을 해친다(설계자의 자기 정당화를 읽게 됨). 검토자는 측정 기록·장부·보정 기록·자기 반박만 본다.

| 시작 때 플레이북 | 40개 · 누적 검정 160(합) | 40개 · 누적 검정 151(서로 다른 서명) · 눈 항목 없음 · 보정 기록 1건 |
| 서버 계산 / 활성 시간 | 11.6초 / 209초 | 15.4초 / 286초 |

**설계자 생각 요약은 실제로 저장되고 화면에 보인다**([스크린샷](research/stage4-screens/02-thinking-summary-per-turn.jpg), `ct_session_messages`의 assistant `thinking` 10개 모두 비어 있지 않음, 300–1,500자). 차트를 건너뛰거나 본 이유, 멈춘 이유가 생각에 그대로 나타난다:

- 턴 4에서 차트를 **건너뛴** 이유: "I'll skip chart review since the numbers already suggest no exploitable direction."
- 턴 8에서 차트를 **본** 이유: "With no viable candidates left, I'll spend the remaining budget on a blind calibration set instead—running a 24-chart blind test on the k=8 label using the blindReserve anchors, split 12 events and 12 controls, since I haven't viewed any charts yet…" (남은 예산으로 보정을 하기로 한 것 — 눈을 강제로 쓰게 하지 않았다)
- 턴 9에서 채점 직전 식별 누출을 스스로 짚음(위 「차트 식별 누출」).
- 멈춘 이유(턴 10): "Given these overlaps with already-rejected ideas and the risk of adding redundant tests to the ledger without new information, I'll submit zero candidates."

해석과 한계: 이 한 번의 실행은 같은 데이터의 3단계 BTC 실행과 독립적인 증거가 아니고(다른 종목이지만 같은 플레이북·같은 설계자), 비용 $0.97로 "ETH에서 비용 후 우위 없음"에 도달했다. 설계자가 새 도구를 실제로 썼다는 점(losers 대조군, 24장 블라인드 + 예비 앵커)이 확인된 것이 이번 실행의 의미다. 블라인드 세트는 설계자가 스스로 고른 시점에, 거래 판단과 무관하게 마지막에 한 번 썼다. 후보가 나오지 않아 검토자 입력의 `repeatedBoard`·`eyeCalibrationBefore`와 개발·최종 단계는 실제 실행으로는 검증되지 않았고 합성 테스트(`tests/ct-stage4-*.test.mjs`)로 검증했다. 한 연구의 결과를 일반 무수익성의 증거로 쓰지 않는다.

### 천장 측정 확장 (4단계 2부, 모델 비용 $0)

판정 기준을 측정 전에 [보고서](research/ct-ceiling-2026-10-14-field.md) 맨 앞에 등록·커밋하고 140개 조합(종목 BTC·ETH·SOL × 기간 1·3·5년 × 보유 4 × 비용 B-1/B-2a/B-2b × 피처 F1/F2/F3, Binance·Upbit 가격 경로)을 같은 방법으로 쟀다. 결론: **후보 없음** — 기준 5개를 모두 만족한 조합 0개(비용 1배 일평균 양수 2개는 선택 거래가 1건씩, 양수 폴드 최대 1/4). 파생·괴리 피처를 더해도, Upbit의 낮은 수수료를 써도, ETH·SOL로 넓혀도, 5년으로 늘려도, 국면(일봉 SMA200 위·아래)을 쪼개도 바뀌지 않았다. 후보가 없어 DSL·설계 도구 확장은 하지 않았다. 세부는 보고서.


## 연구 교훈 (2026-10-15, 설계 세션 5단계)

`docs/prompts/ct-stage5-lessons.md`의 작업 결과다. 바꾼 이유(지시서 1절, 로컬 DB의 실제 기록):

- 플레이북은 시도한 아이디어마다 한 행을 쌓지만 설계자는 시작 때 **최근 40개 원자료**를 직접 읽고 추론한다. "계열 전체가 왜 죽었나"라는 상위 결론은 저장되지 않고, 40개를 넘기면 오래된 실패는 시야에서 사라진다(누적 검정 수만 전체를 센다).
- 기각된 것만 있고 **어디가 아직 안 건드려졌는지**는 어디에도 없다. 4단계 ETH 실행은 "이미 기각된 아이디어와 겹친다"며 후보 0개로 멈췄는데, 겹치지 않는 곳으로 가는 길은 기억에 없었다.
- 설계자가 기억을 읽는지는 시스템 지시의 권고로만 작동하고, 서버는 후보가 죽은 계열의 변형인지 확인하지 않는다.

새 기능은 모두 **`policy.traderTools = 3`인 새 계약에서만** 켜진다(`toolsVersion 3`). `traderTools ≤ 2` 계약의 시스템 지시(`CT_DESIGNER_SYSTEM_STAGE4`)·도구 정의(`CT_SESSION_TOOLS_STAGE4`)·안정 블록·요청 옵션은 바이트 단위로 그대로이고 SHA-256을 테스트가 고정한다(안정 블록은 개정 전 코드가 같은 입력에서 만든 값과 같은 해시). 게이트(일평균 > 0, 스트레스 포함)·롱 전용·당일 청산·1분봉 백테스트·시간순 60/20/20·최종 구간 1회 평가는 바꾸지 않았다. **교훈에는 수치가 아예 없다**(증류 모델이 어떤 수익률·p값·거래 수도 보지 못하고 출력도 측정값 패턴이 있으면 거부한다). 모델 가중치·프롬프트를 자동으로 고치는 학습은 없다.

**판 서명과의 관계.** 판 서명(`lib/ct-board.ts`)은 그대로이지만 설계 도구 정책 버전(`tools`)이 서명에 들어 있어서, 4단계 정책으로 돌린 판은 5단계 정책에서는 새 판이다(의도: 도구가 바뀌면 같은 데이터도 한 번 다시 볼 수 있다). 5단계 효과를 보려고 이전에 연구한 판을 다시 돌려도 409가 나지 않는다. 같은 5단계 판을 세 번 이상 돌리는 것은 그대로 막힌다.

### 계열 (`lib/ct-families.ts`)

교훈과 커버리지를 합산하려면 아이디어를 같은 기준으로 묶어야 한다. 고정 열거형 `CT_FAMILIES`: `mean_reversion`(급락·과매도 반등) · `breakout`(범위·고점·저점 돌파) · `trend_following`(모멘텀 추종·추세 속 눌림) · `volatility_regime`(변동성 수축·확대·국면) · `time_seasonality`(시간대·요일) · `liquidation_cascade` · `levels_gaps`(VWAP·전일 고저·시가 범위·갭) · `multi_timeframe_context`(상위 시간대 조건) · `holding_overnight`(전일 → 다음 날 보유) · `other`. **값을 추가하는 것은 허용하되 기존 값의 의미는 바꾸지 않는다**(저장된 교훈이 그 이름으로 남는다); 바꿀 때는 여기에 이유를 적는다.

분류는 **모델 호출 없는 결정적 규칙**이고 어디에도 저장하지 않는다(읽을 때 계산하므로 지난 기록에도 적용된다; `ct_playbook`에 컬럼을 더하지 않았다).

1. 아이디어 텍스트의 **머리**(가설 문장 또는 후보 이름, ` — ` 앞)에 대한 키워드 규칙을 순서대로 적용한다. 꼬리(설계자가 쓴 이유)는 다른 계열의 원인을 말하는 일이 잦아 쓰지 않는다. 순서가 정의의 일부다: 다음 날 보유 → "직전 특징으로 미리 고를 수 있다"류의 메타 가설(`other`) → 청산 → 기준 가격·갭 → 시간대 → 변동성 수축·국면 → 돌파 → 추세 → 반등·평균회귀 → 상위 시간대.
2. 규칙에 걸리지 않으면 조건 구조(feature 목록)로 정한다: 레벨 피처 → `levels_gaps`, ATR·수축비 → `volatility_regime`, 고점 거리·스윙 고점 → `breakout`, 저점 거리·스윙 저점 → `mean_reversion`, 큰 주기 + 작은 주기가 함께 → `multi_timeframe_context`, 그 밖은 `other`.
3. 장부 서명은 텍스트가 없고 방향(gte/lte)이 있으므로 **구조 분류**(`ctStructuralFamily`: 피처와 방향만)를 쓴다. 제출된 후보는 이 구조 분류와 위 1·2(후보 이름·메커니즘 텍스트와 구조, 플레이북 행이 될 바로 그 문자열)를 **둘 다** 계산하고, 둘 중 하나라도 `dead` 계열이면 확인 대상이다(이름을 바꿔 규칙을 피할 수 없다).

실제 기록(로컬 DB의 1분봉 항목 125개)에서 `other`는 5.6%(코인 7개/88, 주식 0/37)이고 테스트가 고정 픽스처로 30% 이하를 지킨다. 규칙을 만든 뒤 125개를 눈으로 훑어 나온 어긋남(`상위 시간대`가 시간대 규칙에 걸림, `눌리면`·`드리프트` 누락)을 고쳤다. 남은 한계: 한 문장이 두 계열에 걸치면 순서가 먼저인 쪽이 이긴다(예: "VWAP 되돌림 근사" 추세 눌림이 `levels_gaps`).

### 커버리지 지도 (`ctCoverage`, 모델 호출 없음)

"아직 안 건드린 영역"은 모델이 아니라 장부에서 센다. 입력은 같은 시장·소유자의 1분봉(`comparable`) 플레이북 **전체**(40개 제한 없음, 일봉 시드 제외), 이전 실행들의 장부 서명(`ct.tests.signatures`, 서로 다른 서명만), 이전 후보·사전 검사의 실제 `spec`이다. 출력(`CTCoverage`)은 개수만이다(성과 수치 없음; 테스트가 모든 숫자가 0 이상의 정수임을 확인한다).

- 계열별: 아이디어 수(서로 다른 메커니즘·구조 쌍) · **서로 다른 검정 수**(조건 서명을 구조 분류로 계열에 배정; 반복 실행이 같은 서명을 다시 센 것은 한 번) · 최고 등급 · 마지막 실행.
- 어휘별 사용 여부: 피처 × 주기 79칸(기본 피처 10 × 주기 6 + 레벨 7(1분봉만) + 변동성 2 × 6) 중 어떤 검정·후보·플레이북 구조에도 한 번도 안 쓰인 칸(`untouched`, 설계자에게는 상위 30개와 나머지 개수), ATR 단위를 못 써 본 피처, 진입 시간 창 사용 여부, 안 쓴 관리형 청산 요소(`stop.*`·`target.*`·`breakeven`·`trail.*`·`timeStop`·`atrBasis`).
- 계열 × 청산 구조(고정 손절·목표 / 관리형)의 빈 칸: 후보로 간 항목만 센다.

### 교훈 증류 (`ctDistillRun`)

연구가 `done`이 되고 `recordCTPlaybook`이 끝난 직후 **한 번**, 유료 모델 호출 1회로 이 실행의 아이디어를 계열 단위 교훈으로 증류한다. `ct.lessonsRecorded`(`{at, lessons, rejected?, downgraded?}` · `{skipped: "reserve" | "no_ideas"}` · `{failed}`)가 표시이고 한 번만 쓰므로 재개해도 다시 사지 않는다(같은 응답은 `paidCall`의 완료 응답 재사용 키로도 재사용된다: 프롬프트는 시각 같은 변동 요소 없이 결정적이다). **실패해도 실행 결과는 그대로**이고 `lessons_record` 도구 기록에 failed로 남는다.

- **입력(누출 없이)**: 이 실행의 플레이북 항목 · 기각 가설 · 학습 게이트·개발 탈락 후보의 구조와 사유, `noEdgeReason`, 눈의 판정(`pooled.verdict`만), 같은 시장의 현재 교훈. 항목마다 `ctPlaybookView`를 "모든 구간과 겹침"으로 불러 `detail`을 비우고 사유(와 `noEdgeReason`)의 숫자를 `ctStripNumbers`로 `#`로 가린다. 설계자의 생각과 위험·증거 검토자의 출력은 넣지 않는다(자기 정당화의 재생산 방지; 4단계 검토자 독립성 규칙과 같다). 프롬프트에는 계열별 사실표 `familyFacts`(아이디어 수, 쓴 피처 칸, 후보 수, 그중 관리형 청산·시간 창·ATR 단위를 쓴 수 — 개수와 이름만)와 각 `cause` 값의 정의가 들어 있어 `nextToTry`가 "관리형 청산을 쓴 후보는 아직 없다"처럼 사실표가 보여 주는 빈 곳에만 근거하게 한다(처음 소급 증류는 이 표 없이 돌아서 `nextToTry`가 전부 비었고 `cause`를 잘못 쓴 교훈도 있었다). 입력은 `lessonMaxInputChars`(60,000자)를 넘지 않는다: 그 계열의 이전 항목을 오래된 것부터 줄이고, 그래도 크면 문장을 자른다.
- **출력**(zod 서버 검증; `strict` 도구 문법은 쓰지 않는다 — 2026-10-13에 400 "compiled grammar is too large"): 계열마다 `family` · `verdict`(`dead|weak|unresolved`) · `cause`(`no_edge_after_cost|sample_too_small|regime_concentrated|fails_stress|holdout_flip|overfit_by_search|eye_no_skill|duplicate_of_dead|untestable_here`) · `lesson`(한국어 한 문장 ≤ 200자) · `nextToTry`(한 문장 ≤ 160자 또는 null) · `evidence`(근거 항목의 **ref** — 프롬프트의 항목마다 `i1`, `i2`…를 붙이고 서버가 플레이북 id로 되돌린다. 처음에는 긴 id를 그대로 베끼게 했는데 모델이 id를 틀려 코인 교훈 3개가 버려졌다).
- **서버 검증**(`ctValidateLessons`): ① 이 실행의 **새 항목이 없는 계열**의 교훈은 무시한다(오래된 교훈을 새 증거 없이 지우거나 약하게 바꿀 수 없다; 새 증거가 없는 계열은 그대로) ② 근거(ref 또는 id)가 `ct_playbook`의 실제 행이 아니면 교훈을 버린다 ③ 빈 문장·길이 초과·**측정값 패턴**(`%`, 소수, 부호 있는 수, 건·배·회 등 단위가 붙은 수, `p =`, `×N`)이 있는 문장은 거부한다 — "4시간" 같은 규칙의 정수는 허용한다 ④ 문장의 "가족"은 "계열"로 고친다(모델이 family를 직역한다). ⑤ `dead`는 그 계열의 아이디어가 **3개 이상**이고 최고 등급이 `development_failed` 이하이며 **서로 다른 조건 구조가 2개 이상**일 때만 허용하고, 미달이면 거부하지 않고 `weak`로 낮춘다(`downgraded`; 구조가 같은 변형은 한 메커니즘으로 본다 — "서로 다른 메커니즘"의 서버 쪽 정의) ⑥ 한 계열에 교훈 하나, 근거 목록은 현재 교훈의 근거와의 합집합.
- **저장** `ct_playbook_lessons`(`id = <실행>:<시장>:<계열>`, append-only: 같은 실행을 다시 증류하면 같은 id를 덮어쓰고 이전 실행의 행은 지우지 않으며 읽을 때 (시장, 계열)별 최신 행이 현재 교훈).
- **모델**: `ctLessons` = OpenAI `gpt-6-luna`(effort low, 출력 상한 8,000토큰) — 원리 추출(`ctAnalyst`)과 같은 값싼 급이다. 요약·정리만 하고 판정권이 없으며 설계자(Anthropic)와 다른 회사라 독립 검토 규칙에도 걸리지 않는다. 입력 $0.1 · 출력 $0.5 / 백만 토큰(`lib/strategy-generation-models.ts`의 가격표). 실제 기록으로 잰 소급 증류 입력은 코인 88개 전체 35,820자(실측 입력 14,659토큰·출력 1,323토큰, **$0.0021**), 주식 37개 18,471자(7,372/1,100토큰, **$0.0013**); 실행 끝의 일반 호출은 새 항목만 넣어 훨씬 작다(아래 5.2: 입력 4,929토큰·출력 167토큰, **$0.0006**).
- **전용 예비 예산** `policy.lessonReserveUsd = $0.05`(지시서 제안 $0.25는 위 단가로 재계산했다: 입력 상한과 출력 상한을 모두 채운 최악의 예약값이 $0.017이라 3배 여유). 새 계약은 시작 때부터 설계자와 두 검토자의 천장에서 이 금액을 빼고(`researchCeilingUsd`), 증류 호출만 예산 전체까지 쓸 수 있다. 예산이 소진돼도 증류는 이 몫으로 돌고, 예산이 정말 모자라면 호출 없이 `{skipped: "reserve"}`이다. `reserveFraction` 35% 검토 예비와는 별개다. 설계 세션 시작·마지막 턴 판정(`headroom`)에도 이 금액이 빠진다.

### 설계 세션: 안정 블록과 지시문

3 이상 계약의 안정 블록(캐시 대상)은 `playbook` 다음에 **`lessons`**(계열별 현재 교훈: `family`·`verdict`·`cause`·`lesson`·`nextToTry`·`evidence`(플레이북 id)·`omittedEvidence`(설계자의 40개 목록 밖 근거 수)·`lastRun`; `deadFamilies`)와 **`coverage`**를 싣는다. 실행 시작 때 한 번 `lessons_summary` 도구 캐시로 고정되므로 재개해도 같다. `playbook`의 `omittedOlderEntries`는 그대로 남는다. 기존 `calibration`·`alreadyMeasured`·누적 검정 수도 그대로다.

시스템 지시(`CT_DESIGNER_SYSTEM`, 5단계)는 4단계 본문에 1단계 읽기 지시(lessons·coverage)와 균형 문단을 더했다: 교훈은 "이 판에서 이 계열이 죽은 이유"를 알려 주는 기억이지 "이 영역을 채워라"는 목표나 성과의 증거가 아니다; 빈 영역은 가능성일 뿐 증거가 아니다; `dead` 계열의 후보는 교훈의 `cause`가 이번에 왜 적용되지 않는지 `lessonChecks`에 적어야 한다; `nextToTry`는 제안이고 따라가면 그 검정도 장부에 들어가 다음 양성을 우연히 만들기 쉽게 한다; 이 실행의 장부와 누적 검정 수를 고려해 "우위 없음"은 여전히 정상 결과이고, 새 정보 없는 검정도 **빈 칸을 채우기 위한 검정도** 더하지 말라.

### `submit_candidates`와 서버 확인 (`lessonChecks`)

3 이상 계약의 도구 정의에만 새 필드가 있다(`ctSubmissionSchemaStage5`; 이전 계약의 도구 정의 바이트는 캐시 키라 건드리지 않았다. `assertCTTool`의 입력 검증 스키마는 4단계 스키마의 상위집합이라 4단계 제출도 그대로 통과한다).

- `lessonChecks[]`: 후보마다 `{candidateIndex, family, lessonId | null, differsBecause}`. 서버가 후보의 계열을 위 3번대로 **스스로 계산**하고, 그 계열에 `dead` 교훈이 있는데 `differsBecause`가 없거나 20자 미만이면 `is_error` tool_result로 같은 세션에서 고치게 한다(기존 zod·명세 검증 실패와 같은 방식; 거부된 제출의 중복 카운트는 되돌린다). 모델이 선언한 `family`가 서버 값과 다르면 서버 값을 쓰고 불일치(`declaredFamily`)를 기록한다. 통과한 값은 후보(`lessonCheck`)에 저장되어 검토자에게 간다. 후보 0개로 끝나는 제출과 살아 있는 계열은 확인하지 않는다(`noEdgeReason`의 교훈 인용도 강요하지 않는다: 무의미한 인용만 생긴다).
- `rejectedHypotheses[].family`(선택): 없으면 서버가 플레이북 행이 될 바로 그 텍스트·구조로 채운다.

### 검토자

위험·증거 검토자의 `research`에 `lessons`(후보 계열들 `candidateFamilies`, 그 교훈 `forCandidate`, 같은 시장의 `deadFamilies`)와 `lessonChecks`가 3 이상 계약에만 실리고, 검토 지시에 "이 규칙이 `dead`로 판정된 계열의 변형인가, 후보가 적은 차이가 실제로 다른 메커니즘인가, 빈 커버리지 칸은 승인 이유가 아니다"가 붙는다. 이전 계약의 프롬프트는 글자 하나도 바뀌지 않는다(테스트). 설계자의 생각 요약은 여전히 넣지 않는다.

### 화면

CT 화면의 「플레이북」 섹션에 「항목 / 교훈」 탭이 생겼다(읽기 전용, 유료 동작 없음). 교훈 탭은 계열별 카드(판정 · 원인 · 한 문장 교훈 · 아직 안 본 변형(제안) · 근거 항목 링크(누르면 항목 탭으로 가서 그 항목으로 스크롤) · 갱신일·실행)와 「아직 안 건드린 영역」(계열별 개수, 안 쓰인 피처 칸, ATR 단위, 시간 창, 관리형 청산 요소, 계열 × 청산 구조의 빈 칸)을 보인다; 교훈이 없으면 빈 상태 안내. 진행 화면의 설계 세션 섹션에는 "시작 때 받은 교훈 N개 · dead 계열 M개 · 교훈 증류 기록됨 / 건너뜀(예비 부족) / 실패"가 한 줄로 나온다. 증류 단계는 에이전트 목록에 「교훈 증류」로 보인다. 화면 모델(`lib/ct-lessons-view.ts`)은 순수 함수라 테스트가 읽는 것이 그대로 그려진다.

### 소급 증류 (`scripts/research/ct-lessons-backfill.ts`)

이전 실행들의 교훈이 없으면 5단계 첫 연구의 효과를 볼 수 없다. 기본은 **`--dry-run`**: DB를 읽기 전용으로 열고 모델을 호출하지 않으며, 시장별로 계열별 항목 수·서로 다른 구조 수·최고 등급, `other` 비율, 입력 크기·예상 비용, 서버 검증이 `dead`를 허용할 계열을 출력한다. `--run`을 줘야 호출하고, `--max-usd`(기본 $0.50)를 넘으면 중단하며, 결과는 `source: backfill`(`run_id = backfill:<시장>:<날짜>`)로 저장하고 모든 교훈과 근거 대조표를 출력한다. **소유자가 확인하고 `--run`을 줄 때만 돈다.**

## 봉 주기 자유 선택 (2026-10-16, `traderTools = 4`)

소유자 결정: 수익을 내는 단타 고수가 어떤 봉을 보는지 모르는데, 봉 주기를 미리 하나로 정하고 그 안에서만 전략을 찾게 하면 "고수의 뇌"를 찾는 범위를 사람이 좁히는 셈이다. 그래서 봉 주기는 계약이나 화면 설정이 아니라 **설계자의 선택**이다. 처음에는 화면에 1/5/15/60분 선택지를 붙였다가 이 이유로 되돌렸다(연구 요청 `minutes`는 다시 1만 받는다). 시작 화면 요약은 "봉 주기 에이전트 선택"으로 바뀌었다.

- **계약**: 데이터는 그대로 1분봉이다(`contract.minutes = 1`). 새 계약은 `policy.traderTools = 4`(`ctSessionPolicy(...).freeBars`)로 동결된다. `traderTools ≤ 3` 계약의 지시문(`CT_DESIGNER_SYSTEM_STAGE5`)과 도구 정의(`CT_SESSION_TOOLS_STAGE5`)는 변경 전(커밋 `fa974b5`)과 SHA-256이 같고 테스트가 고정한다. `QQUAN_CT_POLICY_VERSION=3`이면 5단계 정책으로 동결한다.
- **규칙의 봉**: 후보마다 `spec.minutes`를 1/5/15/60(주식 1/5/15)에서 고른다. 한 제출 안의 후보들이 서로 다른 봉을 써도 된다(`ctBarChoices`, `ctBarAllowed`, `validateCTSpec`). 주식 60분봉은 시계 격자가 09:30 개장과 맞지 않아 거부한다. 5/15/60분 데이터로 동결된 이전 계약은 다른 봉을 만들 수 없다.
- **봉 만들기 (`ctBarsAt`)**: 시계 격자에서 연속된 **완전한 1분**만 묶는다. 1분이 하나라도 빠진 봉은 만들지 않고(합성 없음), 로컬 저장소의 `minutes: N` 집계와 같은 규칙이다. 결과는 입력 배열마다 캐시한다(1년 BTC → 15분봉 약 11ms). `replayCT`가 규칙 봉으로 직접 만들어 쓰므로 학습 선별(`screen_rule`)·개발·최종·스트레스(비용 2배·1봉 지연·손절 ±10%)가 모두 같은 함수를 지난다. 모의·실전 엔진(`ct-trading-engine.ts`)도 1분 피드를 규칙 봉으로 바꿔 진입·청산을 판단한다. 같은 규칙을 그 봉의 데이터로 돌린 결과와 `deepEqual`이다(테스트).
- **봉 단위 산수**: 모든 봉 수(lookback·offset·maxGapBars·cooldownBars·maxHoldBars·timeStop.bars·조회 지평)는 규칙 봉 기준이다. timeframe 1/3/12는 그 봉의 1/3/12배이고, 60/240/1440은 1시간·4시간·하루 그대로다. 진입은 다음 봉 시가, 손절·목표를 같은 봉에서 모두 건드리면 손절이다. **당일 마지막 거래 봉은 하루 끝 한 봉 전에 닫히는 봉**이다(`ctDayClosing`: 1분은 23:59, 15분은 23:45, 60분은 23:00. 주식은 정규장 종료 한 봉 전). `entryWindows`·`noEntryBeforeDayEndMinutes`는 분 단위 그대로다. `opening_range_position.lookback`은 분 단위이고 봉의 배수여야 한다. `ct-pattern-1` 주식 패키지는 이전의 1분 규칙을 유지한다.
- **엔진에서 일반화한 곳**(1분봉 결과는 비트 단위로 같다): 상위 시간대 봉의 완성 판정(기초 봉이 구간을 빈틈없이 덮으면 완성), 시가 범위(분 → 봉 수), 당일 마지막 봉(`dayLastIndex`), 진단의 직전 60봉 범위, 차트 패널(5/15/60분 데이터에서도 가운데·오른쪽 패널을 그림). 설계 도구 차트는 계속 1분 데이터로 1시간·5분·1분 패널을 한 장에 보여 준다.
- **측정 도구**: `label_moves`·`query_conditional_returns`·`read_bars`는 `barMinutes`를 받는다(새 도구 정의 `CT_SESSION_TOOLS`. 스키마는 `ctLabelMovesSchemaBars`·`ctQuerySchemaBars`·`ctReadBarsSchemaBars`). `contrast_moves`는 라벨의 봉을, `screen_rule`·`diagnose_trades`는 규칙의 봉을 따른다. 서버는 허용되지 않은 봉(예: 3분, 주식 60분)을 오류로 돌려준다. `cost_hurdle` 표는 1분봉 기준이고(지평 = 분) 지시문이 그렇게 말한다. 조회 기록과 요약에는 봉이 남는다(`[15분봉] …`).
- **다중 검정 장부**: 같은 구조라도 다른 봉이면 다른 검정이다. 조건 서명은 `b15:` 접두사, 라벨은 `|b15`, contrast는 라벨 꼬리 `b15`, 진단은 규칙 서명을 그대로 쓴다. 1분 서명은 변경 전과 같고, 계열 분류 파서는 접두사를 무시하므로 같은 피처로 읽는다. `ctLabelKey`(이전 실행에서 이미 잰 것)도 봉을 포함한다.
- **플레이북**: 후보 행(학습 탈락·개발·최종)은 자기 봉으로(`15m`), 기각 가설은 근거 조회의 봉으로 기록한다. 실행 행(`ct_playbook_runs`)은 데이터 봉(`1m`)이다. 누적 검정 수와 교훈·커버리지 입력은 **일봉 시드를 뺀 모든 분봉 기록의 합**이다(`timeframe <> 'daily'`. 같은 시장 역사를 캔 검정이므로). 기존 기록은 모두 `1m`이라 숫자가 바뀌지 않는다. 화면의 주기 필터에 5/15/60분이 생겼다.
- **지시문**: 새 계약에는 "봉 고르기" 단락이 붙는다. 고수가 어떤 차트를 보는지 아무도 알려 주지 않았다는 점, 같은 아이디어를 여러 봉에서 본 뒤 정할 것, 봉도 가설의 일부이니 메커니즘에 맞는 이유를 댈 것, 비용은 봉과 무관하게 왕복 고정이라 굵은 봉은 큰 움직임을 노리는 대신 거래가 적고 청산이 거칠어진다는 점, 봉을 바꿀 때마다 장부에 검정이 늘어나니 이기는 봉을 찾으려고 훑지 말 것. 계약 보기에 `barChoices`가 들어간다.
- **함께 고친 것(새 계약만)**: 1봉 지연 스트레스에서 지연된 진입이 당일 마지막 봉(마감 봉 다음)에 열리면 그날 강제 청산될 수 없어 자정을 넘을 수 있었다. 1분봉에서는 23:58 신호에서만 생겨 드물었지만 60분봉 실데이터에서는 개발 구간 2건이 자정을 넘었다. 이제 그런 진입은 받지 않고 `blocked.day_end`로 센다. 고정된 1분봉 회귀 결과가 바뀌므로 이전 계약에는 적용하지 않는다.
- **검증**: CT 테스트 224개 통과(`tests/ct-bar-minutes.test.mjs` 12개. 실제 설계 세션 1개 — 5분봉 라벨 → contrast → 조회 → read_bars → 5분봉 규칙 선별·진단 → 3분봉 요청 거부 → 제출, 장부 서명 확인). 실데이터(BTCUSDT 1년 1분봉 525,600봉, 무료 계약 보기)로 1/15/60분 각각 조회·학습·개발·비용 2배·1봉 지연 리플레이, 라벨, contrast 3모드, 차트, read_bars, 진단을 모두 돌렸다. 진입은 전부 봉 격자 위였고, 자정을 넘는 거래는 수정 후 0건이었다. 15분봉 리플레이는 85ms(1분봉 1.9초). 예시 규칙의 성과는 모두 음수였다(검증용 규칙일 뿐 탐색 아님).
- **한계**: 코인 1/3/12배 조건의 이력 한도 1,500봉은 규칙 봉 기준이다. Binance 연구는 지금도 실행 경로가 없어서 굵은 봉의 실전 워밍업은 확인하지 않았다. 주식 실행은 당일 세션 안의 봉만 쓰므로 Toss 당일 1분봉으로 충분하다. 유료 설계 세션은 이 변경 후 돌리지 않았다.

## 사용 흐름

1. CT에서 시장을 선택하고 **전략 생성**을 누른다. 기본 연구 비용 상한은 $8다.
2. 연구 중에는 화면 상단에 고정되는 상태바(단계 n/11, 경과, 후보, 백테스트, 비용 미터, 러너, 일시정지/재개/취소)와 **지금 하는 일** 패널, 단계 스테퍼, 최신 후보 카드, 활동 피드로 진행을 추적한다. 지금 하는 일 패널은 현재 작업 주체(모델 호출이면 역할·모델·설계 세션·턴·경과·실시간 입력(캐시 읽기 포함)/출력 토큰과 출력 한도·호출 비용, 서버 도구면 어떤 백테스트/조회/원문 읽기인지, 일시적 오류면 원인과 재시도까지 남은 시간)와 연구에 참여하는 6개 에이전트(서버 엔진, 총괄, 자료 분석, 연구·설계, 독립 위험 검토, 독립 최종 검토)의 상태·호출 수·비용을 보여 준다. 옛 실행의 역할명(`designer` 등)도 같은 에이전트로 표시한다. 설계 세션 섹션은 세션별 턴·도구·조회 목록, 기각 가설, 학습 게이트 탈락 후보를 보여 준다. 새 기록이 없으면(모델 호출 5분, 그 외 45초, 재시도 예정 시각 + 45초) 멈춤으로 표시한다. 활동 피드는 도구 호출과 모델 호출을 한 시간순으로 보여 준다. 실시간 토큰은 이 탭이 진행하면 `advance` NDJSON 스트림의 `usage`에서, 러너가 진행하면 약 2초마다 저장되는 `strategy_generation_meters`(`GET`의 `liveMeter`)에서 온다. 연구가 실행 중이면 2초, 아니면 5초마다 폴링하고 백그라운드 탭에서는 멈춘다. 판정 로직은 `lib/ct-activity.ts`(테스트 `tests/ct-activity.test.mjs`)에 있다. 가설 설계, 실제 실험과 수정 이력을 확인하고 도구 결과는 개별 다운로드할 수 있다.
   생성 작업은 계정 전체에서 동시에 1개만 `running`이다(`idx_generation_active`). 다른 브라우저 세션·전략 탭·CT 코인/주식에서 시작한 작업이 슬롯을 잡고 있으면 CT·전략 화면이 시작 버튼 위에 그 작업(종류·단계·시작/갱신 시각·비용)과 **취소 버튼**을 표시한다(`GET`의 `blocking`, `POST action: cancel_blocking`). 소유자 쿠키는 http 로컬 주소에서는 `Secure` 없이 발급한다. 막고 있는 작업이 2분 넘게 갱신되지 않고 러너도 꺼져 있으면 멈춤 경고와 연구 러너 실행 명령을 함께 보여 준다. 소유자는 `QQUAN_OWNER_ID`가 설정되면 모든 브라우저에서 같은 값이다(로컬 `.dev.vars` 기본). 설정이 없을 때만 브라우저 쿠키가 소유자이며, 이때 다른 브라우저 세션에서 시작한 작업의 세부 진행은 노출하지 않는다.
3. 독립 검토와 동결된 최종 평가를 모두 통과한 경우에만 **전략 등록**이 가능하다. 통과 후보가 없으면 정상적으로 종료하며 등록 버튼이 생기지 않는다.
4. 등록한 버전으로 모의 대시보드를 시작한다. 연구 완료는 매매 시작을 뜻하지 않는다.
5. 실전은 같은 해시의 전향 모의 거래 20건 이상, 비용 후 양수 성과, 러너 온라인, 계좌/잔고/권한 확인, 명시적 시작 확인을 요구한다. Upbit는 `UPBIT_TRADING_DISABLED=false`도 필요하다.
6. 정지는 미체결 매수 취소 → 소유 포지션 청산 → 체결 대사 순서다. 러너를 종료하는 것만으로 청산되지 않는다.

새 연구나 새 등록이 기존 실행을 변경하지 않는다. 시작할 때 가장 최근에 명시적으로 등록한 한 버전과 연구 자본을 고정한다. 다른 전략을 적용하려면 기존 운용을 정지하고 다시 시작한다. 한 실행 장부는 동시에 한 포지션만 가진다.

## 내부 연구 에이전트

기존 `strategy-generation` 실행기의 비용 예약/사용량, 응답 캐시, 작업 잠금, 체크포인트, 취소/재개와 독립 회사 검토를 재사용한다. 슬롯 선택기를 복제하지 않았다. CT는 전략 탭과 별도의 CT 전용 역할(`CT_MODELS`)을 쓴다(2026-10-13).

| CT 역할 | 모델 | 하는 일 |
| --- | --- | --- |
| `ctOrchestrator` | OpenAI `gpt-6.1-sol` · medium | 공개 접근법 웹 검색(선택 사항). `prompt_cache_key`는 실행 ID |
| `ctAnalyst` | OpenAI `gpt-6-luna` · low | 읽은 원문에서 원리·인용·근사·재량 요소 추출 |
| `ctDesigner` | Anthropic `claude-opus-5-5` · adaptive thinking · effort high | **설계 세션**: 학습 구간 측정 도구로 가설을 세우고 검증한 뒤 후보 0–3개 제출 |
| `ctRiskReviewer` | OpenAI `gpt-6.1-sol` · high | 동결 규칙의 누출·과최적화·**데이터 스누핑/다중 검정** 검토 |
| `ctEvidenceReviewer` | OpenAI `gpt-6.1-sol` · high | 최종 평가 증거·수치 게이트·다중 검정 확인 |

검토자는 후보를 쓴 역할과 다른 회사여야 한다(`assertDifferentProvider`, `ctReviewRoles`). 이전 실행의 후보(옛 `designer`, OpenAI)는 옛 검토 역할(Anthropic)로 검토된다. Anthropic 장애 대체는 같은 회사의 `claude-sonnet-5-5`뿐이다. 새 CT 연구 생성 시 CT가 실제로 쓰는 모델만 접근을 사전 확인한다.

### 왜 바꿨는가 (기준 실행 `9a3c8627`, BTCUSDT 1분봉, 2026-10-13)

총비용 $1.16 중 설계 호출 6회가 $1.03(89%), 호출당 입력 44K–55K 토큰, 캐시 적중 0. 입력의 약 60%가 무작위 1분봉 3구간 원시 CSV, 약 22%가 원문 전문이었다. 후보 6개는 첫 후보 하나를 다섯 번 고친 것이고(손절 0.55% 고정) 모두 비용 후 수익 미달로 탈락했다. 왕복 비용 약 0.31%가 평균 1분 범위 0.053%의 약 6배인데 설계 모델은 이 비용 장벽을 수치로 받지 못했고, 모든 조건에 웹 출처를 강제당해 데이터로 자기 가설을 확인할 수단이 없었다. 그래서 가장 어려운 일(비용 후에도 남는 우위가 데이터 어디에 있는가)을 Opus에게 측정 도구와 함께 맡기고, 웹 출처는 필수 근거에서 선택적 영감으로 내렸다.

CT의 단계별 실제 수행은 다음과 같다.

`lib/ct-tools.ts`가 입력/출력 스키마와 단계 권한을 검사한다. 도구는 데이터 현황, 수집, 허용 기억, 검색, 읽기, 비용 장벽, 조건부 수익 조회, 1분봉 열람, 학습 사전 검사, 후보 제출, 컴파일, 백테스트, 실패 진단을 제공한다. 검토 모델 호출도 기존 완료 응답/사용량 장부에 기록된다. 시장/종목/기간/예산은 모델 입력으로 변경할 수 없다. 실주문 도구는 없다. 성과 필드를 넣은 설계나 임의 코드/eval은 거부한다.

검색·읽기는 제품 안에서 수행한다. Node에서는 DNS의 모든 주소를 검사하고 검증 주소에 HTTPS 연결을 고정한다. 사설/메타데이터 주소, 사용자정보 포함 URL, 타 호스트 리다이렉트, 과대 본문을 거부한다. PDF·영상 내용 추출·로그인 자료는 지원하지 않는다. YouTube HTML을 읽었다는 사실이 영상 강의를 확인했다는 뜻은 아니다. 독립 검토는 내용 의미의 일치도 판단하며, 코드의 대응 검사는 검토를 대체하지 않는다.

## 설계 세션 (2026-10-13)

`design`/`reflect` 단계는 `generationCall` 1회가 아니라 **설계 세션**이다. 한 번의 진행(advance)마다 모델 턴 하나 또는 그 턴의 도구 실행 묶음 하나를 처리하고 저장한다.

**세션 시작 컨텍스트**(도구 호출 없이, 안정적인 것부터): 시스템 지시(역할·목적 함수·DSL·과최적화 규칙, `CT_DESIGNER_SYSTEM`) → 고정 블록(계약·비용·게이트·한도, 비용 장벽 표, `ctAnalyst` 원리 요약과 출처 id·제목·URL, 허용 기억의 규칙 텍스트) → 이전 세션 기록(조회 목록, 기각 가설, 후보별 규칙 텍스트와 학습·개발·스트레스 핵심 수치·탈락 사유; 전체 spec JSON은 부모로 지정 가능한 개발 실험 후보만; 세션 사이에 뒤에만 추가) → 이번 세션 안내와 사용자 brief. 원문 전문과 원시 가격 CSV는 넣지 않는다.

**비용 장벽 표 `cost_hurdle`**: 학습 구간 5봉마다 다음 봉 시가 진입을 가정해 보유 5/15/60/240/390봉의 MFE/MAE 분위수(p10–p90)와 MFE가 왕복 비용의 1·2·3배를 넘는 비율을 계산한다. 시간대(코인 UTC 4구간, 주식 개장 60분·장 중반·마감 60분)와 직전 60봉 범위 3분위 변동성 국면으로 나눈 표와 한 줄 결론을 붙인다. 왕복 비용은 `replayCT`와 같은 `ctNetTradePct` 공식이다(BTCUSDT 계약 0.3095%, 비용 2배 0.618%).

**도구**(모두 학습 구간 전용·서버 계산·무료, `tool()`을 거쳐 `ct_tools`에 캐시되어 재개 시 재계산하지 않음):

| 도구 | 내용 |
| --- | --- |
| `query_conditional_returns` | DSL 조건 그대로의 1–4단계 시퀀스로 이벤트를 찾는다(`detectCT`를 `replayCT`와 같은 이력 창·feature 캐시로 호출). 보유 시간별(최대 5개) 총수익 분위수, 비용 후 평균·중앙값·비용 2배, MFE/MAE, 같은 시간대 구성의 무조건 기준선 대비 차이, 손절·목표 격자(최대 4×4, `ctExit` 그대로) 목표 먼저/손절 먼저/시간 청산 비율과 비용 후 기대값, 월별 이벤트·기대값, `read_bars` 기준 시각. 앞을 내다보는 구간이 `trainingToMs`를 넘는 이벤트는 버린다. 결과의 `queryId`가 근거 id다. |
| `read_bars` | 서버가 제공한 시각(조회 대표 이벤트, 부모 후보·사전 검사의 학습 거래 시각)만 최대 4개, 앞뒤 합계 240봉. 첫 시가 대비 bp 정수 o/h/l/c, 구간 중앙값 대비 거래량 배수, 시각은 첫 줄과 30봉마다. |
| `screen_rule` | 완성 spec을 `validateCTSpec` 후 학습 구간만 `replayCT`로 돌려 `ctSummary`와 `ctGate` 사유를 돌려준다. 개발 결과는 돌려주지 않는다. 이 리플레이는 실험 단계의 학습 백테스트와 같은 캐시를 쓴다. |
| `submit_candidates` | 후보 0–3개와 `noEdgeReason`, `rejectedHypotheses`. 서버가 zod·명세·근거를 다시 검증하고 실패하면 `is_error` tool_result로 같은 세션에서 고치게 한다. 후보 0개는 「통과 전략 없음」 정상 종료(최종 구간 미개봉). `strict: true`는 실제 API가 400 "compiled grammar is too large"로 거부해(2026-10-13 측정, 비용 $0) 쓰지 않는다. 어떤 도구도 strict가 아니며 서버 zod 검증이 그 역할을 한다. |

**한도**(`CT_POLICY`, 이전 계약에 없으면 현재 값): 세션당 모델 턴 12회, 도구 호출 24회, `screen_rule` 6회, 연구당 세션 3회. 계산 시간은 기존 `maxComputeMs`(600초)를 공유한다. 마지막 턴 직전(턴·도구 한도 또는 예산 여유가 턴 예약의 2배 미만)에 "지금 제출하라"는 안내를 tool_result 뒤에 붙인다. `tool_choice`는 강제하지 않는다(`auto`). 그래도 제출하지 않으면 세션을 실패로 기록하고, 실패 2회 또는 세션 한도면 「통과 전략 없음」으로 끝낸다. 후보 한도 6은 **제출된(중복 제거 후) 후보 수**로 센다. 정체·중복 한도 규칙은 유지한다. 활성 작업 한도는 짧은 Opus 턴이 많아져 1,800초에서 3,600초로 늘렸다(새 계약부터).

**근거 규칙(근거 버전 2)**: `spec.sourceIds`·`mapping[].sourceId`는 근거 id다 — 확인된 웹 출처 id, 또는 이 실행에서 완료된 학습 구간 `query_conditional_returns`의 `queryId`. 조회 근거는 그 조회가 같은 feature와 같은 `timeframe`을 실제로 측정했을 때만 인정한다(lookback·임계값 차이는 `implementationAssumption`에 적는다). 존재하지 않는 id, 다른 실행의 id, 학습 구간 밖 조회는 거부한다. 수락된 후보에 `evidenceVersion: 2`가 붙고, 필드가 없는 옛 후보와 등록 패키지는 웹 출처 규칙으로 계속 읽힌다. 부모가 있으면 실측 문제·변경·기대 효과가 필요하고, 새 메커니즘은 `parentId: null`로 낸다.

**요청 형태(Opus 5.5)**: `thinking: {type: "adaptive"}`, `output_config.effort: "high"`(기본 medium이므로 명시), `tool_choice: auto`, temperature·budget_tokens 없음, 스트리밍 후 `finalMessage()`. 캐시 지점은 시스템 프롬프트(앞에 렌더링되는 도구 정의 포함), 첫 메시지의 고정 블록 끝, 최상위 자동 캐시(최신 블록) 3개다. assistant `content`(thinking 블록·서명 포함)는 수정 없이 다음 요청에 그대로 붙인다. `refusal`·`max_tokens`는 기존 `IncompleteResponseError` 경로이고, 절단은 한도 64,000토큰·effort medium으로 1회 재시도한다.

**내구성·비용 장부**: 세션의 모델 턴 하나하나가 `ask()`와 같은 `paidCall` 장부를 거친다 — 호출 전 턴 단위 예약(입력은 캐시 쓰기 단가, 출력은 턴 한도), `job.calls` 기록, 실시간 미터, 완료 응답 재사용 키(실행 id·세션·턴·직전 메시지 해시), 중단 시 미확인 비용, 절단 재시도. 메시지 기록은 `ct_session_messages(run_id, session, seq)`에 한 행씩 append-only로 저장하고(`strategy_generation_runs.payload`에는 참조만), 러너가 죽어도 저장된 턴부터 이어 이미 지불한 턴을 다시 사지 않는다. 취소 후 늦게 온 응답은 저장되지 않는다. 검토 예비 예산(`reserveFraction` 35%)은 유지하며, 새 세션은 턴 예약 3배 이상의 여유가 있을 때만 연다.

## 실행 명세와 동일 코드 계약

`ct-pattern-1`·`ct-pattern-2`의 JSON DSL만 실행한다(계약의 엔진과 명세의 엔진이 같아야 하고 새 연구는 `ct-pattern-2`). 한 패턴은 시간순 1–4개 단계, 단계마다 AND 조건 1–6개와 단계 간 최대 봉 수로 구성된다. feature는 수익률, SMA 거리, 가격 범위, 상대 거래량, 변동성 수축 비율, 이전 고점/저점 거리, 범위 내 위치, 확정 스윙 고점/저점 거리이고 `ct-pattern-3`에서 VWAP·전일 고저종·당일 시가·시가 범위·당일 고저 위치와 ATR 피처가 더해진다(위 「단타 트레이더의 어휘」). lookback/offset은 과거의 2–120/0–120봉, 시간배수는 1/3/12(1분 기준 1/3/12분 완성 봉)와 `ct-pattern-2`의 60/240/1440(위 「관찰 창」)이다. 최대 보유는 주식 390봉(정규장 한 세션), 코인 `ct-pattern-2`는 1,440봉이며 어느 쪽이든 포지션은 당일 경계에서 닫힌다. 2026-10-13 이전 엔진은 상위 봉 묶음의 연속성을 상위 봉 크기로 비교해 시간배수 3/12 조건이 항상 null이었다. 수정 후에야 실제로 평가된다. 스윙은 오른쪽 2봉 이후에만 확정한다. 상위 봉은 완성된 봉만 사용한다.

진입 유효기간, 최대 스프레드/괴리, 손절/목표/시간 청산(`ct-pattern-3`: 본전·트레일·시간 손절·R 목표), 진입 시간 창, 마지막 단계 저점 무효화, 위험/배분/거래량 참여 한도, 쿨다운을 수치로 고정한다. 롱 현물/주식만 지원한다. 추세선 작도, 자유 코드, 임의 지표, 숏/레버리지, 재량 판단은 지원하지 않는다. 표현할 수 없는 조건은 설명에만 넣어 통과시킬 수 없다.

`lib/ct-engine.ts`의 `detectCT`, `ctExitStep`(고정형 청산의 `ctExit`와 같은 판정), `ctQuantity`를 백테스트와 모의/실전이 공유한다. 실시간 판단 경로에는 모델/연구 실행기 호출이 없다. 거래마다 시작 당시 spec/hash와 실제 신호 관측값을 저장한다. 이름·설명만 다른 동일 규칙은 정규화 해시로 탐지한다. 실제 실행 전에도 승인 해시를 확인한다.

## 검증과 시장 차이

기본 데이터는 최근 180일, 시간순 60% 학습 / 20% 개발 / 20% 최종이다. 각 경계에서 필요한 이력을 다시 확보하며 이전 구간 신호/포지션을 넘기지 않는다. 최소 500봉이 없거나 비정상/중복 가격이 있으면 보류한다. 동일 시장·겹치는 종목·겹치는 최종 기간을 다른 연구에서 다시 열지 않는다. 원문과 모델 사전학습이 과거 기간을 몰랐다고 주장하지 않는다.

백테스트는 완성 봉 이후 다음 봉 진입, 비용/스프레드/슬리피지, 거래량 참여, 최소 주문, 수량 정밀도, 신호 만료와 미체결을 반영한다. 같은 봉에서 손절/목표가 모두 닿으면 손절을 먼저 적용하고 불리한 갭은 시가로 처리한다. 보유 중 봉이 누락되면 `data_error`이며 낙관적 청산을 만들어내지 않는다. 무거래, 데이터 오류, 실행 실패, 전략 기준 미달을 구분한다. OHLCV 참여율 제한은 실제 과거 호가/대기열/부분체결 복원이 아니다. 모의는 현재 호가에서 전량 체결하는 단순 모델이고 실전은 실제 누적 부분체결을 대사한다. 이 차이는 검토와 전향 모의 요구에 포함된다.

서버 게이트는 거래 20건 이상, 비용 후 양수 수익, **일평균 비용 후 순수익 > 0**, 최대 낙폭 15% 이내, 규칙 준수 100%, 종목/월 집중도 제한이다. 일평균은 평가 구간의 모든 날(주식은 뉴욕 기준 거래일, 코인은 UTC 날짜)의 일별 순수익률 평균이며 무거래일은 0으로 넣는다. 수수료·세금·스프레드·슬리피지를 모두 뺀 값이다. 비용 2배·1봉 지연·손절 민감도도 총수익과 일평균이 모두 양수여야 통과한다. 이 필드가 없던 과거 결과는 저장된 일별 행에서 다시 계산한다. 목표 수익은 게이트와 별개다. $8/$16/$24 예산 안에서 유료 호출 전에 예약하며 웹 검색 요금은 중앙 모델 비용 설정을 사용한다. 후보 최대 6개(제출 기준), 설계 세션 최대 3회, 개발 실험 묶음 최대 12개, 누적 계산 600초(1분봉 BTC 180일은 약 26만 봉), 활성 작업 3,600초(이전 계약 1,800초), 개선 정체 3회에서 정상 종료한다. 리뷰 예산을 미리 남긴다.

주식 연구는 Toss 인증·계좌·주문 API를 호출하지 않는다. 기존 MASSIVE_API_KEY로 7일씩 과거 분봉을 수집하며 빈 주간도 건너뛰어 계속한다. 수집 중이던 기존 Toss 연구는 재개 시 수집 데이터를 초기화해 공급자 혼합을 막는다. 이미 수집을 완료한 연구의 동결 데이터는 유지한다.

주식은 현재 종목 선택의 생존/선택 편향을 표시한다. 과거 구성 종목 복원이나 수정주가 복원이 아니다. 연구 원봉은 Massive adjusted=false이며 연속 세션 안에서만 패턴 이력을 사용한다. 집계는 UTC 격자이므로 60분 주식 봉은 정규장 첫 30분을 완성 60분 봉으로 만들지 않는다. 알려진 NYSE 2025–2028 휴장/조기 폐장만 버전 관리하며 그 밖의 연도는 거부한다. 긴급 폐장/거래정지/기업행사와 실전 IP 제약은 별도 한계다.

차트는 엔진의 패턴 구간, 조건값, 실제 사용 기준선, 확정 스윙, 신호/진입/손절/목표/청산과 거래량을 표시한다. 리플레이에서는 알려진 시점 이후만 선/표식을 보여준다. 수익·손실 대표 사례를 함께 선택하고 모든 연구 거래는 도구 결과 다운로드에서 확인한다. 운용 대시보드의 보유/거래 기록에서 개별 거래 차트를 열 수 있다. `ct_trade_charts`는 당시 관측한 봉과 실제 신호·체결·동결 해시를 별도 보존하므로 최신 시세 캐시가 사라져도 근거가 남는다. 최대 480봉(긴 운용은 처음 200/마지막 280봉)을 저장하며, 수정된 과거 봉은 원본을 덮어쓰지 않고 오류로 기록한다. 차트 저장 장애는 주문 감시/청산을 막지 않고 이벤트로 남긴다. 의도/근거 저장 중 만료된 매수 신호는 전송 직전에 다시 차단한다. 20봉 참고 고점/저점은 전략이 사용한 돌파선이라고 표시하지 않는다.

## 저장, 재개와 운용 안전성

기존 `strategy_generation_runs`에 CT 상태를 저장한다. `ct_data_pages`는 페이지 체크포인트, `ct_tools`는 완료 도구 응답, `ct_session_messages`는 설계 세션 메시지(append-only), `ct_replay_pages`는 전체 거래 기록, `ct_exposure`는 최종 기간 소진, `ct_strategies`는 등록 패키지, `ct_runtime`은 연구 러너 heartbeat, `ct_trade_charts`는 실제 운용 거래의 관측 봉과 규칙/체결 근거다. 큰 거래 목록은 별도 페이지에 저장하고 상태에는 대표 사례와 실제 총 거래 수를 남긴다.

브라우저/러너는 기존 DB lease로 같은 작업을 중복 실행하지 않는다. 완료 유료 응답과 도구 응답은 단계 저장 실패 후에도 재사용한다. 취소 후 늦게 온 응답은 상태/등록을 변경하지 못한다. 연구 기억은 동일 소유자·시장·주기·종목·비용·자본·엔진으로 제한하고 이전 개발 구간 결과만 전달한다.

장부는 `relay`, `surge`, `ct-stock`, `ct-crypto` × paper/live로 분리한다. 실계좌는 장부별 가상 잔액으로 격리됐다고 가정하지 않는다. 브로커 단위 DB 잠금, 실제 주문 가능 잔고/미체결, 소유 수량을 함께 검사한다. 다른 장부 미체결 매수의 잔여 수량 × 지정가 × 1.01 예약액을 추가 차감한다. 브로커가 이미 차감했다면 보수적으로 이중 예약되어 진입 가능 금액이 줄어들 수 있다. 주문 의도/identifier를 먼저 저장하고 응답 유실은 조회/대사한다. Upbit는 identifier로 복구하며 Toss가 client ID를 조회에 제공하지 못하는 경우 자동 재주문하지 않고 대기한다. 미확정 주문은 신규 진입과 정지 완료를 차단한다. 신호 만료, 오래된 호가, 손실 한도, 단일 포지션, 다른 장부 미확정 주문도 신규 진입을 차단한다.

브라우저를 닫은 뒤에는 상시 머신의 러너가 필요하다. 메모리 타이머는 영구 실행기로 쓰지 않는다. 연구 loop와 주문 감시 loop는 분리되어 있다. 연구 러너가 없으면 화면에 대기를 표시한다.

```sh
# .dev.vars는 서버 비밀이며 Git에 포함하지 않는다.
node --env-file=.dev.vars scripts/trading-runner.mjs --url http://localhost:3000
# 연구만 검증: 주문 감시 tick을 보내지 않는다.
node --env-file=.dev.vars scripts/trading-runner.mjs --generation-only
```

원격 실행에는 서버와 러너에 같은 `STRATEGY_RUNNER_SECRET`을 설정한다. Sites 원격 실행에서는 기존 사이트의 접근 정책에 맞는 인증을 확인한다. 요청이 실제 주문을 보내는 위치는 러너 머신이 아니라 대상 앱 서버이므로 Toss/Upbit의 허용 IP도 앱 서버 출구 IP여야 한다. 러너가 꺼지면 자동 매매 감시가 지속된다고 표시하지 않는다.

실제 Upbit 현재가/호가/계좌 읽기와 Toss SPY 15분 연구의 원봉 4페이지 수집도 확인했다. 실제 주문은 0회다. 전체 주식 연구, 실제 통과 후보의 독립 검토/최종 평가/등록, 전향 모의 체결, 실전 주문은 실데이터 통합 검증되지 않았다. 통과→독립 검토→최종 동결→등록→동일 규칙 실행, 유실 응답/부분체결/취소 순서는 고정 모델 응답과 합성 데이터 테스트로 구분해 검증한다. 한 연구의 성과를 일반 수익성의 증거로 사용하지 않는다.

기본 연구 실행은 로컬 Node + SQLite + Parquet다. 웹사이트 변경의 호스팅 배포 대상은 Sites이며, [배포 문서](deployment.md)에 따라 기존 프로젝트의 빌드·D1 연결·API 동작을 검증한다. 로컬 연구 DB와 시장 파일은 Sites에 자동 이전되지 않는다. 과거 Vercel용 Node/Nitro 및 D1 REST 어댑터 구성은 기본 배포 완료 기준이 아니다.
