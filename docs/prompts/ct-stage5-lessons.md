## 1. 왜 하는가 (실제 기록)

`docs/ct.md`와 로컬 DB(`~/.qquan/state/research.sqlite`)에서 확인한 사실이다.

### 1.1 기억은 있지만 원자료다

- 플레이북은 시도한 아이디어마다 한 행(메커니즘 · 조건 구조 · 등급 · 사유 · 측정 기간)을 쌓고, 설계 세션 시작 때 **같은 시장 최근 40개**를 그대로 넣는다. 누적 검정 수도 들어간다.
- 설계자는 이를 읽고 실제로 같은 계열을 피했다(BTC 1회차: "이전 4회 연구의 평균 회귀·돌파·추세 지속·투매 반등이 모두 실패", NVDA: 이전 후보를 다시 쓰지 않음, ETH: 이전 연구가 시간 대조군에 의존했음을 보고 `losers`로 변경).
- 그러나 "계열 전체가 왜 죽었나"라는 상위 결론은 저장되지 않는다. 매번 설계자가 40개 항목을 직접 읽고 추론한다. 40개를 넘으면 오래된 실패는 시야에서 사라진다(`omittedOlderEntries`). 누적 검정 수만 전체를 센다.

### 1.2 "하지 마라"만 있고 "이쪽은 아직이다"가 없다

- 플레이북에는 기각된 것만 있다. **어디가 아직 안 건드려졌는지**는 어디에도 없다.
- 4단계 ETH 실행의 설계자는 턴 10에서 "이미 기각된 아이디어와 겹치고, 새 정보 없는 검정을 장부에 더할 위험이 있어 후보 0개를 제출한다"고 멈췄다. 겹침을 알려 주는 기억은 있는데, 겹치지 않는 곳으로 가는 길을 알려 주는 기억은 없다.
- 3회 반복 실행 중 마지막(`3ab2ad6c`)은 7턴, 도구 7회, 예산의 8%만 쓰고 끝났다. 누적 검정 수가 커질수록 일찍 멈춘다.

### 1.3 설계자가 기억을 읽는지는 강제되지 않는다

- 플레이북은 시스템 지시의 권고("Do not re-run a mechanism the playbook shows as failed unless you can say what is different now")로만 작동한다. 서버는 후보가 이미 죽은 계열의 변형인지 확인하지 않는다. 확인은 후보가 생긴 뒤 검토자가 한다.

이번 작업의 목적은 세 가지다.
1. 연구가 끝날 때마다 **계열 단위 교훈**을 증류해 쌓는다(왜 죽었나, 무엇이 남았나).
2. **아직 안 건드린 영역**을 서버가 결정적으로 계산해 보여 준다(모델의 상상이 아니라 장부에서).
3. 설계자가 교훈을 읽은 것을 **서버 규칙으로 확인**한다(죽은 계열의 후보는 차이를 적어야 통과).

**하지 않는 것:** 모델 가중치·프롬프트를 자동으로 고치는 학습은 하지 않는다. 게이트를 완화하지 않는다. "안 건드린 영역"을 후보 목표로 삼지 않는다(1.2의 겹침 때문에 멈추는 것도, 빈 영역을 채우려 억지로 검정을 늘리는 것도 같은 크기의 위험이다. 5.1의 균형 문구 참조). 파생 데이터·DSL 확장은 이번 범위 밖이다.

### 공통: 새 정책 버전으로만 켠다

- 이번 변경(안정 블록의 교훈, 도구 정의·지시문 변경, `submit_candidates` 필드, 증류 호출)은 **새 계약에서만** 켠다. `policy.traderTools = 3`(`toolsVersion 3`).

- `traderTools = 2` 이하 계약은 지금과 **바이트 단위로 같은** 시스템 지시, 도구 정의, 안정 블록, 요청 옵션으로 재개되어야 한다.
  - 현재 `CT_DESIGNER_SYSTEM`을 `CT_DESIGNER_SYSTEM_STAGE4`로 고정하고, `CT_DESIGNER_SYSTEM_STAGE2`처럼 SHA-256 테스트를 붙인다. 새 지시문이 `CT_DESIGNER_SYSTEM`(5단계)이 된다.
  - `submit_candidates` 스키마의 새 필드는 3 이상 계약의 도구 정의에만 존재한다. 이전 계약의 도구 정의 바이트는 캐시 키이므로 건드리지 않는다.
- `QQUAN_CT_POLICY_VERSION`(판 서명 검증용 override)을 이 버전에도 쓸 수 있게 하되 기본 동작은 바꾸지 않는다.

### 2.1 계열 분류 (`lib/ct-playbook.ts` 또는 새 `lib/ct-lessons.ts`)

교훈과 커버리지를 합산하려면 아이디어를 같은 기준으로 묶어야 한다. 자유 서술 메커니즘만으로는 묶을 수 없다.

- 고정 열거형 `CT_FAMILIES`를 둔다. 출발점(현재 기록에 나온 계열): `mean_reversion`(급락·과매도 반등), `breakout`(범위·고점·저점 돌파), `trend_following`(모멘텀 추종·추세 속 눌림), `volatility_regime`(변동성 수축·확대·국면), `time_seasonality`(시간대·요일), `liquidation_cascade`, `levels_gaps`(VWAP·전일 고저·시가 범위·갭), `multi_timeframe_context`(상위 시간대 조건), `holding_overnight`(전일 → 다음 날 보유), `other`.
- 열거형을 바꿀 때는 `docs/ct.md`에 이유를 적는다. 값 추가는 허용하되 기존 값의 의미를 바꾸지 마라(저장된 교훈이 깨진다).
- 분류 방법: 기존 `ct_playbook` 행의 `structure`(feature·timeframe 목록)와 `mechanism`에서 **결정적 규칙**으로 계열을 정한다(키워드·feature 이름 매핑 + 우선순위 표). 모델 호출 없이 재현 가능해야 한다. 규칙으로 못 정하면 `other`로 두고, `other` 비율이 30%를 넘으면 5.1에서 규칙을 보강한다.
- 계열 분류는 `ct_playbook`에 새 컬럼으로 넣지 말고 읽을 때 계산한다(스키마 변경 없이 소급 적용). 테스트가 기존 행 전부에 대해 분류가 결정적임을 확인한다.

### 2.2 커버리지 지도 (결정적, 모델 호출 없음)

"안 건드린 영역"은 모델이 아니라 장부에서 계산한다.

- 입력: 같은 시장의 `ct_playbook` 행 전체(40개 제한 없음), 각 실행의 `ct.tests.signatures`(다중 검정 장부), 현재 DSL 어휘(`lib/ct-spec.ts`·`lib/ct-moves.ts`의 feature 목록, 시간 창, 레벨, ATR 단위, 관리형 청산 종류).
- 출력 `CTCoverage`:
  - 계열별: `{ family, ideas, tests, bestGrade, lastRun }`(`tests` = 서로 다른 장부 서명 중 그 계열에 속하는 수)
  - **어휘별 사용 여부**: DSL feature × timeframe, 시간 창, 레벨 피처, ATR 단위, 관리형 청산 변형이 지금까지 어떤 검정·후보에도 한 번도 안 쓰였는지 `untouched` 목록
  - 계열 × 청산 구조(고정 손절·목표 vs 관리형)의 빈 칸
- 수치는 개수만이다(성과 수치 없음). 개수는 학습 구간 결과에 의존하지 않으므로 누출 규칙의 대상이 아니다. 단, 항목이 "어떤 칸에 있다"는 사실은 해당 항목의 측정 기간이 새 연구 구간과 겹쳐도 동일하다(기존 `ctPlaybookView`의 등급 공개 규칙과 같다).
- 같은 서명을 반복 실행으로 센 것은 한 번으로 센다(`ctDistinctPriorTests`의 규칙).

### 2.3 교훈 증류 (유료 모델 호출 1회, 연구 종료 시)

**테이블** (`ensureCTSchema`에 추가, `CT_PLAYBOOK_SCHEMA`와 같은 패턴):
`ct_playbook_lessons`(id 결정적, owner_id, market, timeframe, run_id = 이 교훈을 만든 실행, family, verdict, cause, lesson, next_to_try, evidence_ids, measured_from, measured_to, model, recorded_at). 같은 실행을 두 번 증류해도 같은 결정적 id로 덮어쓴다(멱등). **행은 append-only**로 두고, 읽을 때 (market, family)마다 가장 최근 행을 현재 교훈으로 본다. 이전 버전은 지우지 않는다(기록 보존).

**호출 시점·실패:** 연구가 `done`이 될 때 `recordCTPlaybook` 직후 한 번. 플레이북 기록처럼 **한 번만** 하고(`ct.lessonsRecorded` 표시), 실패해도 실행 결과를 되돌리지 않는다(`lessons_record` 도구 기록에 failed로 남긴다). 중단 후 재개되면 이미 지불한 응답을 다시 사지 않는다(`paidCall`의 완료 응답 재사용 키).

**입력 (누출 없이):**
- 이 실행의 플레이북 항목들과 기각 가설, 학습 게이트 탈락·개발 탈락 후보의 **구조와 탈락 사유 분류**, `noEdgeReason`, 보정 기록 요약(눈의 판별력 판정 불가 여부).
- 해당 시장의 현재 교훈(있다면) — 증분 갱신을 위해.
- **모든 수치를 가린 뷰만** 준다: 항목마다 `ctPlaybookView`를 "모든 구간과 겹침"으로 호출해 `detail`을 비우고 사유의 숫자를 `ctStripNumbers`로 가린다. 증류 모델은 어떤 수익률·p값·거래 수도 보지 못한다. 그래서 교훈은 구조적으로 수치가 없다.
- 설계자의 생각(`ct_session_messages`의 thinking)과 위험·증거 검토자 출력은 넣지 않는다(자기 정당화의 재생산 방지, 4단계의 검토자 독립성 규칙과 같다).

**출력 스키마** (zod 서버 검증, `strict` 도구 문법은 쓰지 않는다 — 2026-10-13에 400 "compiled grammar is too large"로 거부됨):
```
lessons[]: {
  family: CT_FAMILIES,
  verdict: "dead" | "weak" | "unresolved",
  cause: "no_edge_after_cost" | "sample_too_small" | "regime_concentrated" | "fails_stress" | "holdout_flip" | "overfit_by_search" | "eye_no_skill" | "duplicate_of_dead" | "untestable_here",
  lesson: 한국어 한 문장(최대 200자) — 왜 이 계열이 이 판에서 안 됐는가,
  nextToTry: 한국어 한 문장(최대 160자) 또는 null — 이 계열 안에서 아직 확인하지 않은 구체적 변형,
  evidence: 이 교훈의 근거 플레이북 항목 id 배열(1개 이상)
}[]
```
- `verdict = dead`는 **그 계열의 항목이 3개 이상이고 최고 등급이 `development_failed` 이하이며 서로 다른 메커니즘이 2개 이상**일 때만 허용한다(서버가 항목으로 검증). 한 번 실패한 아이디어 하나로 계열을 죽이면 안 된다. 미달이면 `weak`로 낮춘다(서버가 거부하고 같은 호출 안에서 고치게 하거나, 한 번 재시도 후 낮춘다).
- `evidence`의 id는 실제 `ct_playbook` 행이어야 한다. 없는 id를 가진 교훈은 버린다.
- `lesson`·`nextToTry` 문자열에 `%`, 소수, "p=", "건" 앞 숫자 같은 **측정값 패턴이 있으면 거부**한다(규칙 임계값의 정수는 허용하지 않아도 되며, 의심스러우면 거부).
- 같은 (market, family)가 이미 교훈이 있으면 새 증거를 반영해 갱신하고, 새 증거가 없는 계열은 그대로 둔다(모델이 오래된 교훈을 지우거나 약하게 바꾸지 못하게, 서버가 `evidence`의 합집합을 유지하고 `verdict`를 낮추려면 새 항목이 있어야 한다).

**모델·비용:**
- 설계자(Opus)보다 싼 모델로 충분하다. 기존 역할 매핑에서 요약·추출용으로 쓰는 것과 같은 급을 쓰고, thinking은 끄거나 낮은 effort로 둔다. 선택과 단가 근거를 `docs/ct.md`에 적는다.
- 증류 입력은 시장당 수천 토큰이어야 한다. 항목 전체를 넣되 위 규칙으로 줄이고, 입력 토큰 상한과 출력 토큰 상한을 정책 필드로 고정한다.
- **전용 예비 예산** `lessonReserveUsd`(제안 $0.25, 구현 때 실제 단가로 재계산)를 새 계약의 연구 예산에서 연구 시작 때 따로 떼어 둔다. 설계·검토가 이 예비를 쓰지 못한다. 연구 도중 예산이 소진돼도 증류는 이 몫으로 돈다. 예비가 모자라면 증류를 건너뛰고 `ct.lessonsRecorded = { skipped: "reserve" }`로 남긴다. 이 예비는 `reserveFraction` 35% 검토 예비와 별개다.

### 2.4 설계 세션 시작 컨텍스트에 넣기

3 이상 계약의 안정 블록에 다음을 **고정(실행 시작 때 한 번, 도구 캐시 `lessons_summary`)**으로 넣는다. 순서는 캐시 안정성을 위해 `playbook` 다음이다.

1. `playbook`(기존): 최근 40개 원자료. 이번에는 40개 중복 제거 뒤 남은 수를 `omittedOlderEntries`로 계속 보여 준다.
2. `lessons`: (market, family)별 현재 교훈. `family`·`verdict`·`cause`·`lesson`·`nextToTry`·`evidence`(플레이북 항목 id)·`lastRun`. 원자료 40개에 근거 id가 있으면 설계자가 바로 대조할 수 있고, 40개 밖의 근거는 `omitted`로 표시한다.
3. `coverage`: 2.2의 지도. `untouched`는 길이 상한(상위 N개)을 두고 상한 초과분은 개수만 알린다.
4. 기존 `calibration`·`alreadyMeasured`·누적 검정 수는 그대로 둔다.

교훈·커버리지 읽기는 학습 구간 전용 정보만 쓰므로 누출 규칙을 새로 만들 필요는 없지만, 읽는 시점에 `ctPlaybookView`의 겹침 규칙이 적용된 원자료와 **서로 모순되는 숫자가 없어야 한다**(교훈에는 숫자가 없으므로 구조적으로 보장되며 테스트로 확인한다).

**시스템 지시 (`CT_DESIGNER_SYSTEM` 5단계) 추가 문구** — 영어로 쓰되 균형을 지켜라:
- 교훈은 "이 판에서 이 계열이 죽은 이유"를 알려 주는 기억이지 "이 영역을 채워라"는 목표가 아니다. 빈 영역은 가능성일 뿐 증거가 아니다.
- `dead` 계열의 후보는 교훈의 `cause`가 이번에 왜 적용되지 않는지 구체적으로 적어야 한다. `nextToTry`는 제안이지 지시가 아니고, 따라가면 그 검정도 장부에 들어가 다음 양성을 우연히 만들기 쉽게 한다.
- 이 연구의 장부와 누적 검정 수를 고려해 "우위 없음"은 여전히 정상 결과다. 새 정보 없는 검정을 더하지 마라. 같은 이유로, 빈 칸을 채우기 위한 검정도 더하지 마라.

### 2.5 서버가 읽었는지 확인 (`submit_candidates`)

3 이상 계약의 `submit_candidates`에 필드를 더한다(도구 정의는 계약 안에서 고정):
- `lessonChecks[]`: 후보마다 `{ candidateIndex, family(서버가 계산한 값과 일치해야 함), lessonId 또는 null, differsBecause }`.
- 서버가 후보의 `spec`에서 계열을 **결정적으로** 계산(2.1)한다. 그 계열에 `verdict = dead` 교훈이 있으면 `differsBecause`가 비어 있거나 20자 미만이면 `is_error` tool_result로 같은 세션에서 고치게 한다(기존 zod·명세 검증 실패 처리와 같다). 모델이 선언한 `family`가 서버 계산과 다르면 서버 값을 쓰고 불일치를 기록한다.
- `rejectedHypotheses`의 각 항목에도 선택 필드 `family`를 둔다(없으면 서버가 2.1로 채운다). 이렇게 하면 증류 입력이 정리된다.
- 통과한 `differsBecause`는 후보 기록에 저장되고 위험·증거 검토자에게 간다: "이 규칙은 `dead`로 판정된 계열의 변형인가, 후보가 적은 차이가 실제로 다른 메커니즘인가".
- 후보 0개로 끝나는 제출은 검증 대상이 아니다. `noEdgeReason`에서 교훈을 인용했는지는 확인하지 않는다(강요하면 무의미한 인용이 생긴다).

### 2.6 검토자 입력

위험·증거 검토자의 `research` 입력에 `lessons`(해당 후보 계열의 교훈과 같은 시장의 `dead` 계열 목록)와 후보의 `lessonChecks`를 더한다. 검토 지시에 이미 있는 "이미 기각된 메커니즘의 변형인가" 문장을 교훈 기반으로 구체화한다(3 이상 계약만). 설계자의 생각 요약은 여전히 넣지 않는다.

### 2.7 화면

- CT 화면의 「플레이북」 섹션(접이식)에 「교훈」 탭을 더한다: 계열별 카드(verdict, cause, 한 문장 교훈, 근거 항목 링크, 마지막 갱신 실행·시각), 그 아래 「아직 안 건드린 영역」(커버리지 지도).
- 읽기 전용이다. "다시 증류" 같은 유료 동작 버튼은 만들지 마라(소유자가 CLI 스크립트로 한다, 2.8).
- 진행 화면의 설계 세션 섹션에 이 실행이 시작 때 받은 교훈 수·`dead` 계열 수를 한 줄로 보인다. 연구 종료 후 증류 상태(`기록됨` / `건너뜀(예비 부족)` / `실패`)를 보인다.
- 새 UI는 `docs/design-system.md`·`app/ui.css` 프리미티브를 쓴다.

### 2.8 소급 증류 (기존 실행 소급)

이미 끝난 실행들(`bcf289ab` · `450b45dd` · `3ab2ad6c` · `893af88c` · `a682e11b` · `ae0d8fd0` · `8c2fe70f` · `f8aeaf03` 등)의 교훈이 없으면 5단계 첫 연구의 효과를 볼 수 없다.

- `scripts/research/ct-lessons-backfill.ts`: 시장별로 기존 플레이북 행 전체를 입력으로 한 번 증류한다.
- **`--dry-run` 기본.** 입력 토큰 수, 예상 비용, 계열별 항목 수, `other` 비율, 서버 검증으로 `dead`가 허용될 계열을 출력만 하고 모델은 호출하지 않는다. `--run`을 줘야 실제 호출하며, 한도를 `--max-usd`(기본 $0.50)로 받고 초과하면 중단한다.
- 시장(코인/주식)별로 따로 돈다. 결과는 `source: backfill`로 표시한다.
- 소급 증류는 소유자가 확인하고 `--run`을 줄 때만 돈다. 에이전트가 임의로 실행하지 마라.

## 3. 바꾸면 안 되는 것

- 1–4번 지시서의 불변 조건 전부.
  - 게이트 완화 금지(일평균 > 0, 스트레스 포함), 롱 전용, 당일 청산(코인 UTC 00:00), 1분봉 백테스트, 시간순 60/20/20, 최종 구간 1회 평가
- 설계자에게 개발 구간은 요약 수치만, 최종 구간은 아무것도 주지 않는다. 최종 구간 성과는 어디에도 저장하지 않는다. **교훈에는 수치가 아예 없다**(입력에서 가리고 출력도 검사한다).
- 독립 검토자는 설계자와 다른 회사(`assertDifferentProvider`)다. 증류 모델은 검토자가 아니며 판정권이 없다. 교훈은 기억이고 증거가 아니다.
- `traderTools ≤ 2` 계약의 시스템 지시, 도구 정의, 안정 블록, 요청 옵션은 바이트 단위로 그대로 둔다. SHA-256 테스트로 고정한다.
- 판 서명(같은 판 3회 → 409)과 보정 기록, "이미 잰 것" 규칙은 건드리지 않는다.
- 누적 검정 수 계산(서로 다른 장부 서명 기준)을 바꾸지 마라. 교훈 증류와 커버리지는 이를 늘리지도 줄이지도 않는다.
- 실주문 도구를 만들지 않는다. 증류 호출은 공개/저장된 연구 기록만 읽는다.
- preserved thinking, 턴 단위 비용 장부, 재개 시 재지불 없음.

## 4. 테스트

`tests/ct-lessons.test.mjs`를 새로 만들고, 아래를 전부 자동 테스트한다. 전체 `node --experimental-strip-types --test tests/*.test.mjs`가 통과해야 한다(변경 전 실패분은 구분해 보고).

**계열 분류·커버리지**
- 분류가 결정적이다: 같은 행을 두 번 분류해도 같고, 저장된 실제 행 전부(실DB 샘플 또는 고정 픽스처)에 계열이 하나씩 붙는다.
- `other` 비율이 픽스처에서 30% 이하다.
- 커버리지 합산: 같은 서명을 반복 실행으로 기록해도 한 번만 센다. 한 번도 안 쓰인 feature·timeframe·청산 종류가 `untouched`에 나온다.
- 커버리지에 성과 수치가 없다.

**증류**
- 모델은 가짜 응답으로 대체한다. 입력에 `detail`·숫자가 없다(최종 수익률 99.9를 넣은 픽스처가 입력과 저장 행 어디에도 없다).
- 출력 검증: 없는 근거 id → 해당 교훈 버림. `dead`인데 항목 3개 미만 또는 메커니즘 1개 → 거부 후 `weak`로 낮춤. 숫자/백분율이 든 문장 → 거부.
- 멱등: 같은 실행을 두 번 증류해도 같은 결정적 id, 행이 늘지 않는다. 새 증거 없이 `dead`를 `weak`로 낮추려는 갱신은 서버가 거부한다.
- 증류 실패·예비 부족이 실행 결과(`done`)를 바꾸지 않는다. 재개 시 이미 지불한 응답을 다시 사지 않는다(호출 횟수 0).
- 예비 예산: 설계·검토가 `lessonReserveUsd`를 쓰지 못한다. 예산 소진 상태에서도 증류가 이 몫으로 돈다.

**세션·정책**
- `traderTools = 2` 계약: 시스템 지시, 도구 정의, 안정 블록이 이전 SHA-256과 같다. 안정 블록에 `lessons`·`coverage`가 없다.
- `traderTools = 3` 계약: 안정 블록에 `lessons`·`coverage`가 있고, 재개해도 같다(도구 캐시).
- `submit_candidates`: 죽은 계열의 후보에 `differsBecause`가 없으면 `is_error`가 나오고 같은 세션에서 고칠 수 있다. 살아 있는 계열·후보 0개는 검증하지 않는다. 모델이 선언한 `family`가 서버 값과 달라도 서버 값을 쓴다.
- 검토자 입력에 `lessons`와 `lessonChecks`가 3 이상 계약에서만 들어가고, 설계자의 생각 요약은 여전히 없다.

**화면**
- 교훈 탭 렌더링, 빈 상태, 계열 카드의 근거 링크가 플레이북 항목으로 연결된다.

## 5. 실제 실행 검증

### 5.1 소급 증류 dry-run과 실행 (모델 비용 ≤ $0.50, 소유자 승인 후)

1. `ct-lessons-backfill.ts --dry-run`을 코인·주식 각각 돌려 계열별 항목 수, `other` 비율, 예상 비용을 보고한다. 소유자에게 보고하고 `--run` 승인을 받는다.
2. 승인 뒤 `--run --max-usd=0.50`. 나온 교훈 전체를 표로 보고한다(계열, verdict, cause, 한 문장, 근거 id). **사람이 눈으로 확인하라:** 각 `dead` 판정이 실제 항목(계열 3개 이상, 메커니즘 2개 이상)에 근거하는지, 교훈에 수치가 없는지, 근거 id가 모두 실존하는지.
3. 커버리지 지도를 같은 시점의 실DB로 출력하고 `untouched` 목록이 실제로 한 번도 안 쓰인 어휘인지 장부 서명으로 대조한다.

### 5.2 유료 연구 (Opus 설계, 한도 $8)

`CLAUDE.md`·메모리의 규칙대로 유료 연구는 검증 목적 외에 반복하지 않는다. 1회, 필요하면 같은 종류 판에서 최대 2회.

- **판:** 같은 판은 세 번 이상 못 돌리므로 5단계 효과를 볼 판을 정한다. 이전에 연구한 판 중 하나를 쓸 수 없다면 다른 종목(예: 기존에 안 돌린 SOL)으로 한다. 어느 판으로 하는지는 소유자에게 확인한다.
- **비교 기준(4단계 ETH 실행):** 가설 검정 101회(트리 후보 분할 3,720), 도구 흐름, 마지막 턴에서 "겹침이 많고 장부에 중복 검정을 더할 위험" 때문에 후보 0개 제출. `docs/ct.md` 「판과 눈」 5.2 참조.
- 보고할 것:
  1. 시작 때 받은 `lessons`·`coverage`의 내용(안정 블록 발췌).
  2. 설계자가 교훈을 인용·반박한 위치(생각 요약, `lessonChecks`).
  3. **재검정률:** 이 실행의 장부 서명 중 이전에 이미 있던 서명의 비율(5단계 전 ETH 실행과 비교). 낮아져야 좋은 신호지만 목표가 아니다.
  4. **새 정보율:** 이 실행의 장부 서명 중 이전 실행에 없던 것이 계열·어휘 기준으로 새 칸에 해당한 비율.
  5. 서버가 죽은 계열 후보를 막은 횟수와 `differsBecause` 내용.
  6. 증류 호출: 비용, 입출력 토큰, 생성된 교훈의 변경분(이전 대비). 예비 예산 범위 안인지.
  7. 연구 총비용, 종료 사유. **후보가 없으면 그것이 정상 결과다.** 후보가 나오면 위험·증거 검토자가 `lessonChecks`를 어떻게 평가했는지 인용한다.
- **실패 시나리오 점검(꼭 보고):** 교훈이 설계자를 더 일찍 멈추게 했는가(턴·도구·예산 사용량이 이전 실행보다 줄었나), 빈 영역을 채우려 새 정보 없는 검정을 늘렸는가(장부 증가). 두 방향 중 어느 쪽으로 쏠렸는지 숫자로 적고, 쏠렸다면 2.4의 문구 조정안을 제안한다(구현은 소유자 확인 후).

### 5.3 화면

교훈 탭 스크린샷(교훈 있음 / 빈 상태), 진행 화면의 증류 상태 줄. 파일은 `docs/research/stage5-screens/`에 둔다.
