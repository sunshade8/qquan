## 1. 왜 바꾸는가 (실측 근거)

기준 실행은 코인 연구 `9a3c8627-1564-4176-83fd-844f23c030d7`(BTCUSDT, 1분봉, 2026-10-13)이다. 원자료는 `strategy_generation_runs`, `ct_tools`, `llm_usage` 테이블에 있다.

- 총비용은 $1.16이고, 그중 설계 호출 6회가 $1.03(89%)이다. 호출당 입력은 44K~55K 토큰, **캐시 적중은 0**이었다.
- 설계 입력의 약 60%는 무작위 1분봉 3구간 원시 CSV(약 57K자)다. 약 22%는 원문 4개 전문인데, 자료 분석 단계에서 이미 원리를 뽑아 둔 뒤에도 매 호출 다시 넣는다. 프롬프트 순서가 `contract → statistics → minuteBars(매번 바뀜) → sources(고정) → trials`라서 고정 부분이 캐시되지 않는다.
- **후보 6개 모두 같은 이유로 탈락했다.** 사유는 비용 후 수익 미달, 일평균 미달, 비용 2배·지연·손절 민감도 실패였다. 개발 구간 수익은 -0.7%~-3.4%였다. 6개는 사실상 첫 후보 1개를 5번 고친 것이고 손절 0.55%는 한 번도 바뀌지 않았다.
- **구조적 원인은 비용 장벽이 보이지 않는다는 것이다.**
  - 계약 비용: 수수료 0.1%, 스프레드 0.05%, 슬리피지 0.03%. 엔진 공식(`lib/ct-engine.ts`)으로 왕복 약 **0.31%**다.
  - BTC 1분봉 평균 범위는 **0.053%**다.
  - 따라서 평균 봉의 약 6배 이상 움직임을 잡아야 한다. 설계 모델은 이 사실을 수치로 받지 못하고 짧은 매매 구조만 반복했다.
- **역할 설계가 거꾸로다.**
  - 가장 똑똑한 모델이 하는 일이 "웹 블로그 글의 원리를 DSL로 옮기기"다. `validateCTCandidate`가 조건마다 웹 출처 `sourceId`를 강제하므로 글에 없는 아이디어는 낼 수 없다.
  - 데이터는 학습 구간 155,520봉 중 무작위 1,170봉(0.75%)을 눈으로 훑는 것뿐이다. 자기 가설을 데이터로 미리 확인할 수단이 없다.

**목표:** 가장 어렵고 창의적인 일, 즉 "비용을 뺀 뒤에도 남는 우위가 데이터 어디에 있는가"를 찾는 일을 가장 똑똑한 모델에게 맡긴다. 그 모델에게 학습 구간 전용 측정 도구를 주고, 가설을 세워 검증하게 한 뒤, 살아남은 것만 규칙으로 확정하게 한다. 웹 출처는 필수 근거에서 선택적 영감으로 내린다.

이 재설계로 수익 전략이 나온다는 보장은 없다. 성공 기준은 연구 과정의 질과 비용 대비 효율이다(10절). 우위가 없으면 싸고 빠르게 "없음"으로 끝나는 것도 성공이다.

## 2. 모델 역할 변경 (CT 전용)

`GENERATION_MODELS.designer`는 전략 탭(`advanceSlotResearch`)도 쓴다. **기존 역할은 건드리지 말고 CT 전용 역할을 추가하라.** 전략 탭과 급등주의 모델 배정은 이번 범위가 아니다.

| CT 역할 | 제공자 / 모델 | 설정 |
|---|---|---|
| `ctOrchestrator` (웹 검색) | OpenAI `gpt-6.1-sol` | effort `medium`. 웹 검색은 OpenAI 내장 `web_search`를 그대로 쓴다. |
| `ctAnalyst` (원문 원리 추출) | OpenAI `gpt-6-luna` | effort `low` (현행 유지) |
| **`ctDesigner` (연구·설계·수정)** | **Anthropic `claude-opus-5-5`** | adaptive thinking, effort `high`(아래 참고), 도구 루프 |
| `ctRiskReviewer` | OpenAI `gpt-6.1-sol` | effort `high` |
| `ctEvidenceReviewer` | OpenAI `gpt-6.1-sol` | effort `high` |

- 검토자는 작성자와 다른 회사여야 한다(`assertDifferentProvider`). 설계자가 Anthropic이 되므로 CT 검토자는 OpenAI로 옮긴다. `advanceCTResearch`의 `assertDifferentProvider` 호출을 새 역할 기준으로 바꾸고, 같은 회사면 예외가 나는지 테스트로 고정하라.
- `researchModel`의 장애 대체는 Anthropic 역할을 Anthropic 안에서만 대체해야 한다(독립성 유지). 현재 대체 모델 `claude-sonnet-5`를 `claude-sonnet-5-5`($2/$10)로 올려라.
- `lib/ct-activity.ts`의 `CT_AGENTS`, `agentModel`, `callDoing`과 `app/ct-progress.tsx`가 새 역할 이름과 모델을 표시하게 하라. 기존 실행 기록에 남은 옛 역할명(`designer` 등)도 화면이 깨지지 않게 매핑하라.
- `checkGenerationModels`는 CT가 실제로 쓰는 모델만 사전 확인하게 하라.

### Claude Opus 5.5 API 제약 (어기면 400)

- `thinking: {type: "adaptive"}`만 쓴다. `{type: "disabled"}`, `budget_tokens`, `temperature`/`top_p`/`top_k`는 모두 400이다.
- **effort 기본값이 `medium`이므로 반드시 `output_config.effort`를 명시하라.** 설계는 `high`로 시작한다. `xhigh`는 비용·품질을 측정한 뒤 판단한다. `ResearchEffort` 타입에 `xhigh`가 없으면 추가한다.
- **강제 `tool_choice`(`any`, `{type:"tool"}`)는 400이다.** `auto`만 쓰고, 마지막 제출은 프롬프트로 유도하거나 `strict: true` 도구로 받는다.
- **preserved thinking:** 도구 루프에서는 assistant 응답의 `content` 전체(thinking 블록 포함)를 수정 없이 그대로 다음 요청에 붙인다. 이전 턴을 편집·삭제·재정렬하지 말고 append-only로 유지한다.
- **긴 출력은 스트리밍**하고 `finalMessage()`로 받는다. 지금처럼 스트림 이벤트로 실시간 토큰 미터를 갱신한다.
- **refusal에 대비한다.** `stop_reason: "refusal"`을 확인하고, 기존 `IncompleteResponseError` 경로로 처리한다.
- **prompt caching:** 시스템 프롬프트, 도구 정의, 고정 컨텍스트 순으로 쌓고 `cache_control: {type: "ephemeral"}`를 건다. 상위 수준 자동 캐싱도 가능하다. 실제 `usage.cache_read_input_tokens > 0`을 측정해 보고하라.
- SDK 사용법은 설치된 `@anthropic-ai/sdk` 문서와 타입에서 확인한다. 기억에 의존하지 마라.

## 3. 설계자를 "도구를 쓰는 연구자"로 (핵심 변경)

현재 `design`/`reflect` 단계는 `generationCall` 1회로 후보 1개를 받는다. 이것을 **설계 세션(design session)**으로 바꾼다. Opus 5.5가 학습 구간 측정 도구를 여러 번 호출해 가설을 세우고 검증한 뒤, 후보 1~3개를 제출하는 도구 루프다.

### 3.1 세션 시작 시 자동으로 넣을 컨텍스트 (도구 호출 없이)

다음 순서로 안정적인 것부터 넣는다(캐시를 위해).

1. 시스템 지시: 역할, 불변 조건, DSL 설명, 목적 함수, 과최적화 규칙.
2. 계약: 시장, 종목, 구간 경계, 비용, 자본, 게이트, 한도.
3. **비용 장벽 표 `cost_hurdle`**. 서버가 학습 구간에서 계산한다.
   - 엔진과 같은 공식으로 계산한 왕복 비용(%)과 비용 2배 시나리오.
   - 보유 시간 5/15/60/240/390분별: 진입 후 최대 유리 이동(MFE)과 최대 불리 이동(MAE)의 분위수(p10/p25/p50/p75/p90), 그리고 MFE가 왕복 비용의 1배·2배·3배를 넘는 비율.
   - 위 값을 시간대(코인은 UTC 시각 4구간, 주식은 장 초반·중반·후반)와 변동성 국면(직전 60분 범위 3분위)으로 나눈 표.
   - 한 줄 결론, 예: "평균 1분 범위 0.053%, 왕복 0.31% → 비용의 2배를 넘는 움직임은 60분 보유 기준 X%에서만 나타남".
4. 원리 요약: `ctAnalyst`가 추출한 approaches(원리, 인용, 근사, 재량 요소)와 출처 id·제목·URL. **원문 전문은 넣지 않는다.**
5. 허용된 연구 기억(`ct.memory`).
6. 이전 후보 기록(수정 세션일 때). 후보마다 규칙 텍스트(`ctRuleText`), 학습·개발 핵심 수치(순수익, 일평균, 수익 일 비율, 최악의 날, 거래 수, 낙폭), 스트레스 결과, 탈락 사유를 넣는다. **전체 spec JSON은 부모로 지정 가능한 후보에만** 넣는다. 이 블록은 세션 간에 뒤에 추가만 한다.
7. 사용자 brief.

### 3.2 설계 세션 도구 (모두 학습 구간 전용, 서버 계산, 무료)

각 도구는 `CT_TOOLS`에 입력·출력 zod 스키마와 단계 권한(`design`, `reflect`)으로 등록한다. 실행은 기존 `tool()`을 거쳐 `ct_tools`에 캐시되어 재개 시 재계산하지 않아야 한다. **조회 시점과 앞을 내다보는 구간(horizon)이 모두 `trainingToMs` 이전이어야 한다.** 경계를 넘는 입력은 도구가 거부한다. 수치는 반드시 `ctFeature`/`detectCT`/`replayCT`와 **같은 코드**로 계산하라. 별도 구현 금지.

1. **`query_conditional_returns`**: 핵심 탐색 도구.
   - 입력: DSL 조건 1~6개(`ctConditionSchema` 그대로)로 된 1~4단계 시퀀스, `maxGapBars`, 보유 시간 목록(최대 5개), 선택 사항으로 손절·목표 격자(최대 4×4), 쿨다운(봉).
   - 출력:
     - 이벤트 수, 고유 일수.
     - 보유 시간별 전방 수익률의 평균·중앙값·분위수, MFE/MAE 분위수.
     - 손절·목표 격자별 "목표 먼저 도달" 비율과 비용 후 기대값(%).
     - 월별 이벤트 수와 기대값(안정성 확인용).
     - 같은 시간대의 무조건 기준선 대비 차이.
   - 결과에 `queryId`(입력 해시)를 붙인다. 이것이 근거 id가 된다.
2. **`read_bars`**: 무작위 CSV 대체.
   - 입력: 기준 시각 목록(최대 4개), 앞뒤 봉 수(합계 최대 240). 기준 시각은 직전 조회 결과의 대표 이벤트나 부모 후보의 학습 구간 최악·최선 거래 시각이어야 한다. 서버가 제공한 시각만 허용한다.
   - 출력은 압축 형식이다.
     - 첫 봉 시가 기준 bp 정수의 o/h/l/c.
     - 거래량은 구간 중앙값 대비 배수(소수 둘째 자리).
     - 시각은 첫 줄과 30봉마다만 표기.
   - 원시 가격 CSV는 쓰지 않는다.
3. **`screen_rule`**: 완성 전 사전 검사.
   - 입력: 완성된 후보 spec 초안.
   - `validateCTSpec`을 통과한 경우에만 **학습 구간만** `replayCT`로 돌려 `ctSummary`와 `ctGate` 사유를 돌려준다.
   - 개발 구간 결과는 절대 돌려주지 않는다.
4. **`submit_candidates`**: 세션 종료.
   - 입력: 후보 1~3개(`ctCandidateSchema` 확장판, 3.3 참고).
   - `strict: true`로 정의하고, 서버가 zod로 다시 검증한다.
   - 실패하면 `is_error: true` tool_result로 사유를 돌려주고 같은 세션에서 고치게 한다(세션 한도 안에서).

**세션 한도** (`CT_POLICY`에 추가):
- 세션당 모델 턴 최대 12회.
- 도구 호출 최대 24회.
- `screen_rule` 최대 6회.
- 계산 시간은 기존 `maxComputeMs`를 공유한다.

한도에 도달하면 마지막 턴에 "지금 제출하라"는 지시를 넣는다. `tool_choice`는 강제하지 않는다. 그래도 제출하지 않으면 세션을 실패로 기록하고 기존 정체·후보 한도 규칙으로 처리한다.

### 3.3 근거 규칙 변경 (`validateCTCandidate`)

- `spec.sourceIds`/`mapping[].sourceId`를 **근거 id**로 일반화한다. 근거는 둘 중 하나다.
  - 웹 출처 id.
  - 이 실행에서 실제로 완료된 `query_conditional_returns`의 `queryId`.
- **조회 근거**인 조건은 그 조회가 같은 feature와 같은 `timeframe`을 실제로 포함했을 때만 인정한다. lookback·임계값은 달라도 되지만 차이를 `implementationAssumption`에 적게 한다.
- 기존 실행·등록 패키지와 호환되도록 스키마 버전을 올리고, 옛 형식도 읽을 수 있게 하라.
- 지어낸 근거를 막는다는 원래 목적은 유지한다. 존재하지 않는 id, 다른 실행의 id, 개발·최종 구간 조회는 거부한다.

### 3.4 후보 처리 흐름

1. 세션이 후보 1~3개를 제출한다.
2. 서버가 정규화 해시로 중복을 제거한다.
3. 각 후보를 학습 구간 `replayCT`와 `ctGate`로 걸러낸다(무료).
4. 학습 게이트를 통과한 후보만 기존 experiment 절차(개발, 비용 2배, 1봉 지연, 손절 ×0.9/×1.1)를 그대로 돈다.
5. `maxCandidates`(6)는 **제출된 후보 수**로 센다.
6. 정체 판정(`stagnation`)과 후보 한도 규칙은 유지한다.
7. 모든 후보가 탈락하면 `reflect` 세션을 연다. 새 세션은 이전 세션의 대화를 이어 붙이지 않는다. 3.1의 6번 블록에 새 결과를 추가해서 시작한다.

### 3.5 내구성·재개·비용 장부 (반드시 지킬 것)

- 세션의 **모델 턴 하나하나가 기존 `ask()` 경로와 같은 보장**을 가져야 한다.
  - 호출 전 비용 예약.
  - `job.calls` 장부 기록.
  - 실시간 사용량 미터.
  - 완료 응답 재사용 키(실행 id, 세션 번호, 턴 번호, 직전 메시지 해시).
  - 중단 시 미확인 비용 처리.
  - 절단(`max_tokens`) 시 한도를 바꾼 재시도.
  - `generationCall`을 늘리든 별도 함수를 만들든, 이 장부를 복제하지 말고 재사용하라.
- 세션 메시지 기록(assistant content 원형 포함)은 턴마다 체크포인트에 저장한다. 러너가 죽어도 같은 턴부터 이어서, 이미 지불한 턴을 다시 사지 않아야 한다. 큰 기록은 `strategy_generation_runs.payload`를 키우지 말고 별도 테이블에 페이지로 저장하라(`ct_replay_pages` 방식 참고, `db/ensure` 또는 `ensureCTSchema`로 테이블 생성).
- 취소 후 늦게 도착한 응답은 상태를 바꾸지 못한다. 기존 규칙과 같다.
- 예산:
  - Opus 5.5는 Sol보다 단가가 2배다. 세션 시작 전 "세션 최대 턴 수 × 턴당 예약" 대신 **턴 단위로 예약**한다. 검토용 예비 예산(`reserveFraction`)은 유지한다.
  - 기본 예산 $8 안에서 설계 세션 2~3회와 검토가 가능해야 한다. 단가와 캐시 적중률로 실제 추정치를 계산해 보고하라.

## 4. 설계자 시스템 프롬프트 (구현 시 이 내용을 담아라. 영어로 작성해도 된다)

다음 내용을 빠짐없이 담되, 지시보다 목적과 근거를 설명하는 방식으로 써라. Opus 5.5는 지나치게 규정적인 프롬프트에서 품질이 떨어진다.

- 너는 CT 연구자다. 목표는 **하루 단위로 비용 후 순수익이 양수인 규칙**을 찾는 것이다.
  - 서버 게이트: 총 순수익 > 0, 평가 구간 모든 날 기준 일평균 순수익 > 0(무거래일 0), 비용 2배·1봉 지연·손절 ±10%에서도 양수, 거래 20건 이상, 낙폭 15% 이내.
- 먼저 `cost_hurdle`을 읽고, 어떤 보유 시간·시간대·국면에서 비용을 넘는 움직임이 충분히 자주 나오는지 판단한 뒤 가설을 세워라.
- 가설마다 현상, 메커니즘(왜 그런 움직임이 생기는지), 반증 조건을 먼저 정하고 `query_conditional_returns`로 확인하라. 기준선보다 나은지, 월별로 안정적인지 봐라.
- 가설은 **서로 다른 메커니즘**으로 여러 개 탐색하라. 같은 아이디어의 임계값만 바꾸는 것은 탐색이 아니다.
- 조회 횟수가 늘수록 우연히 좋아 보이는 결과가 늘어난다.
  - 소수의 이벤트나 한두 달에 몰린 효과는 믿지 마라.
  - 서버는 모든 조회 기록을 검토자에게 넘긴다.
- 웹 원리 요약은 영감일 뿐 성과 증거가 아니다.
- 표현할 수 없는 조건(추세선, 뉴스, 숏 등)은 규칙에 넣지 말고 한계로 적어라.
- 제출 전 `screen_rule`로 학습 구간 결과를 확인하라. 학습 구간에서 이미 게이트를 못 넘는 후보는 제출하지 마라.
- 우위를 찾지 못했으면 억지로 후보를 만들지 말고, 그 사실과 근거(어떤 가설을 어떤 결과로 기각했는지)를 제출하라. `submit_candidates`가 후보 0개와 사유를 받을 수 있게 하라. 이 경우 연구는 "통과 전략 없음"으로 정상 종료한다.
- 출력 텍스트는 간결한 한국어로 쓴다. 성과를 주장하지 않는다.

## 5. 그 밖의 변경

- **웹 검색 단계는 유지하되 선택 사항으로 둔다.** brief가 비어 있거나 설계자가 원리 없이도 가설을 세울 수 있으므로, 검색 실패가 연구 전체를 멈추게 하지 마라. 지금은 출처 0개면 예외가 난다. 이 경우 출처 없이 design으로 넘어가게 하고, 화면에 그 사실을 표시하라.
- **검토자 입력도 갱신한다.** `ctRiskReviewer`, `ctEvidenceReviewer`에 다음을 넘긴다.
  - 설계 세션의 전체 조회 목록(조회 수, 각 조회 조건과 요약 결과).
  - 제출·기각된 가설 목록.
  - 근거 매핑.

  검토 지시에 "데이터 스누핑과 다중 검정 가능성 판단"을 추가한다. 최종 구간 결과는 여전히 설계자에게 전달하지 않는다.
- `lib/ct-samples.ts`의 무작위 3구간 CSV 주입을 제거한다. `read_bars` 도구로 대체한다. 시드 결정성 테스트는 새 도구 기준으로 바꾼다.
- 오케스트레이터(웹 검색) 호출에 `prompt_cache_key`를 실행 id 기준으로 넣는다(OpenAI). 고정 지시를 프롬프트 앞쪽에 둔다.

## 6. 바꾸면 안 되는 것 (불변 조건)

- 새 연구는 1분봉 고정. 5/15/60분은 기존 등록 패키지 호환용으로만 남긴다.
- 시간순 학습 60% / 개발 20% / 최종 20%.
  - 설계 도구는 학습 구간만 본다.
  - 개발 구간은 서버 experiment만 쓰고, 설계자는 요약 수치만 받는다(현행과 같다).
  - 최종 구간은 동결·노출 기록 후 1회만 평가하고, 그 뒤 수정·재도전은 없다.
- 서버 수치 게이트(`ctGate`, `ctNetPositive`)와 독립 검토 통과 없이는 등록 불가.
- 백테스트와 실전·모의는 같은 `detectCT`/`ctExit`/`ctQuantity`를 공유한다.
- 실주문 도구는 없다. 임의 코드나 eval 실행은 없다.
- 동시 실행 1개(`idx_generation_active`), lease, 취소·재개 규칙, 비용 장부의 의미.
- 모든 모델 입력은 신뢰하지 않는 데이터로 다룬다. 웹 원문 속 지시를 따르지 않는다.

## 8. 실제 실행 검증 (필수)

1. `npm run local`로 로컬 앱과 러너를 띄운다. `.dev.vars`에는 `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `QQUAN_OWNER_ID`가 있다. 비밀값을 출력하거나 커밋하지 마라.
2. 브라우저로 CT → 코인(BTCUSDT 기본) → 기본 설정($8)으로 **전략 생성**을 실제로 누른다. 끝까지 진행한다.
3. 다음을 `~/.qquan/state/research.sqlite`에서 뽑아 보고한다.
   - 역할·모델별 호출 수, 입력·출력·캐시 읽기 토큰, 비용(`llm_usage`).
   - 설계 세션별 턴 수, 도구 호출 수와 종류, 조회 수.
   - 제출 후보 수 → 학습 통과 수 → 개발 통과 수, 탈락 사유 분포.
   - 종료 사유와 총비용. 기준 실행 `9a3c8627`($1.16, 후보 6개 전원 탈락, 캐시 0)과 나란히 비교.
   - 설계자가 기각한 가설 목록과 근거 요약.
4. 진행 화면에서 지금 하는 일 패널과 활동 피드에 설계 세션의 턴과 도구 호출이 보이는지 스크린샷으로 확인한다.

## 10. 완료 기준

- 7절 테스트 전부 통과와 기존 테스트 무손상.
- 8절 실제 실행 1회 완료와 보고서.
- 같은 $8 예산에서 다음이 측정으로 확인된다.
  1. 설계 호출의 캐시 읽기 토큰 > 0.
  2. 원시 CSV·원문 전문이 설계 입력에서 사라짐.
  3. 서로 다른 메커니즘의 가설이 2개 이상 조회로 검증됨.
  4. 학습 게이트를 못 넘는 후보에 개발 구간 계산과 모델 비용이 쓰이지 않음.
- 수익 전략 발견은 완료 기준이 아니다. 우위가 없으면 근거와 함께 "없음"으로 끝나는 것을 정상 결과로 보고하라.
- 배포는 하지 않는다. 커밋은 소유자 지시에 따른다.
