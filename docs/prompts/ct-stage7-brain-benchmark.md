### 1.1 지금은 어떤 개선도 반증할 수 없다

- 천장 측정 세 번(무차별 탐색, 모델 비용 $0)이 모두 **후보 없음**이었다: 4단계 140조합, 실행·방향 192조합.

### 1.3 블라인드 판독의 검정력이 모자란다

## 3. A — 시험판 (정답이 있는 판)

### 3.1 심는 방법

`lib/ct-bench.ts`(순수 함수)에 다음을 만든다.

- 입력: 실제 Binance 1분봉(`loadCTData`가 만드는 것과 같은 형식), 심을 명세 `BenchPlant`, 시드.
- 명세 `BenchPlant`:
  - `trigger`: **현재 DSL과 측정 도구로 표현할 수 있는** 차트 모양 조건(피처·룩백·봉 주기·임계값). DSL 밖의 조건은 설계자가 원리적으로 찾을 수 없으니 시험이 아니다.
  - `side`: long | short
  - `horizonBars`, `horizonTimeframe`: 우위가 나타나는 구간(보유 하루 이내, UTC 00:00을 넘기지 않음)
  - `driftBp`: 사건 뒤 구간에 누적으로 더할 기대 수익(bp). **왕복 비용의 배수로 정한다**(현재 코인 프로필의 왕복 비용을 `lib/ct-costs.ts`에서 읽을 것).
  - `maxPerDay`: 하루 최대 사건 수(희소성)
- 심는 방식: 시간순으로 한 번 훑는다. 완성된 봉에서 (이미 심은 값이 반영된) 과거만 보고 `trigger`를 평가한다. 발화하면 다음 `horizonBars` 동안 봉마다 로그수익률에 `driftBp / horizonBars`를 더하고, 그 뒤 가격 경로를 누적으로 다시 만든다. 한 봉의 시가·고가·저가·종가에는 같은 배율을 적용해 봉 모양을 보존한다. 거래량은 바꾸지 않는다.
- 출력: 심은 봉 데이터, 실제 발화 시각 목록, 명세 해시 `plantHash`.
- 결정론: 같은 입력·명세·시드면 바이트 단위로 같은 결과가 나와야 한다(테스트).

### 3.2 난이도별 판 (사전 등록)

BTCUSDT, 최근 365일, 1분봉으로 시작한다. 명세의 구체 임계값은 구현자가 정하되, **정한 뒤 실행 전에 커밋**하고 이후 바꾸지 마라.

| 판 | 우위 | 봉 | 방향 | 세기(왕복 비용 배수) | 희소성 |
|---|---|---|---|---|---|
| P1 쉬움 | 단일 피처(예: 짧은 급락 뒤 반등) | 5분 | 롱 | ×4 | 하루 1–3회 |
| P2 보통 | 두 조건 모양(예: 범위 수축 뒤 상향 이탈) | 15분 | 롱 | ×2.5 | 하루 0.5–2회 |
| P3 어려움 | 60분 맥락 + 1분 진입 | 60분+1분 | 숏 | ×1.5 | 하루 0.3–1회 |
| N0 대조 | 심지 않음(`driftBp = 0`, 같은 파이프라인 통과) | — | — | 0 | — |

**명세는 설계자에게 절대 보이지 않는다.** 명세 파일은 `scripts/research/bench/plants.json`(또는 DB의 봉인 행)에 두고, 실행에는 `plantHash`만 기록한다. 시험판 실행의 지시문·안정 블록·도구 결과·웹 출처 어디에도 명세 문구가 들어가면 안 된다(테스트로 확인: 시험판 실행의 모든 요청 본문에 명세의 피처 이름+임계값 문자열이 없는지).

### 3.3 판 자체의 타당성 검사 (모델 비용 $0, 유료 실행 전 필수)

각 판마다 다음을 확인하고 보고서에 표로 적는다. 하나라도 실패한 판은 명세를 고친 뒤 다시 검사한다. 이 단계에서 명세를 고치는 것은 허용되지만, 유료 실행이 시작된 뒤에는 금지다.

1. **신탁 후보**: 심은 규칙 그대로를 CT 후보로 만들어 학습·개발·최종 게이트(`ctGate`, 비용 2배·1봉 지연 스트레스 포함)를 통과하는지 본다. 통과하지 못하면 판이 너무 어렵거나 엔진과 심는 방식이 어긋난 것이다.
2. **무차별 탐색 기준선**: 기존 천장 측정 경로(`walkForward` 등)를 시험판 데이터에 돌린다. 심은 우위가 탐색 공간 안에서 발견되는지 확인한다. 이 결과가 "모델 없이도 찾을 수 있는 상한"이다.
3. **N0 거짓 양성**: 같은 무차별 탐색을 N0에 돌린다. 후보가 나오면 기준선 자체의 거짓 양성률로 기록한다.
4. **실제 판과의 차이**: 심은 판과 원본의 일별 수익률 분포·변동성·1분 범위 평균을 비교한다. 심은 흔적이 비현실적으로 튀면(예: 사건 뒤 봉 범위가 원본 분포의 99% 밖) 세기나 방식을 조정한다.

### 3.4 격리 (불변 조건)

시험판 실행은 계약에 `bench: { id, plantHash, board: "P1"|"P2"|"P3"|"N0", designerModel, replicate }`를 갖고, 다음을 지킨다. 모두 테스트로 고정하라.

- **쓰지 않는다**: `ct_playbook`, `ct_playbook_runs`, `ct_playbook_lessons`(증류 포함), `ct_scoped_memory`, `ct_strategies`(등록 거부), 운용·모의·실전 경로 전체, 기존 `ct_calibration`.
- **읽는 것은 고정한다**: 안정 블록의 플레이북·교훈·커버리지·보정 요약은 시험 묶음을 만들 때 한 번 동결한 스냅샷을 모든 모델·반복에 똑같이 쓴다. 그래야 모델 간 비교가 공정하다.
- **최종 노출**: 실제 `ct_exposure`에 쓰지 않는다. 시험판의 최종 구간은 심은 데이터라 실제 홀드아웃을 소모하지 않는다. 별도 이름공간(`bench_exposure` 또는 `ct_exposure`의 `kind` 열)으로 분리하라.
- **다중 검정 장부**: 시험판 실행마다 독립 장부로 시작한다. 실제 연구의 누적 검정 수에 더하지 않는다.
- **판 서명**: 서명에 `plantHash`·`designerModel`·`replicate`를 넣는다. 같은 판의 반복 실행이 409로 막히거나 `ctResolveBoard`가 방향을 바꾸지 않게 한다. 시험판에서는 `ctResolveBoard`를 끈다(같은 판을 같은 조건으로 반복하는 것이 목적이다).
- **웹 검색·원문 추출 끔**: 심은 판에서는 외부 출처가 의미 없고, 비용과 분산만 늘린다. `sourceNote`에 "시험판: 웹 출처 생략"을 남긴다.
- **화면**: CT 연구 목록에서 시험판 실행은 기본으로 숨기고, 「시험판」 필터나 하위 탭에서만 보인다. 실제 연구 집계(완료 수, 비용 합계 등)에서도 빠진다.

### 3.5 설계자 모델 선택 (시험판과 판독 세션 전용)

- `bench.designerModel` ∈ {`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`}. 실제 연구의 기본 설계자(`CT_MODELS.ctDesigner`)는 바꾸지 않는다.
- 지시문·도구 정의·안정 블록은 모델과 관계없이 **바이트가 같아야 한다**. 모델별 효과가 아니라 프롬프트 차이를 재게 되면 안 된다.
- 모델별 API 차이를 확인하라(`claude-api` 스킬의 모델 표와 이전 가이드를 직접 읽을 것. 기억에 의존하지 마라):
  - Opus 5.5: thinking 끄기 불가, effort 기본 medium(우리는 명시적으로 지정)
  - Sonnet 5.5: `{type:"disabled"}`는 400이다. effort 단계가 재보정됐다. 턴별 effort 시스템 메시지(`mid-conversation-output-config-2026-07-01`)는 thinking이 켜진 상태에서만 지원된다.
  - Haiku 5.5: 현재 fast 등급은 `reasoningParams`에서 thinking을 끈다. 설계자로 쓸 때는 다른 모델과 같은 adaptive + effort 규칙을 쓴다. 한 요청의 프롬프트가 100K를 넘으면 단가가 5배라 비용 예약에 반영하라.
  - 세 모델 모두 강제 `tool_choice`(any/tool)는 400이다. 지금처럼 `auto`를 유지한다.
- **세션 중간에 모델을 바꾸지 마라.** 캐시가 모델별이라 바꾸는 순간 40–75K 토큰을 다시 쓴다.
- GPT-6.1 Sol 설계자는 이번 범위가 아니다. 현재 코드에 OpenAI 설계 루프가 살아 있는지만 확인해서 보고하라. 큰 어댑터를 새로 만들지 마라. 검토자 독립성 규칙(`assertDifferentProvider`)은 그대로 둔다. 세 모델이 모두 Anthropic이니 검토자는 계속 OpenAI다.

### 3.6 채점 (서버 계산, 사전 등록)

실행이 끝나면 `ct_bench_results`에 한 행을 쓴다.

- `recovered`(주 지표, 참/거짓): 설계자가 낸 후보·부품·북 중 하나 이상이 학습·개발 게이트를 통과하고, **진입 시각이 심은 발화 시각과 겹치며**(같은 봉 ±1봉 허용, 겹침 비율 = |교집합| / min(|후보 진입|, |발화|) ≥ 0.5), 방향이 같은 경우.
- `recoveredFinal`: 위 후보가 최종 구간에서도 비용 후 일평균 > 0인 경우.
- `near`: 겹침 비율 0.2–0.5인 제출이 있으면 기록한다(부분 발견).
- `falsePositive`(N0 전용): 어떤 후보든 모든 게이트를 통과한 경우.
- 과정 지표: 비용(역할별·토큰 항목별), 모델 턴 수, 도구 호출 수, 제출 거부 수, 장부 검정 수, 심은 피처를 처음 측정한 턴 번호(측정 도구 입력의 피처·봉 주기가 명세와 맞는지 서버가 비교), 고른 봉 주기가 명세와 맞는지, 종료 사유.
- 채점기는 설계자에게 보이지 않는다. 채점 결과는 실행이 끝난 뒤에만 계산한다.

## 4. B — 판독 장부 (누적되는 블라인드 예측)

### 4.1 판독 세션 (새 작업 종류, 연구와 별개)

- 목적: 설계자 모델의 "차트를 보고 다음을 읽는 능력"을 싸게, 많이, 누적해서 잰다.
- 형식: 한 번의 짧은 세션. 안정 블록(판독 규칙 + 자기 판독 기록 요약) → 서버가 고른 블라인드 차트 24장 → 도구 `submit_forecasts` 한 번 호출. 일반 보기·`read_bars`·측정 도구는 주지 않는다.
- 차트 형식: `ct-chart-3-blind`(시간대 없는 형식)를 그대로 쓴다. 바이트 동일한 렌더 경로를 재사용하라.
- **시각은 서버가 고른다.** 설계자는 시각도, 시각 목록도 모른다.
  - 판독 구간: 실제 CT 연구가 쓰는 범위(최근 365일과 모든 `ct_exposure` 구간)와 겹치지 않는 **더 오래된 구간**(예: 2019-01-01부터 최근 400일 전까지)을 계약 상수로 정한다. 판독은 결과를 보여 주는 일이라, 실제 연구의 학습·개발·최종 구간과 섞이면 안 된다.
  - 층화 무작위: 시드 고정, 같은 UTC 날짜·같은 종목에서 최대 2장, 같은 날 두 시각은 4시간 이상 떨어뜨린다. 결과 구간(시각 + 지평)이 판독 구간 안에 있어야 한다.
  - 한 시각은 장부 전체에서 한 번만 쓴다(모델 비교용 공유 세트는 예외, §4.4).
- 예측 항목(시각마다): 방향 `up | down | flat`(flat = 지평 수익의 절댓값이 왕복 비용 미만), 크기 구간(예: <1c, 1–2c, 2–4c, >4c, c = 왕복 비용), 확신 0.5–1.0, 짧은 태그(설계자가 본 셋업, 자유 문자열 40자 이하).
- 지평: 계약 상수로 하나만 정한다(기본 60분). 여러 지평은 다중비교를 늘리므로 이번에는 하나만 쓴다.

### 4.2 장부 `ct_eye_ledger`

예측 한 개가 한 행이다: id, owner, 모델 id, 정책 버전, 차트 형식, 시장·종목, 시각의 해시(원래 시각은 서버만 아는 별도 열), 지평, 예측(방향·크기·확신·태그), 실제 결과(지평 수익 bp, 방향, 크기 구간), 세트 id, 출처(`eye_session` | `bench`), 기록 시각. 멱등으로 기록한다.

집계(서버 계산, 모델별·차트 형식별·지평별):

- 방향 적중률(실제 flat 제외 기준과 포함 기준 둘 다), 이항 p, Wilson 95% 구간
- **기후값 대비 Brier 기술 점수**: 기준 = 판독 구간에서 같은 지평의 up/down/flat 기저 비율
- 확신 구간별 보정(0.5–0.6 / 0.6–0.7 / 0.7–0.8 / 0.8+ 각각의 실제 적중률)
- 날짜 군집을 고려한 부트스트랩 구간(시드 20261018, 4,000회)
- 누적 진행: "n / 44 (70% 눈 검정력 0.8)"를 표시

기존 `grade_blind`·`ct_calibration`(이벤트 vs 대조군 분류)은 그대로 두고 동결한다. 판독 장부는 다른 질문(다음 N분 예측)이라 합산하지 않는다.

### 4.3 설계자에게 자기 기록 돌려주기 (정책 9)

- 새 정책 `traderTools = 9`에서만 켠다(`CT_POLICY_V8` 동결, ≤8 지시문·도구·안정 블록 SHA 테스트 유지).
- 실제 연구 설계 세션의 안정 블록에 `eyeRecord` 절을 넣는다. 내용은 **이 설계자 모델의** 누적 판독 기록이다: n, 적중률과 구간, Brier 기술 점수, 확신 보정, **태그별 적중률**(n ≥ 8인 태그만, 상위·하위 각 5개).
- 숫자와 태그만 넣는다. 판독 구간의 시각·가격은 넣지 않는다. 판독 구간은 실제 연구 구간과 겹치지 않으므로 누출 규칙(플레이북의 측정 기간 겹침 규칙)에 걸리지 않는다. 이것도 테스트로 확인하라.
- 지시문에 한 문단을 추가한다(교체 말고 추가만). 판독 기록은 "어떤 셋업에서 내 눈이 맞고 틀리는지"를 알려 주는 자료다. 높은 적중 태그는 가설의 출발점이 될 수 있지만 **근거(evidence)로 인용할 수 없다**. 근거는 여전히 이 실행의 학습 구간 측정이다.
- 판독 세션의 안정 블록에도 같은 `eyeRecord`를 넣어, 모델이 자기 약점을 알고 다음 판독을 하게 한다.

### 4.4 모델 비교용 공유 세트

- 같은 시각 세트(시드 고정 24장 × 4세트 = 96장)를 Opus 5.5·Sonnet 5.5·Haiku 5.5에 각각 보여 준다. 공유 세트는 `shared_set_id`로 묶고, 모델별 누적 장부에는 들어가되 "공유 세트"로 표시한다.
- 비교: 같은 시각에 대한 대응 비교(McNemar 정확 검정, 방향 적중 기준)와 Brier 기술 점수 차이의 부트스트랩 구간.
- 공유 세트를 보여 주는 순서와 이미지 바이트는 모델 간에 같아야 한다.

### 4.5 화면

CT 「검증」 하위 탭에 「판독 장부」 카드를 추가한다. 모델별 n/44 진행, 적중률·구간, Brier 기술 점수, 보정 막대, 태그 표를 보여 준다. 판독 세션 시작 버튼(모델 선택, 세트 수 1–4, 예상 비용 표시)을 둔다. 디자인은 `ui.css` 프리미티브와 기존 CT 카드 형식을 따른다.

## 5. C — 실제 실행과 판정

### 5.1 먼저 고칠 것

- `lib/llm-usage.ts`: `claude-sonnet-5-5`의 캐시 읽기를 $0.10으로 고친다(공식 페이지 2026-10-18 확인). Sonnet 5와 패턴이 겹치지 않게 분리하고, 단가 출처와 날짜를 갱신한다.
- 비용 예약: Haiku 5.5의 100K 초과 할증, 이미지 토큰(장당 1,100 가정 유지)을 시험판·판독 세션 예약에 반영한다.

### 5.2 유료 실행 한도

**이 지시서로 승인된 유료 모델 비용은 총 $15다.** 실행 전 예상 비용표를 보고서에 먼저 쓰고, 누적 비용이 $15에 닿으면 멈추고 보고한다. 시험판 실행 하나의 `budgetUsd`는 $3로 둔다.

예상(실측 단가 기준, 연구 1회 환산):

| 실행 | 개수 | Opus 5.5 | Sonnet 5.5 | Haiku 5.5 | 합계 |
|---|---|---|---|---|---|
| 판독 공유 세트 (24장 × 4) | 모델당 4 세션 | ≈ $0.8 | ≈ $0.4 | ≈ $0.02 | ≈ $1.2 |
| 시험판 P1·P2·P3·N0 × 반복 2 | 모델당 8 | ≈ $8 | ≈ $4 | ≈ $0.3 | ≈ $12.3 |

순서: (1) §3.3 타당성 검사($0) → (2) 판독 공유 세트(싸고 빠름) → (3) 시험판 P1 한 판을 세 모델로 1회씩 돌려 파이프라인 확인 → (4) 나머지 실행.

### 5.3 사전 등록 판정 기준 (실행 전에 커밋하고, 이후 바꾸지 마라)

시험판 반복이 판×모델당 2회뿐이라 결과는 **방향 지표**다. 보고서에 이 한계를 숫자와 함께 적어라.

- **"Sonnet으로 내려도 된다"**: Sonnet의 `recovered` 수 ≥ Opus의 `recovered` 수 − 1(8회 중), N0 거짓 양성이 Opus보다 많지 않고, 판독 공유 세트의 McNemar p ≥ 0.05이고 Brier 기술 점수 차이 구간이 0을 포함하는 경우.
- **"Opus 유지"**: Opus가 `recovered`에서 2회 이상 앞서거나, 판독에서 유의하게 앞서는 경우.
- **"판정 보류"**: 두 모델 모두 P1에서 `recovered` = 0인 경우. 이때 문제는 모델이 아니라 도구·지시문·판 구성이다. 원인을 과정 지표(심은 피처를 측정했는가, 봉 주기를 맞췄는가, 어디서 멈췄는가)로 진단해 보고하라.
- **Haiku**: P1 회수율과 판독 점수만 보고한다. 설계자 교체 판단은 하지 않는다.
- 판정은 보고만 한다. **실제 연구의 기본 설계자 모델 변경은 소유자 결정**이다. 코드 기본값을 바꾸지 마라.
