‘모든 옵션’은 CT 거래에 필요한 상품·방향·증거금·주문 기능을 뜻한다. 출금, Earn, Pay, 대출 상품 가입, 타인에게 자금 송금 등 별개 금융 업무를 추가하지 않는다. 실제 자금 거래나 계좌 설정 변경은 연구 기능 선택만으로 실행하지 않는다.

공통 연구 원칙:

- 수수료는 레이크다. 목표는 확실한 거래만 고르는 것이 아니라 위험 한도 안에서 비용 후 총 기대값 `Σ(조건부 기대값 − 비용)`을 개선하는 것이다. 혼자 비용을 못 넘지만 기준선을 이기는 신호는 부품 후보로 측정한다. 통계 게이트를 통과하기 전에는 유효한 우위로 단정하지 않는다.
- 모든 주요 성과 화면에 **비용 후 일평균·수익일 비율·일간 샤프·최대 낙폭**을 함께 표시한다. 수익일 비율·샤프의 무거래일 처리, 연율화, 무분산 상태를 사전 고정한다.
- 차트 모양 매매 범위를 유지한다. 부품과 라우터의 알파 입력은 계약에 있는 선택 종목의 차트 관측값이다. 뉴스·타 자산 신호·종목 선택으로 범위를 넓히지 않는다. 펀딩·담보·환율·계약 메타데이터는 실행·비용·위험 계산에 필요할 때만 사용한다.
- 원자료는 1분봉이고 후보·부품의 판단 봉은 에이전트가 허용된 범위에서 선택한다. **사용자 봉 주기 선택 옵션은 만들지 않는다.** 거래 상품·방향·레버리지의 직접 지정은 이 원칙과 별개다.

## 2. 버전·저장·운용 경계 — 모든 절에 적용

### 2.1 기존 계약 동결과 새 버전

- 부품·북은 새 `traderTools = 7`과 `ctSessionPolicy(...).book`에서 켠다. 통합 의사결정·기억·상품 의미도 새 계약에 명시적인 schema/engine/accounting/router 버전으로 고정한다. 정책 숫자 하나로 상품 지원 여부를 추정하지 않는다.
- `traderTools ≤ 6`의 지시문·도구 JSON·안정 블록·요청 옵션은 바이트 그대로, 종료 규칙·비용·체결·기억 동작은 기존 계약대로 보존한다. 기존 SHA-256 및 `ct-pattern-1/2/3` 골든 테스트를 유지하고 정책 6 고정 테스트를 추가한다. 새 필드를 과거 해시 대상 객체에 기본 삽입하지 않는다.
- `QQUAN_CT_POLICY_VERSION=6`은 실제 기존 6 정책 전체로 동결한다. 7용 정책 객체에서 숫자만 6으로 바꿔 새 필드·의미를 유입시키지 않는다. 기존 1–5 override도 유지한다.
- `ct-book-1`은 북 신호 집계 버전이다. 공통 의사결정·체결·상품 회계 버전과 함께 해시하며 기존 엔진의 의미를 덮어쓰지 않는다.
- 판 서명에 정책 버전이 있으므로 7은 새 설정의 판이지만 **새로운 독립 표본이나 미노출 최종 구간이 아니다.** 노출·다중검정 장부는 버전 간 이어진다. 오염 실행 `7a4354f4`는 모든 정책의 성능·보정 합산에서 제외하고 원본 행과 오염/노출 이력은 보존한다.
- 비용 프로필의 실측 p90 하한, `ctGate` 기준값, 비용 2배·1봉 지연 스트레스, `paidCall`, 예약 비율과 재개 시 중복 청구 방지를 유지한다. 새 상품은 상품에 맞는 새 비용 모델을 명시하고 기존 수치를 낮춰 통과시키지 않는다.

### 2.2 최종 결과 보존과 연구 기억의 분리

현재 코드는 `ct.final/finalStress/finalDelayed`와 리플레이 결과를 실행 증거로 보존하고, `ct-playbook.ts`는 최종 성과를 기억 `detail`에 저장하지 않는다. 원문의 “최종 성과를 어디에도 저장하지 않는다”는 문장을 전역 저장 금지로 적용하면 기존 결과 화면·복구·비교 리플레이와 충돌한다. 통합 명세는 다음 경계를 따른다.

- **실행·평가 증거 저장소:** 입력/응답·체결·최종 결과·일별 지표를 owner와 split 권한으로 보호해 불변 보존한다. 완료 후 결과 UI·감사·재현·최종 검토만 필요한 범위에서 읽는다.
- **재사용되는 플레이북·교훈:** 최종 성과 수치를 저장하거나 증류 입력에 넣지 않는다. 개발 수치도 기존 기억 저장 정책보다 넓혀 저장하지 않는다. 최종 검토자는 동결 후의 해당 실행 결과만 별도 권한으로 읽으며 설계 수정 권한이 없다. 최종 등급·사유 역시 해당 평가 이전 결정의 입력에 유입되지 않도록 provenance와 availableAt/split으로 통제한다.
- **설계·라우팅·평가 중 의사결정 모델 입력:** 허용된 학습 측정과 현재 커서까지 실제 관측 가능한 시장 입력만 사용한다. 개발/최종 리플레이에서도 현재까지의 가격은 입력 가능하지만 이후 가격과 사후 평가 성과는 입력 불가다. 개발/최종 성과, 사후 기여도, 결과를 암시하는 결론도 제외한다. 숫자 가림만으로 충분하다고 간주하지 않는다.
- 허용된 학습 수치는 필요한 표본·불확실성과 제공할 수 있다. 교훈 증류 경로의 기존 숫자 가림은 유지한다. `99.9` 오염 테스트는 기억·설계 경계의 비노출을 검증하며 정당한 최종 결과 저장까지 금지하지 않는다.

### 2.3 구성요소와 하나의 운용 경로

`부품 → 북`, `단일 후보`, `기준 플레이북 A/B`는 서로 다른 정책 구성이다. 모두 하나의 라우터·운용 패키지·계좌 위험/실행 계층에 연결한다. `ct_playbook`의 연구 기억 행과 실행 가능한 플레이북 정책을 구분한다. 부품은 그 자체로 실전 등록 가능한 전략이 아니다.

이 통합 작업은 라우터·기준 플레이북·Binance 어댑터까지 포함한다. 원문 부품 지시서의 “아직 없으면 만들지 마라”는 별도 작업 간 중복 방지 조건을 폐기한다. 이미 있는 구현은 재사용하고 없는 부분은 이 작업에서 구현한다. 구현 중 연구·모의만 먼저 연결할 수 있으나 전체 완료로 보고하지 않는다. 검증·권한·데이터가 부족한 상품은 이유를 표시하고 실전 활성화를 차단한다.

북의 기본 프로파일은 **같은 instrument·같은 방향의 부품 2–8개, 북당 하나의 목표 포지션**이다. 전체 계좌의 동시 포지션·양방향/Hedge 지원을 금지하는 규칙이 아니다. 롱/숏 북은 지원 capability에 따라 별도 평가하고 라우터가 충돌을 처리한다. Hedge 양쪽 체결·수수료·funding을 임의 상쇄하지 않는다. 다른 상품·통화의 부품을 한 북으로 합치지 않는다.

## 3. 제품 UX — 이 구조로 구현할 것

전역 내비게이션이나 별도 실험 앱을 만들지 않는다. 기존 CT의 주식/코인 선택 아래에 **연구 / 검증 / 운용** 세 개의 하위 탭을 둔다. 시장 선택과 활성 작업 진행 상태는 세 탭에서 공유한다. 기존 폰트·색·`ui-*` 컴포넌트·차트·아이콘 체계를 유지한다. 새로운 디자인 라이브러리나 장식용 대시보드로 갈아엎지 않는다.

### 3.1 연구

- 기존 전략 생성, 자료 준비, 연구 진행, 후보/세션/근거, 플레이북·교훈을 유지한다.
- 코인은 `Binance · 상품 · 결제통화`를 실제 선택값에 맞게 표시한다. ‘Upbit 실행 미지원’은 신규 Binance 계약에서 제거하고 실제 capability 상태로 대체한다.
- 시작 폼의 기본 영역에는 기초자산, 상품, 허용 방향, 연구 기간·예산·위험 한도가 보인다. 레버리지·마진·포지션 모드·주문 조건은 상품 선택에 따라 펼쳐지는 ‘거래 설정’에 둔다.
- 상품별 무효 조합을 입력 순간 설명하고 서버도 재검증한다. 현물에는 레버리지/공매도 스위치를 보여주지 않는다. 선물에는 롱·숏·양방향과 해당 마진/포지션 모드를 제공한다. 옵션에는 CALL/PUT·만기·행사가·매수/매도·노출 설정을 제공한다.
- `직접 지정 / 에이전트 선택`을 지원한다. 에이전트 선택은 사용자가 허용한 상품·방향·레버리지 범위·총위험 한도 안에서만 가능하며, 선택 근거와 최종 설정을 후보 계약에 동결한다. 에이전트가 권한/위험 예산을 확대할 수 없다.
- 상품 목록을 하드코딩된 세 항목으로 끝내지 않는다. capability registry에서 가능한 구성과 상태를 읽는다. 서버가 모르는 값은 ‘자동’으로 넘어가지 않는다.
- 연구 결과의 주요 후속 동작은 `검증에서 비교`와 `판단 리플레이`다. 후보가 0개여도 기준 플레이북의 연구용 리플레이로 이동할 수 있다. 실패 후보를 실전 등록해 우회하지 않는다.
- 공개 데이터만 사용하는 연구는 API 키가 없어도 가능한 범위에서 작동한다. 실계좌 권한과 연구 데이터 준비 상태를 혼동하지 않는다.

### 3.2 검증 — 고정 비교 실험의 유일한 주 화면

상단은 `[비교 기록 선택] [새 비교]`와 시장/상품 표시다. 실험 목록은 날짜·기준 버전·변경점·평가 기간·상태·판정이 있는 간결한 표로 만든다.

`새 비교`는 팝업 연속 사용 대신 한 페이지의 짧은 폼으로 구성한다.

1. **기준 버전 / 변경 버전:** 등록 여부와 무관하게 불변 정책 버전 선택. 최초에는 기준 플레이북 두 개의 고정 라우터 버전을 기본으로 제공한다. 북도 불변 정책 버전으로 비교 대상에 포함한다.
2. **이번에 바꾼 것 하나:** 예: 차트 입력 추가, 상황 필터 추가, 기억 적용 범위 수정, 청산 방식 변경. 서버가 실제 config diff를 계산해 표시한다. 상품/레버리지/데이터/비용이 함께 달라졌으면 단일 기능 효과 비교로 표시하지 않고 ‘전체 구성 비교’로 구별한다.
3. **기간·비용·위험·예산:** 같은 snapshot, 평가일, 초기 자본, 계좌 위험 한도, 실행 비용 모델을 적용한다. 준비된 개발 검증 구간을 기본 선택하고 최종 구간 사용 여부를 명확히 보여준다. 데이터/권한 미충족이면 해당 해결 동작으로 연결한다.
4. **요약 후 `설정 고정하고 비교 시작`:** 모델/도구/메모리 버전, 변경점, 계산·모델 비용 상한, 평가 구간을 저장하고 실행한다. 운영 실거래 버튼과 시각적으로 구별한다.

비교 상세의 표시 순서:

```text
기준 vA → 변경 vB                 완료 / 진행 / 중단 / 실패
변경점: 기억의 적용 범위 수정      평가 202x-xx-xx … 202x-xx-xx

판정: 개선 확인 / 악화 확인 / 판단 보류 / 비교 불가
근거 한 문장: 비용 후 일평균 차이와 신뢰구간, 안전 기준 충족 여부

기준·변경·차이 표
  비용 후 일평균 / 전체 순수익 / 최대 낙폭 / 최악의 날
  수익·손실·무거래 일수 / 수익일 비율 / 일간 샤프 / 거래 수 / 비용 / 모델 호출 비용
  증거금 사용·최소 여유 / 강제청산·주문 실패 / 규칙 위반

동일 자본 기준 일별 누적 자산 그래프 + 기준 대비 일별 손익 차이
날짜별 표: 날짜 | 기준 | 변경 | 차이 | 거래 수 | 주요 판단 차이
행 클릭 → 같은 날짜·같은 시간의 판단 리플레이

접이식 ‘실험 조건과 판정 근거’
  계약 diff, 해시, 검정 방법, 노출 이력, 데이터/비용 가정, JSON 내보내기
```

- 가장 좋은 숫자에 무조건 초록색 ‘승리’를 붙이지 않는다. 통계·위험 조건을 통과하지 못하면 `판단 보류`다. 결과는 사용자에게 이해되는 한 문장과 수치로 설명한다.
- 진행 중에는 완료 일수·단계·비용·heartbeat만 우선 표시한다. 중간 성과로 실험을 멈추거나 변경하게 유도하는 승자 표시를 하지 않는다. 중단된 실험은 선택 편향 가능성이 있는 불완전 결과로 남긴다.
- 결과 페이지의 버튼은 `판단 리플레이`, `새 변경으로 비교`, 조건 충족 시 `전향 모의 후보로 등록`이다. 마지막 동작은 기존 최종 검증·등록 규칙을 우회하지 않는다. 비교 승리가 실거래 시작을 의미하지 않는다.
- 모델 실행·통계 재계산은 화면 열기/필터 변경/행 선택으로 발생시키지 않는다. 저장된 결과만 조회한다.
- URL로 탭·실험·날짜·결정 id를 복원하고 뒤로 가기·새로고침·브라우저 재시작 후 상태를 보존한다. 서버 owner 검사 없이 id만으로 결과를 열지 않는다.

### 3.3 판단 리플레이 — 검증 상세 안의 드릴다운

- 상단: 날짜, 시각, 재생/일시정지, 이전/다음 판단, 속도, 기준/변경 표시 토글.
- 중앙: 동일 instrument 비교에서는 두 버전이 같은 시간축을 공유하는 한 개의 가격 차트. 서로 다른 상품의 전체 구성 비교는 동일 시간 커서를 공유하는 분리 가격 패널을 사용하고 가격을 한 시계열로 합치지 않는다. 진입·청산·기준 레벨·위험선을 버전별로 구분한다. 좁은 화면에서는 기준/변경을 전환하되 시간 커서는 유지한다.
- 오른쪽 또는 모바일 아래: 현재 시각의 두 판단을 나란히 표시한다. `상황 → 선택 플레이북 → 행동 → 기다리는 조건 → 무효화 조건 → 위험/증거금 → 짧은 근거` 순서다.
- 하단: 결정 이벤트 목록, 실제/모의 체결과 비용. 누락 데이터·모델 시간 초과·관망 이유도 표시한다.
- 기본 `당시 정보` 모드는 커서 뒤 가격·성과·차트 스케일 정보를 숨긴다. `결과 보기`는 완료된 일자의 사후 복기 기능이며 당시 모델 입력과 명확히 구분한다.
- 차트 이미지와 입력 스냅샷을 동일 결정 id에서 확인할 수 있다. 비공개 추론 원문 저장을 요구하지 말고 짧은 결정 근거·관측값·구조화된 행동을 저장한다.

### 3.4 운용

- `그림자 관찰 / 전향 모의 / 실전`의 상태와 자금 사용 여부를 명확히 구별한다. 그림자 관찰은 주문 API에 접근할 수 없는 전용 경로다.
- 상품·방향·레버리지·마진/포지션 모드, 전략별/계좌 전체 노출, 담보·부채·펀딩/이자·청산 여유를 상품에 맞게 보여준다. 모두 지원하지 않는 값을 0으로 표시하지 않는다.
- 계좌 연결 상태는 public data / signed account / product permission / user stream / runner / orders enabled를 따로 표시한다. 키 값은 절대 보여주지 않는다.
- 실전 시작은 동결된 버전, 검증, 계좌 상태, 설정 변경 영향, 실제 실행기 연결을 확인한 명시적 시작 동작으로만 가능하다.

모든 화면에 로딩·빈 상태·권한 없음·데이터 미준비·stale·중단·재개·실패 상태, 키보드 포커스, 표 헤더, 색 외 상태 표시, 작은 화면 동작을 구현한다. 기존 CT의 실행 중 작업이 탭 이동 때문에 사라지거나 중복 시작되어서는 안 된다.

### 3.5 부품·북·버전 표시

- 연구 상세에 「부품」 표를 둔다: 봉·방향, 조건 요약, 이벤트/일수, 비용 전 기준선 대비 차이(비용 배수로도), p, 양수 월 비율, 학습·개발 판정, 중복 제거 여부.
- 「북」 카드에는 구성 부품, 결합 규칙과 k, 비용 후 일평균·수익일 비율·일간 샤프·최대 낙폭, 비용 비중, 기여도 막대, 게이트 사유와 비교/리플레이 동작을 둔다.
- 종료 표시: `현재 단계/계약 총단계 · 종료 사유 · 남은 예산`. 데이터 미준비·부품 0개·중복 제거 후 부족·북 탈락 상태를 구분한다. 모바일에서 페이지 전체 가로 넘침이 없도록 표를 카드/접기 방식으로 바꾼다.
- CT 상단의 적절한 위치에 작은 제품 에이전트 버전 `v0.0`을 표시한다. 이후 에이전트 동작 업데이트마다 릴리스 버전을 올리고 기록한다. 이는 `traderTools: 7`, `ct-book-1`, 제공자 모델 ID와 별개다. 현재 제품 버전과 과거 실행에 동결된 버전을 구분하고 실제 사용 모델 ID는 실행 상세에 보존한다.

## 4. 계약·데이터·회계의 공통 기반

기존 단일 long/spot 구조에 문자열 필드를 덧붙이는 것으로 끝내지 않는다. discriminated union 또는 동등한 타입으로 상품별 불가능한 조합을 차단하라.

계약에 필요한 축:

- `venue`, `network`, `product`, 실제 `instrumentId/symbol`, base/quote/settlement/collateral asset, 계약 승수·만기·옵션 right/strike(해당 시).
- 허용 방향과 후보 선택 방향, side와 positionSide, leverage 정책, marginMode, positionMode, 단일/다중 담보 모드, 동시 포지션/총 노출 한도.
- 원자료·판단·체결 시간 단위, 세션/당일 경계, 보유 상한, 주문·청산 규칙, 모델 시간 초과 정책.
- 계좌 위험 예산, 담보 예산, 비용·funding·차입·청산 모델과 버전, 데이터 snapshot, 메타데이터 관측 시점.
- policy/playbook/router/model/prompt/tools/lessons snapshot 버전과 해시, schema/engine/accounting 버전.

`Binance + BTCUSDT`만으로 식별하지 말 것. Spot BTCUSDT와 USDⓈ-M BTCUSDT는 가격·필터·회계·비용이 다른 상품이다. COIN-M과 옵션의 손익 통화를 USDT로 잘못 저장하지 않는다. 보고 통화로 환산할 때 사용한 당시 환율과 native 금액을 모두 보존한다.

기존 1분봉 Parquet/cache/catalog에 상품·price type(trade/mark/index)·단위·계약을 구분하는 키를 추가한다. 타임스탬프 단위, 거래소 봉 마감 포함 여부를 내부 `[start,end)` 규약으로 일관되게 정규화한다. 완성된 봉만 의사결정에 제공하고 누락을 가짜 가격으로 채우지 않는다. 필요한 상위봉은 해당 시점까지 완성된 하위봉으로 집계한다.

새 정책은 **판단 주기와 위험/체결 감시 주기를 분리**한다. 15분봉을 보고 판단하더라도 확보된 1분봉/호가로 손절·펀딩·청산을 처리할 수 있어야 한다. 같은 봉 내부 경로가 불명확하면 보수적 순서 또는 불확실 판정을 사용한다. 기존 계약의 봉 단위 체결 결과는 그대로 보존한다.

## 5. 하루 단위 의사결정 리플레이

### 5.1 상태와 이벤트

고정된 거래일/UTC 일자 전체를 시간순으로 재생한다. 하루 시작의 warmup은 이전 관측 자료만 사용하고 초기 상태/포지션 정책을 계약에 고정한다. 단타 기본은 당일 청산이며 코인 UTC 경계와 화면 KST를 구별한다. 상품 만기/거래중단/유지보수도 이벤트로 처리한다.

결정 이벤트에는 최소한 다음을 저장한다:

`decisionId`, run/arm/policy id, instrument, observedThrough, decidedAt, executionEligibleAt, inputSnapshot/hash, feature/level observations, setup state, selectedPlaybook, action, side/size intent, invalidation/expiry, proposed risk, server acceptance/rejection, short rationale, order intent/fill links, latency/usage/cost, outcome reference.

행동은 구조화된 제한 집합으로 만든다: 관망, 셋업 대기, 대기 취소, 롱/숏 진입 의도, 보유, 지원되는 위험 축소/청산 변경, 일부/전량 청산. `WAIT`와 `NO_TRADE`, 무효한 제안, 실행 실패를 구분한다. 현재 프로파일에서 허용하지 않은 액션은 서버가 거부한다.

판단 확정 뒤에만 다음 이벤트를 공개한다. 현재 결정에서 이후 high/low/종가, 최종 일봉, 미래 이벤트 라벨, 이후 수수료/펀딩, 검증 점수를 읽을 수 없어야 한다. 모델에 넘기는 차트 범위·축·레벨·기억·검색 결과도 이 시점 규칙을 지킨다. 과거 시점 재현 중 자유 웹 검색으로 이후 뉴스를 가져오지 않는다.

### 5.2 하나의 실행·위험 코드

순수한 `state + event + intent → next state + effects` 계층을 둬 리플레이/그림자/모의/실전이 동일한 룰과 위험 체크를 사용하게 한다. 실제 API 제출은 effect executor만 한다. 숫자 계산·주문 수량·증거금·잠금은 LLM에 위임하지 않는다.

기존 엔진의 고정 주문 방식을 사용한 정책은 같은 방식으로 재현한다. 새 주문 종류는 상품별 실행 모델을 갖춘 뒤 계약에서 허용한다. limit touch만으로 maker 전량체결을 가정하지 않는다. 호가/체결 자료가 없으면 queue/partial fill의 한계를 기록하고 보수적으로 모델링한다.

LLM은 사전 등록된 결정 일정/이벤트에서만 호출한다. 매 분 무제한 호출하거나 결과를 본 뒤 추가 질문하지 않는다. 지연은 실제 체결 가능 시점에 반영한다. 시간 초과·잘못된 출력은 미리 정한 관망 또는 위험 축소 정책을 적용한다. 기존 포지션 보호는 모델 응답을 기다리지 않는다.

### 5.3 재현·내구성·격리

- 결정 입력과 모델 응답을 불변 저장하고 재생 시 재호출하지 않는다. 동일 seed만으로 LLM 응답 재현을 보장한다고 쓰지 않는다.
- 실행 lease, append-only events, 스냅샷/체크포인트, 멱등 key로 재시작 시 결정/호출/주문을 중복 생성하지 않는다. 네트워크가 모호하게 실패한 모델 호출의 비용도 기존 정책에 맞게 처리한다.
- 비교 arm별 가상 계좌·포지션·상태·기억을 격리한다. 한 arm의 결정/성과가 다른 arm의 입력에 들어가지 않는다.
- 관망·손실·데이터 오류 날도 포함한다. 수익일만 추려서 평가하지 않는다. 등록 전략이 없어도 기준 플레이북 리플레이는 가능해야 한다.
- 신규 장시간 작업은 러너에서 진행하고 UI는 상태를 구독한다. 탭을 닫아도 저장된 작업이 이어지고 cancel/pause/resume이 실제로 동작한다.

## 6. 기준 플레이북 두 개와 라우터

두 플레이북을 **검증할 기준 가설**로 구현한다. 이름만 추가하거나 프롬프트에 사례 몇 개 넣는 것으로 끝내지 않는다. 고정된 기본 파라미터, 해시, 명확한 반증 조건, 사람이 읽을 수 있는 규칙, 완전한 상태 전이와 테스트를 제공한다. 기본값은 수익이 좋았던 값을 탐색해서 고른 척하지 않는다.

### A. 방향성 움직임 후 첫 되돌림과 재개

선택 종목 자체의 완성된 상위봉으로 방향 맥락을 판단하고, 선행 움직임 → 최초 되돌림 → 구조 유지 → 재개 트리거 → 관리 → 종료를 표현한다. 롱은 상승 후 눌림, 숏은 하락 후 반등의 구조다. 선행 구간의 기준 가격/범위, 움직임 종료 시점, 첫 되돌림 여부, 무효화 레벨을 상태에 저장한다. 사후 최고점·미확정 pivot을 즉시 아는 것처럼 쓰지 않는다.

### B. 횡보 범위 이탈 실패와 범위 복귀

이탈 전에 완성된 데이터로 고정한 범위 → 범위 이탈 → 정해진 시간 안 복귀 → 확인 → 진입/관리/종료를 표현한다. 하단 이탈 실패는 롱 가설, 상단 이탈 실패는 숏 가설이다. 범위를 미래 봉으로 다시 그려 진입을 정당화하지 않는다. 추세 중 역추세 진입을 구분하는 사전 정의 조건을 둔다.

기존 stage를 확장해 ‘같은 기준 가격 재시험’, ‘첫/두 번째 되돌림’, ‘발생 순서와 만료’를 명시적으로 저장한다. 필요에 맞춘 최소한의 관계 연산을 추가하고 임의 코드를 실행하는 DSL은 만들지 않는다. 롱 코드를 수익률 부호만 뒤집어 숏으로 복제하지 말고 가격 레벨, 손절, 갭, trailing, 주문 방향, 차입/증거금까지 일관되게 바꾼다.

기준 라우터는 관측 가능한 맥락으로 A/B/관망을 고른다. 확장 운용 패키지는 검증된 단일 후보와 북을 같은 인터페이스로 추가하며 라우터를 따로 만들지 않는다. 우선순위·동시 신호 충돌·재진입·노출 한도를 고정해 실험한다. 사후에 더 벌었을 플레이북을 선택하는 oracle 라우터는 기준선으로도 실제 성능과 혼동하지 않는다.

사용자는 검증된 플레이북 여러 개를 한 운용 패키지로 선택할 수 있어야 한다. 가장 최근 등록 전략 하나를 무조건 고르는 구조를 바꾼다. 양방향/Hedge와 동시 포지션은 상품·계정·위험 프로파일이 허용하는 범위에서 설정 가능하게 한다. 기존 최대 한 포지션은 구계약/기본 보수적 프로파일에 보존할 수 있지만 전체 시스템의 변경 불가 상수로 남기지 않는다.

## 7. 부품·북 연구와 더하기형 사전 측정

### 7.1 배경과 개념

다음은 원문 작성 에이전트가 `strategy_generation_runs`와 `ct_playbook`에서 관측했다고 남긴 기록이다. 현재 DB의 검증 완료 수치가 아니며 구현 시작 시 재조회한다.

#### 7.1.1 연구가 5/11단계에서 끝난다

최근 완료된 CT 연구 **10개(`a682e11b` … `190f80a2`)가 모두** 다음 상태로 끝났다.

- 단계: 5/11 「가설·규칙 설계」(`design`)
- 종료 사유: `설계자 판단: 비용 후 우위 미발견 · 통과 전략 없음 · 최종 기간 미개봉`
- 설계 세션 1개, 실험된 후보 0개, `screen_rule` 0회, 모델 턴 5–7회(한도 16)
- 사용 비용 $0.43–$0.97, 예산 $8. **예산의 90% 가까이를 쓰지 않은 채 끝났다.**

원인은 코드 한 줄이다. `submit_candidates`가 후보 0개로 오면 `ct-research-store.ts` 약 1735행의 `else if (!submission.candidates.length) done(...)`이 연구를 바로 끝낸다. `maxSessions: 3`인데 2·3번째 세션(`reflect`)은 열리지 않는다. 6–11단계(실험·수정·위험 검토·최종·최종 검토)는 한 번도 실행되지 않았다.

#### 7.1.2 약하지만 실제일 수 있는 우위가 들어갈 자리가 없다

연구 `190f80a2`(NVDA)의 `noEdgeReason`에 이렇게 적혀 있다: 가장 강한 조합(전일 종가 −1.95% 이하 + 당일 범위 하단 17.5%, 5분봉)이 82건/42일에서 총수익 평균 +0.06~+0.19%였고, 기준선보다 0.07~0.20%p 나았다. 하지만 왕복 비용 0.31%에 못 미쳐 기각했다.

지금 구조에서 우위는 **규칙 하나가 혼자 비용을 넘어야만** 살아남는다.
- 설계자 지시문: "do not submit a rule that already fails on training"
- 서버 `ctGate`: 후보 하나의 비용 후 순수익 > 0

그래서 기준선을 이기지만 비용은 못 넘는 신호는 전부 "기각"으로 플레이북에 쌓인다. 원문 관측 당시 `ct_playbook`에는 분봉 기준으로 `rejected_in_training` 120개, `development_failed` 12개가 있다(일봉 시드 제외). 이 중 일부는 **결합했을 때만** 비용을 넘을 수 있다. 현재 구조에는 이런 부품을 별도 보존·평가하여 북으로 결합하는 명시적 경로가 없다. 결합하면 실제 우위가 생긴다는 증거는 아니다.

#### 7.1.3 이미 잰 것 (기대치를 정하는 기준)

천장 측정(64+140+192개 조합)은 깊이 3 이하의 트리로 했다. 깊이 3 트리는 각 경로에서 최대 3개 조건을 AND로 겹치는 형태를 포함한다. 해당 탐색 범위에서는 표본 밖 후보가 없었지만, 모든 confluence 구조의 부재를 증명한 것은 아니다. **아직 시험하지 않은 것은 두 가지다.**
- **더하기형 결합**: 약한 신호 여러 개의 점수를 합산하는 방식. 얕은 트리는 이 구조를 잘 잡지 못한다.
- **북 단위 평가**: 여러 부품을 동시에 운용하면서 겹치는 신호가 중복 진입을 만들지 않는 실제 체결 비용을 반영하는 평가

이 작업은 이 두 가지를 연구 에이전트가 직접 다룰 수 있게 만드는 일이다. 천장 측정 결과는 "하지 말라"는 근거가 아니라 "무엇을 기대하면 안 되는지"의 기준이다.

| 용어 | 정의 | 판정 기준 |
|---|---|---|
| **부품(component)** | 기존 DSL 규칙 하나(진입 조건 + 보유 창). 단독 매매 전략이 아니라 **신호**다 | **비용 전** 총수익이 기준선(같은 시간대 구성의 무조건 진입)을 이기는가 |
| **북(book)** | 부품 2–8개와 사전에 정한 결합 규칙으로 만든 하나의 매매 전략 | 기존 `ctGate` 전부 + 비용 2배 + 1봉 지연. 거래 비용은 실제 체결에 부과하고 부품별 중복 계산을 하지 않는다. 보유 중 funding·이자 등은 별도 반영한다 |
| **단일 후보** | 지금의 후보. 계속 지원한다 | 지금과 같다 |

부품 판정은 비용 전 기준이지만, **비용을 무시하는 단계는 어디에도 없다.** 비용은 북의 실제 체결·보유·부채 장부에서 발생별로 계산하고, 통과 기준은 낮추지 않는다.

### 7.2 무료 사전 측정: 더하기형 결합의 천장 (모델 비용 $0, 가장 먼저)

1. **판정 기준을 측정 전에** `docs/research/ct-ceiling-YYYY-MM-DD-additive.md`(실제 사전 등록일 사용) 맨 앞에 등록하고 커밋하라(이전 천장 보고서와 같은 방식).
2. `scripts/research/ct-ceiling-additive.ts`를 만든다. 천장 측정과 같은 피처(`lib/ct-ceiling-features.ts`), 같은 라벨·비용 프로필·확장 창 워크포워드 4폴드(`walkForward`)를 쓰고, 모델만 **더하기형**으로 바꾼다.
   - (a) 피처별 단조 신호(학습 폴드에서 정한 사분위 방향)의 **동일 가중 부호 합**
   - (b) 고정 정규화 계수의 로지스틱 회귀(계수 하나, 폴드마다 튜닝 금지)
   - 점수 상위 구간(상위 5/10/20%)에서만 진입했을 때, 표본 밖 **비용 후 일평균**과 **비용 전 총수익 − 기준선**을 낸다.
3. 대상: BTC·ETH·SOL(Binance 1분봉) × 1·3년, NVDA 전체 × 보유 상한 4개. 비용은 현재 계약과 2배.
4. **결과는 구현을 막지 않는다.** 결과는 §13.2 실행의 기대치로 보고서와 `docs/ct.md`에 기록한다. 후보가 없으면 "더하기형도 없음"을 그대로 쓴다.
5. 반복 검정 수(조합 × 폴드 × 모델)를 보고서에 적는다.

사전 등록에는 상품·방향·instrument·데이터 snapshot, 4개 보유 상한의 실제 값, 라벨·비용 버전, 피처 방향/정규화·결측 처리·로지스틱 목표·고정 계수, 상위 비율 임계값의 학습 전용 산출, purge/embargo, 성공/기각/측정 불가 기준을 적는다. 기존 비교 기준용 Binance Spot BTC/ETH/SOL과 NVDA를 먼저 고정하고 새 상품 실험은 별도 manifest로 구분한다. 부족한 3년 자료를 다른 거래소로 채우거나 짧은 기간을 3년으로 표시하지 않는다. 무료는 모델 비용 $0이라는 뜻이며 계산·데이터 비용도 기록한다. 사전 등록 커밋 뒤 측정하고 결과 커밋을 분리한다. 기본 측정을 먼저 수행하되 데이터가 막힌 경우 사유를 남기고 독립적인 구현은 진행한다. 로지스틱 회귀는 천장 탐색용이며 운용 북의 학습 가중치 금지와 혼동하지 않는다.


### 7.3 5/11단계 조기 종료 수정

새 정책에서 설계 세션 종료 후의 분기를 다음처럼 바꾼다.

| 제출 결과 | 지금 | 새 정책 |
|---|---|---|
| 새로 수락된 후보 ≥ 1 | `experiment` | 후보 실험; 함께 낸 부품도 실험 큐에서 처리 |
| 새로 수락된 후보 0, 부품 ≥ 1 | — | `experiment`(부품 판정) → `book` |
| 후보 0, 부품 0, **첫 번째 연속** | 즉시 `done` | `reflect` 세션을 연다(아래 과제) |
| 후보 0, 부품 0, **두 번째 연속** | — | `done("두 세션 연속 후보·부품 없음 …")` |

- `reflect` 세션 과제: 이전 세션이 쓰지 않은 커버리지 칸(`ctCoverage`의 안 쓰인 칸), 아직 `dead`가 아닌 계열, 그리고 **"기준선은 이기지만 비용은 못 넘은 측정"을 부품으로 다시 보는 일**을 명시한다. 과제 문장에는 직전 세션의 `noEdgeReason`과 기각 가설 요약을 넣되 §2.2의 시점·split·숫자/결론 차단 규칙을 지킨다.
- 서버 확인: 후보 0·부품 0 세션 다음의 `reflect` 세션에서 다시 0/0을 제출하려면, 그 세션에서 **이 실행의 장부에 없던 새 가설 서명을 2개 이상** 측정했어야 한다. 아니면 제출을 오류로 돌려보낸다(세션 안에서 고칠 수 있게). 단, 마지막 턴 통지(`finalNotice`) 뒤와 예산 부족 시에는 받아들인다.
- 종료 사유에는 **어느 단계에서, 왜, 예산을 얼마 남기고** 끝났는지를 쓴다. 예: `7/12 실패 진단·수정 · 두 세션 연속 후보·부품 없음 · 예산 $6.80 남음`.
- 기존 시간·계산·예산·세션 한도 종료는 그대로 둔다. 예산 여유 검사(`headroom < turnReserve * 3`)도 그대로 둔다.

제출 개수·중복 제거 후 수락 개수·게이트 통과 개수를 별도로 기록한다. 중복만 낸 제출을 유효 후보로 세어 순환하지 않는다. 유효 후보/부품 제출이 있으면 연속 0/0 카운터를 초기화한다. 첫 0/0도 예산·시간·턴·세션 한도로 재설계가 불가능하면 해당 한도 사유로 종료할 수 있다. 부품을 충분히 평가하고도 북이 없으면 기존 한도 안에서 reflect하거나 종료한다. 두 번째 0/0의 새 가설 2개 요구가 무한 재시도를 만들지 않게 finalNotice·예산 예외를 적용한다.


### 7.4 부품 제출과 서버 판정

- `submit_candidates`(새 정책 스키마)에 `components` 배열을 더한다. 항목마다 다음을 받는다.
  - `spec`: 기존 DSL, 진입과 보유 창
  - `hypothesis`, 근거 `mapping`: 기존과 같은 근거 인용 규칙
  - 봉 주기
  - `whyNotAlone`: 혼자 비용을 못 넘는 이유
- 부품은 연구 실행 전체에서 수락된 고유 부품 최대 8개다. 단일 후보 1–3개와 함께 제출해도 된다. 단일 후보의 기존 실행 전체 한도도 유지하며 부품/북/단일 후보별 한도와 전체 계산·예산 상한을 별도로 관리한다.
- **학습 구간 부품 게이트**(서버가 계산한다. 기본값을 사전 등록하고, 결과를 본 뒤 바꾸지 마라):
  - 이벤트 ≥ 60, 고유 일수 ≥ 30
  - 비용 전 총수익 − 기준선 > 0. **일 단위 군집 부트스트랩** 단측 p ≤ 0.05(이벤트가 겹치므로 이벤트 단위 t검정을 쓰지 마라)
  - 양수인 월이 60% 이상, 상위 5일이 총이익의 40% 이하
- **개발 구간 확인**: 같은 부호이고 총수익 − 기준선 > 0, 이벤트 ≥ 20. 실패한 부품은 `component_dev_failed`로 기록하고 북에 넣지 않는다.
- **중복 제거**: 두 부품의 진입 이벤트가 70% 넘게 겹치면 p가 더 작은 쪽만 남긴다.
- 부품 하나는 장부에서 검정 1회로 센다(`ctTestSignature` 규칙 그대로). 부품이라고 장부를 피하게 하지 마라.

기준선은 같은 instrument·방향·판단 봉·보유 창·시간대 구성의 무조건 진입이며, 비용 전 차이는 이벤트당 수익률 평균 차이로 정의한다. 표본 수가 다른 원시 수익 합계를 빼지 않는다. 학습/개발 각각 같은 산식으로 계산한다. 월별 양수 비율은 유효 이벤트가 있는 월의 기준선 대비 차이로 계산하고, 집중도는 일별 양의 비용 전 PnL 합 중 상위 5일의 비중으로 고정한다. 분모가 0이면 통과하지 못한다. 월 수·빈 월 처리·bootstrap 재표집/귀무가설/seed/반복 수·추가 다중검정 보정 방식을 결과 전에 고정한다. 단측 p ≤ 0.05는 탐색 게이트이며 최종 우위의 증거가 아니다.

서로 다른 봉의 이벤트도 공통 1분 타임라인의 실제 실행 가능 진입 시각으로 정규화한다. 중복 비율은 `교집합 이벤트 수 / min(두 이벤트 수)`로 사전 고정하고 70% **초과**면 학습 p가 더 작은 쪽만 남긴다. 동률은 학습 전 고정한 복잡도·서명 순서로 결정한다. 중복 제거에 개발 결과를 쓰지 않는다.

북 구성·규칙·k·청산·학습 순위는 **학습 통과 부품으로 개발을 열기 전에** 최대 3개까지 동결한다. 이후 부품 개발 실패가 나면 해당 부품을 담은 북은 탈락시킨다. 남은 부품으로 개발 성과를 보고 새 북을 조합하거나 k를 다시 맞추지 않는다. 부품 개발 확인은 북 실험 자격의 게이트이며 최적화 입력이 아니다.


### 7.5 북 엔진 (`lib/ct-book.ts`, 엔진 `ct-book-1`)

- **같은 함수가 연구·모의·실전에서 돈다**(「실행 명세와 동일 코드 계약」). 순수 함수 `ctBookStep(state, event, components, rule)` 형태로 만들고, 기존 `ct-engine.ts`의 봉 순회·비용 모델·1봉 지연·당일 청산·주식 세션 처리를 재사용하라. 따로 복제하지 마라.
- **점수**: 각 부품은 신호 발생 후 자기 보유 창 동안 활성(+1)이다. 북 점수 = 활성 부품 수.
- **결합 규칙**은 사전 정의된 두 가지만 허용한다(학습 가중치 금지).
  - `vote`: 점수 ≥ k일 때 북 계약의 고정 방향으로 진입. k ∈ {1, 2, ⌈n/2⌉} 중 **학습 구간에서만** 고른다.
  - `confluence`: 지정한 부품 2개가 동시에 활성일 때만 북 계약의 고정 방향으로 진입.
- **포지션**은 §2.3에 따라 북당 하나의 목표 포지션이다. 겹치는 같은 방향 부품 신호가 추가 주문을 만들지 않으므로 비용을 중복 부과하지 않는다. 실제 체결·부분체결에는 상품 수수료를 부과하며 funding·이자·차입·청산 비용도 별도로 실제 발생대로 계산한다. 서로 다른 북/전략의 실제 주문을 가상 상쇄하여 비용을 없애지 않는다.
- **청산**: vote는 점수가 k 밑으로 내려가면, confluence는 지정한 쌍의 동시 활성이 해제되면 청산한다. 북 수준 손절(ATR 또는 %), 최대 보유, 당일 경계 청산은 계약을 따른다. 청산 구조 선택도 학습 구간에서만 한다.
- **방향**: 구계약은 롱 전용 그대로 보존한다. 새 북은 상품별 데이터·회계·실행 검증을 통과한 capability에서 롱 또는 숏을 지원한다. 현물 매도는 숏 진입이 아니며 옵션 CALL/PUT·계약 매수/매도·기초자산 관점을 구분한다. 지원 불충분한 조합은 명시적으로 차단한다.
- **판정**: 북 결과에 기존 `ctGate`를 **그대로** 적용한다(최소 거래 20, 비용 후 순수익 > 0, 일평균 > 0, 낙폭 15%, 준수 100%, 시기 집중). 비용 2배 스트레스와 1봉 지연 스트레스도 적용한다. 개발 구간은 통과·탈락 판정에만 쓴다.
- **보고 항목**: 부품별 기여도(빼기 하나 분석, 개발 구간), 비용이 총이익에서 차지하는 비율, 수익일 비율, 일간 샤프, 최대 낙폭. 부품 하나가 순이익의 70% 넘게 차지하면 "사실상 단일 전략"으로 표시한다(게이트는 아님).
- (북 구성, 결합 규칙, k, 청산 구조)는 장부에서 하나의 가설 서명이다. 북 후보는 연구당 최대 3개다.
- 통과한 북은 `risk_review` → `final` → `evidence_review`로 간다. 단일 연구에서는 단일 후보와 북을 통틀어 학습에서 정한 우선순위의 개발 통과 정책 하나만 최종에 보낸다. `afterQueue`의 개발 성과 정렬은 새 정책에서 사용하지 않는다. A/B 최종은 §9.2의 별도 사전 등록 묶음 한 번으로만 가능하며 같은 기간을 이중 소비하지 않는다.

서로 다른 판단 봉의 부품은 같은 1분 이벤트 시계에서 갱신한다. 각 부품은 자기 완성 봉에서만 신호를 확정하며 자기 봉 수/보유 창을 실제 만료 시각으로 환산한다. 같은 부품의 반복 신호를 중복 가산하지 않는다. 기본 활성 창은 최초 신호부터 만료까지 고정하고 만료 전 반복 신호로 연장하지 않는다. 동일 시각에는 관측 완료 → 부품 활성/만료 → 북 목표 의도 → 공통 위험 검사 → 실행 가능 체결 순서를 고정한다. 결정 봉 종가 체결로 미래를 앞당기지 않는다. 1봉 지연 스트레스의 기준 봉을 북 계약에 하나로 고정하여 mixed timeframe에서도 같은 의미를 사용한다.

운용 북은 2–8개이며 1개짜리 `vote k=1`은 엔진 동등성 테스트 전용이다. 기여도 빼기 하나 분석은 동결된 개발 평가 후 진단으로만 계산하고 그 결과로 북을 바꾸지 않는다. 계산 예산·변형 횟수·노출을 기록한다. 순이익/총이익이 0 이하이면 기여율·비용 비율을 억지로 유한값으로 만들지 말고 정의 불가와 절대 금액을 표시한다. 실제 체결의 소유권·비용 배분은 공통 장부가 담당한다.


### 7.6 단계 표시

- 새 정책 계약의 단계 목록에 `book`(「부품 결합·북 실험」)을 `reflect` 다음에 넣는다(총 12단계). 이전 계약의 진행 화면은 11단계 그대로 보여야 한다. 단계 목록을 계약 버전에서 얻도록 바꿔라.
- `book` 단계 힌트: "통과한 부품을 사전 정의 규칙으로 결합해 비용 후 성과를 실험합니다".

12단계 목록의 표시 순서는 `data → sources → read → approaches → design → experiment → reflect → book → risk_review → final → evidence_review → done`이다. 이는 상태 전이를 강제하는 선형 파이프라인이 아니다. 부품이 바로 준비되면 `experiment → book`으로 reflect를 건너뛸 수 있고, 단일 후보만 있으면 book을 건너뛴다. 실제 방문·재방문·건너뜀을 표시하며 단계를 채우기 위해 모델을 호출하지 않는다.


### 7.7 설계자 지시문 (새 정책 `CT_DESIGNER_SYSTEM_BOOK`)

6의 지시문 원본은 바이트 그대로 보존하고 별도 7 지시문을 만든다. 부품·북과 통합 상품/방향·기억 경계에 필요한 부분만 명시적으로 바꾸고 차이를 `docs/ct.md`에 적는다. 구버전 문자열을 전역 치환하지 않는다.

- §0의 원칙을 영어 지시문으로 옮긴다. 요지는 다음과 같다. A measurement that beats its time-of-day baseline before costs but not the round-trip cost is a component, not a rejection; register it with `whyNotAlone`. Transaction costs follow the book's actual fills, without duplication across component signals; funding, interest, and other product costs still accrue. Do not stop because no single rule clears the cost. An empty first session must enter reflection when limits allow. Respect the two-empty-session rule and all budget, time, and session limits; report the coverage cells tried and the exact stop reason.
- `noEdgeReason`에는 부품 후보를 찾았는지와 왜 부품 게이트를 못 넘을 것으로 봤는지를 반드시 적게 한다.
- 다중검정 경고는 그대로 둔다. 부품도 검정으로 센다는 사실을 지시문에 명시하라(경고를 없애서 우연을 늘리는 방향으로 고치지 마라).

## 8. 적용 범위가 명확한 기억과 복기

새 계약에서는 교훈을 `(시장, 기법 계열)`의 전역 최신 한 문장으로 적용하는 경로를 scope 기반으로 교체한다. 구계약의 지시문·기억 snapshot은 보존한다.

새 기억은 venue/product/instrument 또는 검증된 종목군, 방향, 판단/체결 주기, 상황 정의와 버전, setup 구조, 비용/위험/레버리지/마진 프로파일, 데이터 기간, evidence grade, 관측/기록/사용 가능 시각, 참조 run/trade/decision을 가진다. 알 수 없는 차원은 unknown이며 wildcard로 간주하지 않는다.

판정은 최소 `해당 조건에서 기각`, `표본 부족`, `표현·데이터 부족`, `검증 중`, `재현됨`, `최근 약화`를 구별한다. 단순 실패 건수만으로 기법 전체를 dead 처리하지 않는다. 기존 dead 교훈은 출처를 보존한 legacy 제한 근거로 옮기며 새 상품/방향/주기에 자동 적용하지 않는다.

새 후보에 기억을 적용할 때 `일치하는 범위 / 다른 범위 / 이번에 참고한 이유`를 남긴다. 유사 사례는 가설 힌트이며 통과/기각의 자동 근거가 아니다. 정보가 새로 생기지 않은 재실험과 새 구조/방향/상품 실험을 구분한다. 그렇다고 버전명·brief·날짜 한 칸 변경이 새로운 독립 표본을 만든다고 간주하지 않는다.

복기는 진입, 플레이북 선택, 청산, 실행 비용, 데이터/시스템 오류를 구분한다. ‘손실 거래가 한때 +1R’이라는 사실만으로 청산 오류라고 확정하지 않는다. 같은 진입에 실행 가능한 대안 청산을 적용한 반사실 결과, 이전 위험 증가 여부와 대안 비용을 함께 기록한다. 누락된 기회도 당시 조건으로 발견 가능한 것인지 분리한다.

성과 수치를 모두 제거하는 대신, 읽는 시점과 허용 split을 서버가 검증해서 허용된 근거 수치·표본·불확실성을 제공한다. 결과 등급·문장도 평가 구간 정보일 수 있으므로 숫자 마스킹만으로 누출을 막았다고 주장하지 않는다. 평가에서 얻은 교훈은 그 평가 이전 결정으로 되돌아갈 수 없다.

비교 실험 시작 시 기억 snapshot을 동결한다. 평가 도중에는 업데이트하지 않고 종료 후 다음 버전의 연구에만 반영한다. `diagnose_trades`를 확장/재사용해 거래가 있는 실험에는 실제 복기 결과를 남긴다. 거래가 없으면 원인을 정량화하고 가짜 복기를 만들지 않는다.

### 8.1 부품·북 기억과 검토자


- 플레이북 등급에 `component_passed`, `component_dev_failed`, `book_development_failed`, `book_passed_final`, `book_failed_final`을 더한다.
- 계열·교훈·커버리지(`ct-families`, `ct-lessons`)가 새 등급을 읽게 한다. `dead` 판정 규칙에서는 **해당 scope에서 `component_passed` 근거가 있는 계열을 단순 실패 건수로 `dead` 처리하지 않는다.** 다른 scope 전체에 영구 생존 판정을 주지도 않는다.
- 다른 실행에서 통과한 부품은 구조(피처·봉·방향)만 근거로 재사용할 수 있다. 수치는 기존 누출 규칙을 따르며, 이번 실행의 학습 구간에서 **다시 측정**해야 하고 장부에 센다.
- 위험·증거 검토자 입력에 다음을 더한다: 북 구성, 부품 간 이벤트 겹침 행렬, 빼기 하나 기여도, 비용 비중, 누적 검정 수. 지시에 "이 북은 우연히 좋아 보이는 부품들의 조합인가, 하나의 부품이 전부인가"를 넣는다.

`component_passed`는 학습·개발 게이트를 모두 통과한 부품에만 쓴다. 개발 전에는 pending 상태로 구분한다. 학습 실패는 실패 사유·split과 함께 기록하며 기존 등급을 재해석하지 않는다. 검토자의 빼기 하나/겹침/개발 결과는 설계 컨텍스트에 역류하지 않는다.

## 9. 고정 비교 실험과 판정 서버

### 9.1 사전 등록

experiment에는 가설, 기준/변경의 불변 버전과 실제 diff, primary metric, 최소 개선 폭, 동일 데이터/거래일, 초기 자본, 위험/비용/체결 모델, 모델·프롬프트·기억 버전, seed, 표본/검정 계획, 예산, 중단 규칙, 연구/개발/최종 구간, 노출 장부를 저장한다. 실행 후 변경하지 못한다.

기본 primary metric은 **같은 평가일 전체의 비용 후 일평균 수익률 차이(변경−기준)**다. 무거래일도 0으로 포함한다. 수익률 분모는 계좌 자본으로 통일한다. 포지션 명목 대비 수익률은 별도 표시한다. 거래 비용과 모델/API 연구비를 분리해서 보고하고 운영 비용을 포함한 손익도 계산 가능한 구조로 둔다.

레버리지·상품이 달라지는 실험은 `전체 구성 비교`다. 동일 위험 예산을 유지하고 자산/명목/증거금 기준 성과를 함께 보고한다. 더 높은 레버리지로 얻은 수익 차이를 차트 판독 개선으로 명명하지 않는다.

### 9.2 데이터 노출과 시간순 검증

- 개발 중 시간순 walk-forward를 사용하고 경계에 걸친 포지션·라벨·lookahead를 purge한다. purge/embargo 길이를 전략의 최대 미래 사용 범위에서 정한다.
- 최종은 후보/기억/라우터가 동결된 뒤 한 번만 사용한다. A/B 최종을 요청했다면 **하나의 사전 등록 평가 묶음**으로 동결된 기준·변경을 동일 최종 구간에서 공동 평가한다. 단일 연구에서 먼저 소비한 최종을 A/B로 다시 열 수 없으며, 평가 묶음 ID와 두 arm 해시를 원자적으로 예약한다. 단일 연구는 동결 정책 하나, 비교 실험은 사전 등록된 묶음 하나가 소비 단위다. arm마다 최종 노출을 독립 연구처럼 두 번 여는 방식은 금지한다.
- 같은 평가 결과로 새 후보를 골랐다면 그 구간은 개발에 노출된 것이다. 실험/버전/product 이름 변경으로 최종을 다시 깨끗하다고 표시하지 않는다. 같은 기초자산의 겹치는 기간과 과거 기억 노출도 기록한다.
- 기존에 이미 본 역사 자료는 탐색/개발로 표시하고, 실제 미노출 구간 또는 이후에 쌓이는 전향 자료로 최종 판단을 진행한다. 데이터가 없으면 ‘평가 대기’가 정상이며 기준을 낮추지 않는다.

### 9.3 통계와 결과 상태

- 거래를 독립 표본으로 세지 말고 동일 일자의 A/B 일별 차이를 사용한다. 연속일 의존성을 고려하는 block bootstrap 등 적절한 방법을 구현하고, block 길이·반복 수·seed·신뢰수준을 사전 저장한다. bootstrap은 최소 수천 회를 기본으로 하고 방법 선택 이유를 문서화한다.
- `개선 확인`: 후보의 절대 비용 후 성과·기존 위험/스트레스 기준을 충족하고, primary 차이의 신뢰구간 하한이 사전 정한 최소 개선 폭을 넘으며 표본/다중비교 조건을 충족한 경우.
- `악화 확인`: 비교 차이의 불확실성 범위가 사전 악화 기준을 만족하는 경우. `판단 보류`: 표본 부족, 신뢰구간이 0/최소 개선 폭을 포함, 위험 기준 미달, 또는 재현성 부족. `비교 불가`: 데이터/실행/계약 불일치.
- 최소 거래 20건 같은 기존 조건은 운영상 하한이지 통계적 확신의 증거가 아니다. 여러 독립 일자와 효과 크기·불확실성을 함께 본다. 새 판정의 최소 표본 기준은 결과를 보기 전에 고정한다.
- 여러 변경 버전을 같은 평가 묶음에서 비교하면 Holm 등 명시한 보정을 서버에서 계산한다. 무제한 적응적 재탐색을 단순 p값 보정으로 해결했다고 주장하지 않는다.
- 검정 장부는 실제 실행한 threshold·청산·방향·상품·레버리지 변형 수와 구조적으로 다른 아이디어 수를 별도로 보존한다. 둘을 모두 ‘독립 검정 수’라고 부르지 않는다.
- 비용 2배, 실제 실행 지연, 손절 민감도, funding/차입/스프레드 악화, 청산 위험을 분석한다. 비용 스트레스에서 음수 funding(수입)을 두 배로 늘려 성과가 좋아지게 하지 않는다. 데이터에 없는 스트레스 항목은 측정 불가로 표시한다.
- LLM 검토자는 측정 결과를 해석할 수 있지만 서버의 통계/실행/위험 실패를 승인으로 덮어쓸 수 없다.

전체 구성 비교에서 상품이 다르면 “같은 snapshot”은 같은 기간과 관측 cutoff를 가진 **상품별 실제 자료를 함께 동결한 데이터 묶음**을 뜻한다. Spot 자료를 선물/옵션 대신 쓰지 않는다. 비용 모델은 같은 산정 원칙·stress 배수를 적용하되 상품별 실제 수수료·funding·이자 구조를 보존한다. 두 구성의 비용 숫자를 억지로 같게 만들지 않는다.

## 10. Binance 상품·방향·레버리지·계좌 구현

`docs/binance-api.md`의 공식 자료를 읽고 최신 스펙을 확인한다. API 전체를 무작정 노출하지 말고 CT에 필요한 typed 어댑터와 capability를 구현한다. SDK 사용 시 실제 버전·지원 endpoint·서명 방식·숫자 처리·오류 보존을 확인한다.

### 10.1 상품과 capability

대상은 Spot, Cross/Isolated Margin, USDⓈ-M·COIN-M의 지원 무기한/만기 계약, 계정에서 지원하는 Options와 Portfolio Margin/Pro다. PM은 상품 이름과 동일시하지 말고 계좌 위험 모드로 모델링한다. 옵션 계약의 존재 여부와 매도 자격은 거래소/계좌에서 확인한다.

각 기능에 `exchangeSupported`, `accountPermission`, `dataReady`, `engineValidated`, `liveReady`, `checkedAt`, `reason`을 구분한다. unknown을 false나 true로 바꾸지 않는다. 권한이 없어도 구현·테스트 가능한 어댑터/회계/화면을 끝내고, 실제 계좌 검증 미완료를 따로 남긴다. ‘구현 안 함’을 ‘거래소 미지원’이라고 표시하지 않는다.

레버리지 최대값은 종목·계좌·명목금액 bracket으로 조회하고 사용자 위험 상한과 교집합을 취한다. 125 같은 고정 최대값을 박지 않는다. 에이전트는 허용 범위 안에서만 제안하며, 레버리지 선택과 포지션 손실 예산은 별도다. 수익률에 배수를 곱하는 레버리지 백테스트는 금지한다.

### 10.2 연구 데이터와 계좌 회계

- **Spot:** 자산·현금·수수료 자산, 최소 주문과 수량 정밀도.
- **Margin:** 담보·차입·상환·미상환 원금·이자·차입 가능 재고, cross/isolated 위험. 역사적 차입 가능성/이자 자료가 없으면 가정을 표시하고 보수적으로 검증하거나 정식 평가를 보류한다.
- **USDⓈ-M:** 실제 선물 가격, mark/index, 유지증거금 구간, margin balance, realized/unrealized PnL, funding의 실제 정산 시각·부호, 수수료, 청산/ADL·만기 처리.
- **COIN-M:** contract size, 계약 수량, inverse PnL, 코인 담보 가치 변동, 코인 결제·funding·수수료·청산을 계산한다.
- **Options:** 실제 옵션 가격/호가/계약 chain, premium, multiplier, 만기/행사/정산, 매수/매도 증거금·노출. 현물 봉에 레버리지를 곱해 옵션 성과를 만들지 않는다. 위험 보조 지표의 추정 모델·시점도 기록한다.
- **PM/Pro 및 multi-asset:** 계좌 전체 위험·담보 haircut·부채·타 포지션을 평가해야 한다. isolated position 계산기로 대체하지 않는다. 재현에 필요한 데이터/모델이 부족하면 해당 모드의 검증 통과와 실전 활성화를 보류하되 제약을 구체적으로 남긴다.

청산은 거래 가격이 아닌 해당 상품의 기준 가격·유지증거금 규칙을 반영한다. intrabar mark 경로/과거 bracket이 부족하면 불확실성을 명시하고 과거 규칙을 현재와 같았다고 주장하지 않는다. 손절과 청산이 같은 봉에서 가능하면 임의로 손절이 먼저였다고 가정하지 않는다. 손절은 손실 상한 보장이 아니며 갭/슬리피지와 초과 손실을 회계에 반영한다.

### 10.3 주문·모드·대사

- 일반/조건부/후행/주문목록, 지원 TIF, maker/post-only, reduce-only, 부분청산을 상품별 기능에 맞게 제공한다. 사용하지 못하는 조합은 이유와 함께 차단한다.
- 주문 의도를 DB에 먼저 기록하고 stable client id, account+product+instrument+positionSide 소유권으로 추적한다. 같은 symbol의 LONG/SHORT를 섞지 않는다.
- 응답 타임아웃·5xx 불명확 상태는 REST/계좌 스트림으로 대사하기 전 재주문하지 않는다. 연결 재시작·이벤트 중복/역순·부분체결·수수료 자산·조건부 주문에서 생성한 실제 주문을 처리한다.
- Hedge에서는 반대 방향 주문이 기존 포지션 청산인지 새 반대 포지션인지 공식 semantics로 검증한다. 허용되지 않는 reduceOnly/closePosition 조합을 만들지 않는다.
- 실제 leverage/margin/position/multi-asset 설정 변경은 계좌에 영향을 준다. 현재 포지션/미체결/다른 전략과 충돌하면 fail closed 하고 수동 해결 이유를 표시한다. 연구 폼 선택/리플레이/화면 진입으로 계좌 설정을 바꾸지 않는다.
- 종료 시 신규 진입 금지 → CT 소유 미체결 처리 → CT 소유 포지션/부채에 맞는 정리 → 체결/상환 확인 → 종료를 수행한다. 계좌의 타 전략 보유를 일괄 취소/청산하지 않는다. 미확인 청산은 ‘종료 완료’로 표시하지 않는다.
- 계좌 공통 위험 엔진이 총노출·증거금·최악 손실·일손실·낙폭·상관/상쇄 가정을 관리한다. 헤지 두 다리의 명목이 상쇄된다고 위험이 0인 것으로 처리하지 않는다.

### 10.4 에이전트 도구 경계

연구 모델에는 과거 snapshot의 시세·메타데이터·비용·계약 조건·포지션 시뮬레이션·리플레이·복기·비교 도구를 제공한다. 서명 키나 임의 HTTP/서명/실주문 함수를 주지 않는다.

실시간 판단 모델은 읽기 snapshot을 받고 제한된 주문 **의도**만 제출한다. 서버가 계좌 권한·프로파일·정밀도·가격/수량·현재 노출·승인 해시·kill switch·미확인 주문을 검사한 후 브로커 어댑터를 호출한다. stop/take-profit 보호는 모델 장애와 독립적으로 동작한다.

외부 웹 자료·모델 출력이 API host, secrets, risk config, approval state를 바꾸지 못하게 한다. 개인 키는 모델 프롬프트·일지·트레이스·스크린샷·프런트 번들에 포함하지 않는다.

### 10.5 Binance 통일과 기존 기록

새 코인 요청은 모든 경로에서 Binance로 생성된다. UI의 일부 문구만 바꾸고 bars/quote/paper/commission/order가 Upbit를 호출하는 상태를 남기지 않는다. 신규 Binance 경로가 Upbit에 호출하지 않는 테스트를 추가한다.

기존 Upbit 계약·포지션·장부는 원래 거래소로 읽고 필요 시 원래 어댑터로 정리할 수 있게 보존한다. Upbit 데이터/교훈/수수료를 Binance 실측으로 재라벨링하지 않는다. 같은 거래소 안에서도 Spot 자료를 선물/옵션 체결 자료로 대신하지 않는다.

기존 키의 보관 경계는 로컬 실행기다. Sites의 장기 연결/로컬 SQLite·Parquet 접근 한계를 고려해 기존 인증된 bridge와 러너 경계를 확장한다. 브라우저→인증된 제어 API→소유자/실행기 확인→로컬 브로커 경로를 검증한다. 개인 키를 Sites 소스에 번들링하거나 UI에 넘기지 않는다. 별도 호스팅 비밀값이 꼭 필요할 경우 기존 Sites 프로젝트의 secret 도구를 사용한다.

## 11. 구현 순서와 문서 산출물

1. 현재 코드·DB·테스트 기준선·데이터·권한을 audit하고, 현재 커밋과 상품 capability 표·의존성·멱등 마이그레이션/백업/rollback 계획을 남긴다.
2. §7.2의 더하기형 측정을 사전 등록·별도 커밋하고 기본 측정을 실행한다. 결과는 구현 여부를 결정하는 게이트가 아니다.
3. ≤6의 해시·동작을 고정하고 정책 7, 상품 identity·schema/accounting 버전, Binance public/signed read와 legacy 경계를 만든다.
4. 하나의 순수 상태/위험/체결 엔진, 상품 회계, 하루 리플레이와 내구성 장부를 만든다. 북은 이 엔진에 의도를 전달하며 별도 체결 엔진을 복제하지 않는다.
5. 부품 제출·학습 게이트·학습 전용 북 동결·개발 게이트·0/0 재설계 분기를 연결하고, 기준 플레이북 A/B·하나의 라우터·운용 패키지·scoped memory·복기를 연결한다.
6. 비교 manifest·노출 장부·paired 통계·판정·arm 격리와 연구/검증/운용 UI·12단계·부품/북·공유 리플레이·버전 표시를 연결한다.
7. 상품별 브로커·스트림·그림자·모의·실전 게이트, 설정 충돌·중단·복구·소유권 대사를 연결한다. 신규 실전 잠금을 유지한다.
8. 무료·유료 검증과 실제 브라우저 흐름을 수행하고 문서·main push·기존 Sites 배포·실제 URL/API를 확인한다.

파일 이름은 기존 구조에 맞추되 `ct-book`, `ct-decision-*`, `ct-experiment-*`, `ct-capabilities`, `binance-*`처럼 책임을 분리한다. `ct-research-store.ts`와 `ct-workspace.tsx`에 전부 누적하지 않는다. 인터페이스·라우트·스키마만 있고 연결되지 않은 기능을 완료 처리하지 않는다.

갱신 문서:

- `docs/ct.md`: 통합 구조, 부품과 북(`traderTools 7`), 현재 DB 재확인 수치, 게이트·엔진·지시문 diff·최종 저장/기억 경계·실행 결과·한계.
- §7.2 더하기형 보고서: 사전 등록 커밋과 결과 커밋, 데이터/비용/표본/반복 검정 수.
- `docs/binance-api.md`, `docs/local-runtime.md`, 필요한 `docs/deployment.md`, 비밀값 없는 `.env.example`.
- `AGENTS.md`: 새 CT 정책을 설명하는 한 줄. 기존 필독·배포 규칙은 유지한다.

사전 등록은 내용 검증 후 측정 전에 로컬 커밋하고, 요청한 구현의 검증이 끝난 시점에 결과와 함께 main에 push한다. 파일 저장마다 중간 코드를 배포하지 않는다. 환경변수 변경은 필요한 경우 기존 Sites secret 경로로 반영하며 값을 로그·문서에 남기지 않는다.

## 12. 필수 검증 — 구현 모양을 복제하는 테스트로 대체하지 말 것

### 시간·판단·기억

- 미래 봉/차트/메모리를 오염시켜도 이전 결정과 입력 해시가 같음.
- 상위봉·pivot 확정 지연·일자 경계·누락 봉·microseconds 변환이 정확함.
- 같은 결정 로그 재생은 모델 재호출 없이 같은 거래·비용·자산곡선을 생성함.
- 재시작/중복 이벤트/동시 요청에서 모델 비용·결정·주문 의도가 이중 기록되지 않음.
- 기억 scope 및 availableAt/split이 맞지 않으면 숫자뿐 아니라 결론도 평가 입력에서 제외됨.

### 플레이북·회계·위험

- 첫 되돌림/두 번째 되돌림, 같은 기준선 재시험, 만료/무효화, 범위 이탈 실패를 구별함.
- 상승/하락 대칭 fixture로 롱/숏 진입·손절·목표·trailing·갭 처리 확인. 옵션/역선물에는 별도 수작업 정답 fixture를 사용함.
- leverage가 달라도 같은 stop-risk 예산에 따른 수량과 증거금 한도가 정확함. 손익 단순 배수 적용을 잡는 테스트가 있음.
- funding 정산 직전/직후·방향·변동 주기, Margin 부분체결/이자/상환 잔액, COIN-M inverse PnL, 옵션 premium/만기·exercise를 확인함.
- cross·hedge·multi-asset/PM의 총위험, 강제청산, stop/청산 같은 봉, 담보 부족을 검증함. 처리 불가능한 상태는 fail closed임.
- 과거 계약의 기존 골든 결과가 유지됨.

### Binance 어댑터

- HMAC test vector, 시간 skew/recvWindow, Decimal 필터·notional·bracket, side/positionSide 모드 조합.
- 429/418 백오프, stale quote, WebSocket sequence gap, 중복/역순 user event, 부분체결, timeout 뒤 실제 체결, cancel/fill race, algo→실제 주문 연결, 재시작 대사.
- live lock이면 주문·차입·이체·설정 변경 등 모든 재정적 변경이 거부됨. 읽기/그림자/모의에서 실제 주문 API가 호출되지 않음.
- 신규 코인 경로에 Upbit 호출이 없고 legacy 청산/조회는 유지됨.
- 실제 읽기 스모크: 상품별 공개/서명 API·필터·수수료·권한을 결과 분류와 함께 확인. 실제 금액/키를 로그에 출력하지 않음.
- 실제 주문 경로는 공식 test/demo 환경과 별도 자격증명이 있을 때 검증한다. 자격증명이 없으면 계약/오류 fixture로 구현 검증하고 테스트넷 체결 미확인을 명시한다. 검증을 위해 운영 자금 주문이나 차입을 만들지 않는다.

### 비교 실험과 UI

- 동일 arm은 차이 0, 동일 일자 정렬·무거래 0·서로 다른 포지션 경로가 정확함.
- 알려진 개선/악화/무효 fixture에서 서버 판정과 신뢰구간·표본 부족 상태가 맞음. 데이터/위험 불일치 비교는 승인되지 않음.
- 평가 도중 config 수정 금지, 평가 노출 재사용 차단, A/B 공동 holdout 1회 소비와 재시작 복구가 맞음.
- 동일 1분봉 snapshot의 양 arm을 실제 하루 이상 끝까지 실행하고 decision→trade→daily→comparison→UI를 대조함. 알려진 미래 수익을 모델에 주는 fixture로 ‘성공’을 만들지 않음.
- 실제 브라우저에서 연구→검증 생성→진행→완료→날짜 행→동기 리플레이→뒤로 가기·새로고침, 실패·중단·재개, 모바일·키보드 동작을 확인함.
- 기존 테스트, 타입/린트, 적절한 로컬·Sites build를 수행한다. 전체 체크 실패는 원인과 기존/신규 여부를 구분하고 신규 문제를 고친다.

### 부품·북·과거 호환성
- 정책 6 이하의 지시문·도구·안정 블록 SHA-256 고정, 정책 6에서 0/0 제출 시 기존 종료 사유 그대로
- 정책 7 분기: 한도 여유가 있는 첫 0/0 → `reflect`, 0/0 연속 → 종료, 새 서명 2개 미만인 0/0 재제출 거부, 마지막 턴 통지 후에는 수용, 학습·개발 조건을 충족하는 부품만 제출한 fixture → `experiment` → `book`, 부족/실패 부품은 사유를 남기고 한도 내 reflect 또는 종료
- 부품 게이트: 알려진 군집 상관 fixture에서 이벤트 단위 검정의 과신을 군집 부트스트랩이 줄이는지(모든 표본에서 항상 더 보수적이라고 가정하지 않음), 월·집중 기준, 70% 겹침 중복 제거
- 북 엔진: 같은 봉에 부품 3개가 겹쳐 켜져도 진입 비용은 한 번만 낸다. 1봉 지연과 비용 2배가 적용된다. 부품 하나짜리 북 `vote k=1`이 같은 청산 규칙의 단일 후보와 **같은 거래**를 낸다(동등성 테스트). 연구와 모의 거래 엔진이 같은 입력에 같은 거래를 낸다.
- 시점: 어떤 부품·k·청산 선택도 학습 구간 밖의 봉을 읽지 않는다(경계 직전·직후 픽스처).
- 누출: 개발·최종 수치가 설계/교훈 입력으로 유입되지 않고, 최종 수치가 재사용 기억 행에 저장되지 않는다. 과거 기억의 허용 학습 수치와 owner가 읽는 평가 결과는 §2.2대로 별도 검증한다(99.9 주입 방식).
- 화면 모델: 12단계 목록, 종료 문구 형식, 부품 표와 북 카드의 빈 상태

기존 테스트 기준선을 먼저 기록하라. 시작 전부터 실패하던 테스트는 커밋을 지정해 구분하라.

- mixed timeframe 부품의 완성 봉·만료·반복 신호, confluence 해제, 일 경계, LONG/SHORT 북 충돌, Hedge 양쪽 비용과 실제 부분체결 회계를 검증한다.
- 개발 수익률 순서를 뒤집어도 학습에서 동결한 후보 우선순위·북 구성·k·청산 구조가 변하지 않는다. 부품 개발 실패 후 재조합이 금지되는지 확인한다.
- 북 1개짜리 동등성 fixture는 허용하되 제품 등록에서 2개 미만을 거부한다. capability 미충족·부품/실패 북의 우회 등록을 차단한다.
- 기존 11단계와 새 12단계, 건너뛴 단계, 현재 제품 v0.0/정책 7/실행 모델 ID를 혼동 없이 표시한다.

## 13. 실제 실행 검증과 비용 한도

### 13.1 무료 검증

- §7.2의 사전 등록 커밋이 측정 결과 커밋보다 먼저임을 확인하고 보고서를 완성한다. 모델 비용 $0을 확인한다.
- 실제 과거 연구 행의 11단계와 새 정책의 12단계 화면을 브라우저로 확인하고 스크린샷을 남긴다.
- 실제 DB·러너에서 부품/북/검토/최종 상태 전이·재개·거절을 통합 검증한다. 실제 시장에서 통과 후보가 없다면 분리된 테스트 DB와 명시적 fixture로 후속 경로를 검증한다. fixture 성과를 실제 연구 결과·실전 등록·수익 발견으로 보고하지 않는다.

### 13.2 유료 연구와 실제 비교

- 새 정책으로 **Binance Spot BTCUSDT의 1분 원자료 1회, NVDA 1회**, Opus 설계·각 연구 예산 $8로 실행한다. 판단 봉은 에이전트 선택이다. 해당 입력 상품·snapshot·모델 실제 ID를 실행 전에 동결한다.
- 두 연구를 포함한 이번 검증의 **추가 유료 모델/API 호출 합계는 $20 이하**다. 실제 하루 A/B 실행도 이 상한 안에서 사전 예약한다. 무료 결정 정책으로 end-to-end를 검증할 수 있으며 유료 LLM 리플레이 증거와 구분한다. 상한 부족은 결과와 남은 검증으로 보고하고 임의 증액하지 않는다.
- 판 서명 409는 자동 우회하지 않는다. 기존 repeat 절차가 허용하면 이유·기존 실행 ID를 기록해 진행하고, 허용되지 않으면 차단 사유를 기록하고 독립 검증을 계속한다. 날짜·버전·상품 이름을 바꿔 미노출인 척하지 않는다.
- 확인 항목: 첫 0/0 뒤 reflect/한도 종료의 실제 분기, 부품 통과·탈락·중복 사유, 북 수·실험 또는 미생성 이유, 종료 단계·사유·남은 예산, 누적 검정 수, `paidCall`의 실제 지출·예약·재개 중복 방지.
- 동일 1분 snapshot의 양 arm을 실제 하루 이상 끝까지 실행해 decision → trade → daily → comparison → UI를 대조한다. 합성 통과 fixture로 이 실제 비교를 대신하지 않는다. 무거래도 실제 결과다.
- 북이 비용을 못 넘으면 그대로 보고한다. 보기 좋은 결과를 위해 재실행하거나 실행을 선별하지 않는다. 부득이한 재실행·중단·오류도 비용과 함께 모두 보고한다. 실제 후보가 탈락했다면 최종 미개봉·후속 등록 차단이 올바른 결과다.

## 14. 완료 기준과 보고

코드가 실행되고 위 흐름이 실제로 연결돼야 한다. 기준 비교의 수익이 음수여도 정직한 결과와 정상 작동이 확인되면 구현 성과다. 양수 전략이 나올 때까지 임계값을 계속 바꾸거나 검사 기준을 완화하지 않는다.

다음 표를 최종 보고에 포함한다: `기능/상품 | 구현 | 데이터 | 계정 권한 | 자동 테스트 | 실제 읽기 | 모의/테스트넷 | 실전 활성화 | 남은 외부 제약`.

‘구현 미완료’, ‘권한 없음’, ‘데이터 없음’, ‘검증 실패’, ‘수익성 없음’은 서로 다른 상태다. 외부 제약이 있어도 독립적으로 가능한 구현·테스트·UI·문서 작업은 계속한다. 인터페이스만 만든 상품을 지원 완료로 보고하지 않는다. 신규 실전 기능은 구현하되 기본 잠금을 유지한다.

최종 전달물:

- 변경 이유와 실제 동작, 비교 실험 UX와 사용 흐름.
- 재현 가능한 테스트 명령·실험 id·기간·비용·결과·판정과 한계.
- 이전 계약/기록 보존·마이그레이션·rollback 방법.
- 비밀값 없는 설정 설명, Binance 기능/권한/데이터 표.
- 검증된 변경만 `main`에 commit/push한 commit SHA.
- `docs/deployment.md`와 Sites 스킬에 따라 기존 Sites 프로젝트 `appgprj_6a91dce3c51c8191bdb6b066a1c71d07`에 배포한 성공 상태와 실제 URL. 비공개 접근 권한 유지. 로컬 runner/bridge를 포함한 실제 API 연결도 확인한다.

완료 증거에는 정책 7의 첫 0/0 분기, 부품·북 흐름의 실제 DB 기록, ≤6 바이트/골든 보존, 개발 비최적화, 최종 단일 소비/기억 격리, 하나의 라우터·실행 엔진 연결, 사전 측정 보고서가 포함되어야 한다. 실제 연구가 부품/북 게이트에서 탈락한 경우 유료 실행이 최종까지 도달해야 한다고 강제하지 않는다. 미실행 후속 경로의 통합 테스트와 실제 성과 증거를 명확히 구분한다.

최종 보고 순서:

1. 바뀐 동작과 주요 파일, 연구→부품/북→검증→리플레이→운용 사용 흐름.
2. 코드·DB audit 결과와 더하기형 천장 결과·사전 등록/결과 커밋.
3. 유료 연구 2회 및 실제 A/B의 ID·기간·상품·단계별 결과·종료 사유·남은 예산·총지출.
4. 부품/북 숫자·게이트·누적 검정·판정·복기, 수익 전략 발견 여부와 구현 상태의 구분.
5. 테스트·브라우저·빌드 결과와 기존 실패/신규 실패 구분, 이전 계약 보존·rollback.
6. 기능/상품 capability 표, 라우터/운용 패키지/북/롱·숏 회계의 연결 상태, 남은 외부 제약과 미검증 사항.
7. main commit SHA·push 결과, 기존 Sites 프로젝트의 성공 상태·실제 URL·인증된 API/runner 연결 결과.

웹 코드 변경이 포함되는 이 구현 작업은 Sites 배포까지 수행한다. 이 프롬프트 자체만 편집하는 별도 작업은 문서 변경이므로 저장소 지침에 따라 검증·commit/push하며 사이트 배포 대상이 아니다.
