## 1. 왜 하는가

CT의 목표는 차트 단타 고수의 판단을 에이전트에 옮기는 것이다. 지금 설계자와 고수의 차이는 다음과 같다.

| 고수 | 현재 설계자 |
|---|---|
| 큰 움직임을 수천 번 보고, 그 직전에 무엇이 있었는지 안다(**결과 → 원인**) | 가설을 먼저 세우고 조회한다(원인 → 결과). 세션당 도구 24회 안에서 임계값까지 손으로 찾는다 |
| 차트를 **그림**으로 본다 | bp 정수 텍스트 240봉을 읽는다 |
| 플레이북이 쌓인다. 실패한 셋업도 기억한다 | 연구 기억(`ctMemory`)이 비용·자본·종목·엔진이 완전히 같은 이전 실행의 후보 12개 수치뿐이다. 1·2번 작업으로 계약이 바뀌면 사실상 0개가 된다 |
| 손실 거래를 복기해서 진입 문제인지 청산 문제인지 가른다 | 부모 후보의 거래 몇 개를 `read_bars`로 보는 정도다 |

LLM은 수치 공간을 손으로 탐색하는 데 약하고, "이 패턴에 메커니즘이 있는가, 우연인가"를 판단하는 데 강하다. 이번 작업은 역할을 그렇게 나눈다.
- **서버:** 거래할 가치가 있던 순간을 찾고, 그 직전의 차이를 통계와 그림으로 정리한다.
- **설계자(Opus):** 메커니즘을 판단하고, 규칙으로 옮기고, 스스로를 의심한다.

## 2. 작업 내용

### 2.1 결과 먼저 학습: `label_moves`, `contrast_moves` (가장 중요)

1번의 라벨·워크포워드 모듈을 재사용한다. 모든 계산은 **학습 구간 전용**이고 서버에서 하며 무료다. 결과는 `tool()` 캐시를 거친다.

**`label_moves`**
- 입력: `k`(MFE 배수, 기본 3), `m`(MAE 배수, 기본 1), `horizon`(봉 수 또는 `day_end`), 비용 배수(1 또는 2).
- 출력:
  - 양성 순간의 수, 하루 평균 수, 시간대·변동성 국면·요일·월별 분포.
  - 대표 시각 목록(`read_bars`·`view_charts` 앵커로 쓸 수 있게 서버가 발급).
  - `labelId`.
- 서로 겹치는 양성 순간(같은 움직임의 연속 시점)은 하나의 사건으로 묶어 센다. 묶음 규칙은 문서화한다.

**`contrast_moves`**
- 입력: `labelId`, 피처 명세 목록(feature·lookback·timeframe·unit, 임계값 없음, 최대 12개), 대조군 방식(기본: 같은 시간대 구간·같은 월에서 무작위 추출, 시드 고정).
- 출력:
  - 피처별 양성 직전 분포와 대조군 분포(분위수), 분위 구간별 lift(양성 비율 / 기저율)와 표본 수.
  - 선택: 얕은 결정 트리(깊이 ≤ 3, 잎 최소 사건 수 상한 이상). 잎마다 2번 청산 구조 하나를 가정한 비용 후 기대값을 준다.
  - **학습 구간 내부 안정성**: 앞 2/3로 찾은 분할을 뒤 1/3에서 다시 잰 lift.
  - `contrastId`. 이것은 근거 id로 인정한다(기존 `queryId`와 같은 규칙: 같은 feature·timeframe을 실제로 측정한 경우에만).
- 이 도구가 시험한 분위 구간·분할 수는 전부 2번의 다중 검정 장부에 합산한다.

설계자 지시(`CT_DESIGNER_SYSTEM`) 변경:
- 연구 순서의 기본값을 "**거래할 가치가 있던 순간을 먼저 보고 → 그 직전의 차이를 찾고 → 메커니즘을 세우고 → 조건부 수익으로 확인한다**"로 바꾼다.
- 가설 먼저 접근도 허용한다.
- `contrast_moves`의 lift는 "어디를 볼지"의 단서일 뿐, 성과 근거가 아님을 명시한다. 최종 확인은 `query_conditional_returns`와 `screen_rule`로 한다.

### 2.2 차트를 그림으로 보기: `view_charts`

1. **서버가 캔들 차트 PNG를 만든다.**
   - SVG를 그린 뒤 PNG로 변환한다. 의존성은 순수 Node에서 동작하는 것으로 고르고 이유를 적는다. 예: `@resvg/resvg-js`.
   - 한 장은 다중 시간대 패널이다.
     - 왼쪽: 최근 5일의 1시간봉. 전일 고가·저가 표시.
     - 가운데: 당일의 5분봉. VWAP, OR 박스, 전일 고가·저가·종가 선.
     - 오른쪽: 앵커 직전 90분의 1분봉. 거래량 막대 포함.
   - 축에는 가격 대신 앵커 시점 대비 %를 쓴다. 가격 수준이 결과를 암시하지 않게 하기 위해서다.
   - 날짜는 표시하지 않는다. 시간대(시각)는 표시한다.
2. **앵커 뒤의 봉은 그리지 않는다.** 결과는 그룹 소속(양성/대조군)으로만 알려 준다.
3. 입력:
   - 앵커는 서버가 발급한 시각만 받는다(`label_moves` 대표 시각, 대조군 시각, 부모 후보의 학습 거래).
   - 한 번에 최대 8장, 세션당 최대 32장(정책 값으로 둔다).
4. 이미지는 tool_result의 image 블록으로 넘긴다.
   - 이미지 크기와 실제 입력 토큰을 측정해 보고한다.
   - 캐시 지점 배치가 깨지지 않는지 확인한다(이미지가 든 결과도 이후 턴에서 캐시 읽기로 재사용돼야 한다).
5. **보정 모드(선택 파라미터 `blind: true`).**
   - 양성·대조군을 섞고 그룹을 숨긴 채 보여 준다.
   - 설계자가 다음 턴에 `grade_blind`로 각 장의 예측(양성/대조군)을 제출하면 서버가 정답률과 이항 검정 p값을 돌려준다.
   - 설계자의 "눈"이 이 시장에서 신호를 갖는지 스스로 확인하는 장치다.
   - 결과는 세션 기록과 검토자 입력에 남긴다.
6. 차트 렌더러는 미래 봉 미포함, 학습 경계, 축 정규화를 테스트로 고정한다.

### 2.3 누적 플레이북 (실행 간 기억)

`ctMemory`를 대체하는 시장 단위 플레이북을 만든다.

1. **새 테이블 `ct_playbook`**(SQLite 마이그레이션, `ensureSchema` 패턴 준수). 항목 하나의 필드:
   - 시장, 종목 집합
   - 메커니즘 요약(한국어 1–2문장)
   - 조건 구조 요약(feature·timeframe 수준, 임계값 제외)
   - 검증 방식(`queryId`/`contrastId`/후보 id)
   - 결과 등급: `rejected_in_training` / `screen_failed` / `development_failed` / `passed_final` / `failed_final`
   - 탈락 사유
   - **측정 기간**(학습·개발 구간 경계)
   - 비용 프로필 버전, 엔진 버전, 실행 id, 날짜
2. 연구가 끝날 때(정상 종료·통과·탈락 모두) 다음을 기록한다.
   - 설계 세션의 `rejectedHypotheses`
   - 학습 게이트 탈락 후보
   - 개발 결과
3. **누출 방지(필수).**
   - 새 연구의 개발·최종 구간과 측정 기간이 겹치는 항목은 수치 없이 "메커니즘 + 결과 등급"만 보여 준다.
   - 최종 구간 성과 수치는 어떤 경우에도 설계자에게 보여 주지 않는다.
   - 기존 `ctMemory`도 `developmentToMs` 비교만 하고 개발 구간 겹침은 검사하지 않는다. 이 점을 함께 고친다.
4. **초기 시드**: `docs/research/results-2026-09.md`의 기각·생존 결과를 항목으로 넣는다. 일봉·다른 시장 결과는 `timeframe: daily`, `market` 구분과 "단타와 직접 비교 불가" 표시를 붙인다.
5. 설계 세션 안정 블록(캐시되는 부분)에 플레이북 요약을 넣는다.
   - 같은 시장 최근 항목 우선이고, 길이 상한을 둔다.
   - 시장별 **누적 검정 수**도 같이 보여 준다.
6. 위험·증거 검토자에게 누적 검정 수와 관련 플레이북 항목을 전달한다. 검토 지시에 다음을 추가한다: "이미 기각된 메커니즘의 변형인가, 누적 검정 수를 고려해도 개발 결과가 의미 있는가".
7. 플레이북을 보는 화면을 CT에 추가한다. 읽기 전용 목록과 필터면 충분하다.

### 2.4 손실 복기: `diagnose_trades`

`screen_rule` 결과의 학습 구간 거래만 받는다(후보 id 또는 screen id).

- **분해:** 시간대, ATR 국면 3분위, 상위 시간대 추세 상태(1시간 SMA 위·아래), 요일, 보유 시간, 청산 사유별로 거래 수와 비용 후 기대값을 나눈다.
- **진입 문제 vs 청산 문제:**
  - 손실 거래 중 진입 후 한 번이라도 +1R(또는 +2×왕복비용)에 닿았던 비율을 잰다. 이 비율이 높으면 **청산 문제**다.
  - 한 번도 수익권에 못 간 비율도 잰다. 이 비율이 높으면 **진입 문제**다.
  - 이익 거래의 MFE 대비 실현 비율(놓친 수익)도 잰다.
- **청산 반사실:** 같은 진입 집합에 2번의 청산 모드(본전·트레일·시간 손절)를 적용한 결과를 나란히 보여 준다.
- 결과의 필터 제안("저변동 아시아 시간대 손실 집중")은 근거로 쓸 수 있다.
  - 단, 필터를 추가한 후보는 부모 후보 대비 변경으로 기록한다.
  - 다중 검정 장부에도 반영한다.

### 2.5 설계 세션의 흐름과 한도

1. `CT_DESIGNER_SYSTEM`을 "단타 고수의 작업 순서"로 다시 쓴다. 단계를 강제하지 말고 이유를 설명하는 기존 문체를 유지한다.
   1. 판 읽기: 비용 장벽, 플레이북, 누적 검정 수
   2. 거래할 가치가 있던 순간 보기: `label_moves`, `view_charts`
   3. 직전의 차이 찾기: `contrast_moves`, 보정 모드
   4. 메커니즘 세우기와 반증 조건 적기
   5. 확인: `query_conditional_returns`
   6. 청산 설계: 청산 모드 비교
   7. 학습 검증과 복기: `screen_rule`, `diagnose_trades`
   8. 제출 전 자기 반박: 이 규칙이 우연일 가장 그럴듯한 이유 3가지와, 그것을 데이터로 배제했는지를 `submit_candidates`의 새 필드 `selfRebuttal`에 적게 한다
2. 도구가 늘었으므로 세션 한도를 측정 근거로 조정한다. 예: 턴 16, 도구 40, `view_charts` 32장.
   - 새 계약에서만 적용하고(`CTPolicyLater` 패턴), 기본 예산 $8 안에서 1회 실행 비용을 측정해 보고한다.
   - 예산을 넘는다면 이미지 수·해상도부터 줄인다.
3. 진행 화면(`lib/ct-activity.ts`, `app/ct-progress.tsx`)에 새 도구 표시를 추가한다.
   - 라벨 수
   - contrast 상위 lift
   - 본 차트 썸네일
   - 보정 정답률
   - 복기 요약(진입/청산 문제 비율)

## 3. 바꾸면 안 되는 것

- 1번 지시서 3절과 2번 지시서 3절의 불변 조건 전부. 게이트 완화 금지, 롱 전용, 당일 청산, 1분봉 백테스트, 시간순 60/20/20, 최종 구간 1회 평가.
- **모든 새 도구는 학습 구간 전용이다.** 앞을 내다보는 구간이 `trainingToMs`를 넘는 라벨·대조군·차트·거래는 버리거나 거부한다.
- 설계자에게 개발 구간은 요약 수치만, 최종 구간은 아무것도 주지 않는다. 플레이북도 이 규칙을 따른다.
- 독립 검토자는 설계자와 다른 회사(`assertDifferentProvider`).
- Opus 5.5 요청 제약, preserved thinking(assistant content 무수정 append), 턴 단위 비용 장부, 재개 시 재지불 없음.
- 모든 모델 입력은 신뢰하지 않는 데이터로 다룬다.

## 4. 테스트

1. `label_moves`: 합성 데이터로 양성 판정, 겹치는 사건 묶음, 학습 경계 밖 앞구간 제외, 비용 배수 반영.
2. `contrast_moves`:
   - 대조군이 같은 시간대·월에서 추출되고 시드로 재현된다.
   - 미래 정보 미사용.
   - 앞 2/3 → 뒤 1/3 안정성 계산이 맞다.
   - 시험 구간 수가 검정 장부에 합산된다.
   - `contrastId` 근거 규칙(feature·timeframe 일치)을 지킨다.
3. `view_charts`: 앵커 이후 봉 미포함, 서버 발급 앵커만 허용, 장 수 한도, 축 % 정규화, 날짜 미표시, `blind` 모드에서 그룹 비노출, `grade_blind` 정답률·p값 계산.
4. 이미지 tool_result가 다음 턴 요청에 바이트 그대로 포함되고 캐시 지점이 유지된다(모의 fetch).
5. 플레이북:
   - 연구 종료 시 기록.
   - 개발·최종 구간이 겹치면 수치 비노출.
   - 최종 성과 미노출.
   - 시드 항목 로딩.
   - 기존 `ctMemory`의 개발 구간 겹침 수정.
6. `diagnose_trades`: 진입/청산 문제 분류, 청산 반사실이 `ctExitStep`과 같은 결과를 낸다.
7. `selfRebuttal` 필수 검증과 검토자 입력 포함.
8. 세션 재개: 이미지가 포함된 턴 이후 중단 → 재개 시 재지불 없음.
9. 진행 화면이 새 도구 활동을 표시한다(`tests/ct-activity.test.mjs` 확장).

## 5. 실제 실행 검증

1. `npm run local`로 앱·러너를 띄우고, CT → 코인 기본값으로 **전략 생성**을 실제로 끝까지 실행한다. 가능하면 주식(NVDA)도 1회 실행한다.
2. 보고할 것:
   - 설계 세션별 도구 사용 순서와 횟수, 특히 `label_moves`→`contrast_moves`→`view_charts`→확인의 흐름이 실제로 나타났는지.
   - 본 차트 수, 이미지 입력 토큰, 캐시 읽기 토큰, 역할별 비용, 총비용($8 대비).
   - 보정 모드 정답률과 p값(실행했다면).
   - 플레이북에 기록된 항목 수와 예시 3개.
   - `diagnose_trades`가 바꾼 후보가 있었다면 그 변경과 결과.
   - 후보 수 → 학습 통과 → 개발 통과, 탈락 사유.
   - 1번·2번 작업 후 실행과의 비교표.
3. 진행 화면 스크린샷: 새 도구 활동, 차트 썸네일, 플레이북 화면.
4. 같은 설정으로 두 번째 연구를 실행해, 플레이북이 첫 연구의 기각 가설을 실제로 피하는지 확인한다(누출 규칙이 지켜지는지도 함께).
